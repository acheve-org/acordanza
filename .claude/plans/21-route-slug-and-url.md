# A shareable, per-area-scoped route URL

Status: done
Issue: not filed yet — file one and link it here before the `plan:` commit
Depends on: nothing. Independent of [20](20-route-display-revamp.md) (the card/modal visual revamp) — either can ship first, in either order; nothing here requires §1–§3 of that plan, and nothing there requires a route to have a slug. Backend: one new `ClimbingRoute.Slug` column + migration + a `by-slug-path` endpoint, mirroring [13](13-first-ascensionist-slug.md)'s `FirstAscensionist.Slug` generation mechanics but `Area`'s per-parent scoping. Frontend: a routing change that consolidates **six** pages' separately-wired detail-modal logic into one shared, URL-addressable overlay.

## Problem

Routes have no shareable URL today. `DetailModal` opens as pure client-side state (`detailRouteId`) on whichever page is behind it, so a specific route can't be linked, bookmarked, or reached with the browser back button — unlike `Area` (`/areas/*`) and `FirstAscensionist` (`/fa/:slug`), both of which already have slugs and their own URLs.

Fixing that surfaces a second, pre-existing problem: **six** pages, not the three you'd guess from "route browsing" (`SearchPage`, `AreaPage`, `FirstAscensionistPage`), independently hand-roll the same `DetailModal` wiring — fetch, six mutations (delete/validate/reject/tick/topo-upload/topo-delete), open/close state — each slightly differently. `PendingTasksPage` and `MyTicksPage` do it too (confirmed by direct grep, not assumed), the former via its own pending-items list rather than `RoutesList`, the latter from clicking a `TickedRouteCard` row. `MyOpeningsPage` is the third of the "hidden" three, using `RoutesList` the same way the well-known trio does. Giving routes a URL is also the natural point to collapse all six onto one implementation.

## Design

### 1. `ClimbingRoute` gains a persisted `Slug` column, scoped per-area

Matching how `Area.Slug` is scoped per-parent, not `FirstAscensionist.Slug`'s flat global namespace. A single global slug namespace across every route in the app was the initial idea and is worth rejecting explicitly: `ClimbingRoute.Name` has no uniqueness constraint at all today (not even per-area), so a global slug would hit the `-2`/`-3` suffix loop constantly on any common route name ("Directa", "Fisura", "Vía Nueva" — the kind of name that recurs across dozens of unrelated crags) and produce noisy, meaningless suffixes. Scoping to the route's area fixes both problems at once: collisions only have to be disambiguated among an area's own routes (typically a handful to a few dozen), and the resulting URL is a real path rather than an opaque slug-plus-suffix.

- **URL shape**: `/routes/{area-slug-path}/{route-slug}`, e.g. `/routes/riglos/pena-amarillo/fisura-del-diablo` — the same `{area-slug-path}` `AreaHierarchyService` already computes (`AreaHierarchy.SlugPath(areaId)`, the exact method `RoutesController.UploadTopo` already calls for the topo blob prefix, `backend/Acordanza.Api/Controllers/RoutesController.cs:452`) plus the route's own leaf `Slug`. Nothing about the area-path segment is stored on `ClimbingRoute` — it's resolved live from `AreaId` via the existing hierarchy snapshot, the same way `Area`'s own multi-segment breadcrumbs are never stored, only each node's own `Slug` is.
- **Moving a route to a different area changes its URL, silently, with no redirect — accepted as-is.** The stored `Slug` doesn't change, but the next time its URL is built (client-side, from `AreaSlugPath` + `Slug`) it reflects the new area automatically. This mirrors how `Area`'s own path already updates automatically when a subtree is reparented, so it's consistent with the rest of the app. A stale bookmark/shared link to a moved route 404s rather than redirecting — considered and explicitly accepted rather than building an id-based fallback-redirect route: at this app's scale (six users), a broken link means asking whoever sent it to resend it, and a redirect mechanism is real code for a failure mode that costs nothing to just... not have.
- **Uniqueness**: `(AreaId, Slug)` unique index, and `GenerateUniqueRouteSlugAsync(areaId, name, excludeId?)` scopes its `-2`/`-3` collision loop to `AreaId` — copied from `AreasController.GenerateUniqueAreaSlugAsync(parentAreaId, name)`, not `FirstAscensionistsController`'s flat version. On `UpdateRoute`, if `AreaId` changes, the slug is regenerated against the *new* area's sibling set too (a route moved into an area that happens to already have a same-named route still needs the suffix).
- **Regenerated on rename or area move, not frozen at creation** — this follows `FirstAscensionist`, not `Area`, and needed checking carefully: `Area.Slug` freezes forever specifically because it doubles as the topo blob-storage path prefix, and changing it would orphan uploaded images. Route topo blob names *look* slug-shaped (`{area-slug-path}/{route-slug}-{NN}.{ext}`) but are actually computed fresh at upload time from `Slugify.ToSlug(route.Name)` directly — there is no persisted `Route.Slug` today, and this plan's new column is not wired into that blob-naming code at all (leave `UploadTopo`'s `blobPrefix` line untouched). So nothing is keyed on the new column, and it can safely regenerate whenever `Name` or `AreaId` changes.
- Migration: add the column + a raw-SQL backfill (lowercase, accent-strip via `translate()`, `regexp_replace` to collapse non-alphanumerics, `ROW_NUMBER() OVER (PARTITION BY "AreaId" ORDER BY "Id")` dedupe suffixing — partitioned, unlike `FirstAscensionist`'s ungrouped version) + the composite unique index — same shape as `20260808140244_AddFirstAscensionistSlug.cs` and `20260804110308_AddAreaSiblingSlugUniqueness.cs` combined.
- New `GET /routes/by-slug-path/{*path}` (named to match `GET /areas/by-slug-path/{*path}`, not `FirstAscensionist`'s flat `by-slug/{slug}`) returning `RouteDetailDto`: split the trailing segment off `path` as the route slug candidate, resolve the remaining segments to an area via `AreaHierarchy.ResolveSlugPath` (the same method `AreasController`'s equivalent action already uses), then look up the route by `(AreaId, Slug)`. Alongside, not replacing, the existing numeric `GET /routes/{id}` — `RouteFormPage`'s edit route (`/routes/:id/edit`) keeps using the numeric id, only the *viewing* path moves to the slug path.
- Both `Slug` and a new `AreaSlugPath` (the pre-computed `AreaHierarchy.SlugPath(route.AreaId)` string) are added to `RouteDto` and `RouteDetailDto` — every list card needs both to build the full detail-link path client-side, so they travel on the summary shape, not just the detail one (unlike `FirstAscensionist.Slug`, which only lives on the profile DTO since that page doesn't need to construct links from a list card).

### 2. One shared, URL-backed overlay, replacing six separate copies of the same wiring

`App.tsx` adopts the standard react-router "background location" pattern: render the normal route tree against `location.state?.backgroundLocation ?? location`, and — only when a `backgroundLocation` is present in state — render a second, small `<Routes>` on top matching `routes/*` (a splat, since the path now carries a variable number of area segments plus the route slug) to a new `RouteDetailOverlay` component. `RouteDetailOverlay` reads the full match via `useParams()['*']`, is the *only* place `DetailModal` is ever rendered from now on, owns the by-slug-path fetch and all six mutations, and closes via `navigate(backgroundLocation)`.

**All six pages fold onto it — not just the three "browse" ones.** `PendingTasksPage` (a review queue) and `MyTicksPage` (tick history) are structurally different contexts from "browse and open a route," but the point of the consolidation is that exactly one component owns route-detail display; carving out two of six as exceptions would mean keeping two copies of the six-mutation wiring for no clear benefit, and a route opened from any context becomes equally shareable/bookmarkable, which is a fair side effect rather than a problem.

- **`SearchPage`, `AreaPage`, `FirstAscensionistPage`, `MyOpeningsPage`** all use `RoutesList`, so `RoutesList`'s `onSelect` prop changes from `(id: number) => void` to `(route: RouteSummary) => void`, and each page's `onSelect` becomes `navigate(`/routes/${route.areaSlugPath}/${route.slug}`, { state: { backgroundLocation: location } })`.
- **`PendingTasksPage`** doesn't use `RoutesList` (it renders its own pending-items list) — its row click handler gets the same `navigate(...)` call directly, using the `RoutePendingDto`'s own area/route slug fields (extend `RoutePendingDto` with `AreaSlugPath`/`Slug` the same way `RouteDto` gets them).
- **`MyTicksPage`** opens the modal from a `TickedRouteCard` row click, not `RoutesList` — same direct `navigate(...)` treatment, needing `AreaSlugPath`/`Slug` added to `MyTickDto` too (a second small DTO addition here, independent of plan 20's `Length` addition to the same record).
- **`routes/*` vs. the existing static routes.** React Router ranks static/dynamic segments above splats, so `routes` (exact, `SearchPage`'s list), `routes/new`, and `routes/:id/edit` all keep matching before `routes/*` is ever tried — no route needs reordering, `routes/*` just catches everything else under the prefix.
- **Fresh-visit fallback** (a pasted link, a reload, no `backgroundLocation` in history state): the normal route tree needs its own match too, so `<Route path="routes/*" element={<SearchPage />} />` joins the existing `<Route path="routes" element={<SearchPage />} />`. `SearchPage` reads `useParams()['*']` and, if non-empty on mount with no `backgroundLocation` already in state, immediately `navigate('/routes/' + splat, { replace: true, state: { backgroundLocation: { pathname: '/routes' } } })` — synthesizing the overlay state once so `RouteDetailOverlay` is still the only component that ever opens the modal, regardless of which of the six pages the link originally came from.
- Net effect on all six pages: each **loses** its `detailRouteId`/`detailRoute` state, its six mutations, and its `<DetailModal .../>` block — they keep only their own list-fetch/filter logic and a click handler that navigates. This is a simplification, not just plumbing to support the URL — six copies of the same wiring become one.

### 3. `RouteFormPage` redirects to the saved route, not the plain list

Today, both create and edit unconditionally `navigate('/routes')` after a successful save (`RouteFormPage.tsx:135`) — you never land on the route you just created or edited. Now that every route has a real detail URL, the save handler instead navigates to `/routes/${areaSlugPath}/${slug}` (available from the create/update response once it echoes the generated slug, or from a follow-up fetch if it doesn't — decide at implementation time which is cheaper). Small, natural fit, and it was a rough edge nobody had previously had the means to fix.

### Non-goals

- **`MyContributionsPage` gains no route-detail entry point.** It's a read-only status table with no click-through today; wiring a click on a contribution row to the new overlay is an obvious, low-cost follow-up once this exists, but it's new functionality nobody asked for and is deliberately left for a separate, later change.
- **No id-based redirect fallback for a moved route's old URL** — see §1's "accepted as-is."
- **No change to topo blob naming** — the new `Route.Slug` column is not read by `UploadTopo`.
- **No visual changes to `RouteCard`/`DetailModal`** — that's [plan 20](20-route-display-revamp.md).

## Steps

1. **Backend.** `Models/ClimbingRoute.cs` (`Slug` property, doc comment referencing the per-area-scoped, regenerate-on-rename-or-move rationale), `Data/AppDbContext.cs` (`HasIndex(r => new { r.AreaId, r.Slug }).IsUnique()`, mirroring `Area`'s `(ParentAreaId, Slug)` index), migration (column + partitioned backfill + composite index, modeled on `20260808140244_AddFirstAscensionistSlug.cs` + `20260804110308_AddAreaSiblingSlugUniqueness.cs`), `RoutesController` (`GenerateUniqueRouteSlugAsync(areaId, name, excludeId?)`, wired into `CreateRoute` and, on name *or* area change, `UpdateRoute`; new `GET /routes/by-slug-path/{*path}` action using `AreaHierarchy.ResolveSlugPath`), `Dtos/RouteDtos.cs` (`Slug` + `AreaSlugPath` on `RouteDto`/`RouteDetailDto`), `Dtos/RoutePendingDto` and `Dtos/TickDtos.cs`'s `MyTickDto` (same two fields, for §2's `PendingTasksPage`/`MyTicksPage` direct-navigate cases).

6. **Docs.** Root `CLAUDE.md`: no change (route slugs aren't part of the four-section table). `backend/CLAUDE.md`: `ClimbingRoute` bullet gains its per-area-scoped `Slug` sentence (contrasted with `Area`'s and `FirstAscensionist`'s), `RoutesController` bullet gains `GET /routes/by-slug-path/{*path}`. `frontend/CLAUDE.md`: the "Modal/dropdown data is fetched by the thing that needs it, when it opens" rule gets a note that `RouteDetailOverlay` is the sole owner of route-detail fetching now, and the per-page bullets for all six affected pages drop their now-removed local detail-modal wiring.
7. **Verify** with the `run-acordanza` skill: open a route from each of the six contexts (Busca, an area page, an aperturista page, "Mis aperturas", "Mis vías", the pending-tasks review queue) and confirm the URL updates to `/routes/{area-slug-path}/{route-slug}`, the underlying list/filters/scroll stay intact, browser back closes the modal, and a hard reload on that URL renders Busca underneath with the modal open. Confirm saving a new/edited route lands on that route's own detail view.

## Testing

**Backend** (`RoutesTests.cs`, extend existing):
- Slug generated on create, collision within the same area suffixed (`-2`); the same name in a *different* area does **not** get suffixed (proves the scoping is per-area, not global).
- Regenerated on rename; regenerated (against the new area's sibling set) when a route is moved to a different area; unchanged on a no-op re-save (`excludeId` guard).
- `GET /routes/by-slug-path/{*path}` resolves a full `{area-slug-path}/{route-slug}` correctly, including a multi-level area path; unknown area path, unknown route slug within a valid area, and a route-slug-only path with no area segments all → 404.
- `RouteDto`/`RouteDetailDto` responses include `slug` and `areaSlugPath`; `RoutePendingDto`/`MyTickDto` likewise.

**Frontend:**
- New `RouteDetailOverlay.test.tsx` — the six mutations (delete/validate/reject/tick/topo-upload/topo-delete) fire against the right endpoint and close/invalidate correctly; this is the test that used to be split (differently) across each of the six pages' own test files and now has one home.
- `SearchPage.test.tsx`/`AreaPage.test.tsx`/`FirstAscensionistPage.test.tsx`/`MyOpeningsPage.test.tsx`/`PendingTasksPage.test.tsx`/`MyTicksPage.test.tsx` — each updated to assert its row/card click navigates to `/routes/{areaSlugPath}/{slug}` with background-location state, rather than opening a local modal.
- One test exercising the fresh-visit fallback: render at a `/routes/{areaSlugPath}/{slug}` URL directly (no router state), assert `SearchPage` renders and the overlay opens.
- **New `App.test.tsx`-level test for the background-location mechanic itself** — the riskiest new piece and, until now, covered only by manual click-through: render the app at a list route, simulate opening a route (navigate with background-location state), assert the underlying list is still mounted (not unmounted/remounted) and its state is preserved, assert browser-back (`window.history.back()` via the test router) closes the overlay and returns to the exact prior location/state, and assert a direct render at a `/routes/{areaSlugPath}/{slug}` URL with no prior state falls back to `SearchPage` + open overlay rather than a blank/broken route match.
- `RouteFormPage.test.tsx` (extend) — save navigates to the new/edited route's detail URL, not `/routes`.
