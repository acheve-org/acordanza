# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Applies to `backend/Acordanza.Api/` — the ASP.NET Core (.NET 10) Web API. See the root `CLAUDE.md` for how this fits with the frontend.

## Commands

All run from `backend/Acordanza.Api/`:

```
dotnet build                                                      # compile
dotnet run                                                        # run the API on http://localhost:5073
dotnet run -- create-user <email> <password> <name> [role]        # provision an account (only way to create one — no HTTP registration); name max 20 chars; role defaults to 'user' (other roles: 'moderator', 'admin')
dotnet run -- enqueue-enrichment <routeId> [--force]               # enqueue route enrichment (plan 18) without the HTTP layer — local smoke-test / operator escape hatch
dotnet run -- process-enrichment                                   # drain the route-enrichment queue once and exit — what the Container Apps Job runs in production
dotnet ef migrations add <Name>                                   # add a migration after changing a model/AppDbContext
dotnet ef database update                                         # apply pending migrations
```

First-time setup (once per machine): `dotnet user-secrets set "Jwt:Key" "$(openssl rand -base64 48)"`. The connection string in `appsettings.json` assumes the `docker-compose.yml` Postgres defaults (`localhost:5432`, db/user/password `acordanza`); `appsettings.Development.json` likewise assumes its Azurite container (topo images, Data Protection keys, and now the route-enrichment queue — see Storage below) is up, so `docker compose up -d` (from the repo root) must be running before `dotnet run`. To exercise `process-enrichment`/`enqueue-enrichment` for real (not the no-op fallback — see Route enrichment below), a contributor also needs `Anthropic:FoundryResource` configured and their own `az login` session to carry the **Cognitive Services User** role on the Foundry resource — Storage/queue is Azurite-emulated locally, but Foundry has no emulator, so this makes a real call against the real Azure resource.

Migrations run automatically on startup (`db.Database.MigrateAsync()` in `Program.cs`) as well as before the `create-user` CLI path — you don't need to run `dotnet ef database update` before every `dotnet run`, only when you want the schema applied without booting the full app.

`backend/Acordanza.Api.Tests/` (xUnit v3 + Shouldly) holds the test suite, in two tiers:

- **Unit tests** — pure classes with no `DbContext`/`HttpContext` (`Services/Slugify`, `Models/Validation`, `Services/AreaHierarchy`, `Authorization/RolePermissions`, `Authorization/Permissions`). No Docker or database needed. Run with `dotnet test Acordanza.slnx --filter "Category!=Integration"` (or the equivalent plain `dotnet test --filter ...` from `backend/Acordanza.Api.Tests/`) — milliseconds, since Testcontainers/`WebApplicationFactory` are never instantiated when nothing needs them.
- **Integration tests** (`Infrastructure/`, plus everything tagged `[Trait("Category", "Integration")]`) — real HTTP requests through `WebApplicationFactory<Program>` against a real Postgres + Azurite pair started per test run via Testcontainers, reset to a clean slate between tests with Respawn (see `Infrastructure/ApiFixture.cs`). Needs Docker running locally. `Infrastructure/TestUsers.cs` seeds a user in a role (plus the two dynamic-grant variants: first-ascensionist-linked, area-expert) and logs them in for real through `POST /api/auth/login`, so the JWT claims under test are the ones production issues — never minted directly. `Infrastructure/SeedData.cs` holds composable area/route/first-ascensionist seeding helpers.

Run everything (both tiers) with plain `dotnet test Acordanza.slnx` from the repo root, or `dotnet test` from `backend/Acordanza.Api.Tests/`.

The integration fixture configures the app entirely through **process environment variables** (`ConnectionStrings__Default`, `Storage__ConnectionString`, `Jwt__Key`, ...), not `WebApplicationFactory`'s configuration hooks — `Program.cs` reads these off `builder.Configuration` *before* `builder.Build()`, earlier than those hooks can reach, so it's the only seam that lands in time. This is process-global, which is why `ApiFixture` is an xunit.v3 **assembly fixture** (`[assembly: AssemblyFixture(typeof(ApiFixture))]`), not per-class: two differently-configured hosts must never exist side by side, and tests don't run in parallel within the assembly (`[assembly: CollectionBehavior(DisableTestParallelization = true)]`) for the same reason. The env vars leak into the test process only, not the developer's shell — a `dotnet test` run and a `dotnet run` in the same shell session don't affect each other.

## Architecture

Flat, controller-per-resource structure — there is no service/repository layer; controllers talk to `AppDbContext` directly via EF Core:

- `Controllers/` — `AuthController` (login incl. passkey second factor, `/auth/me`, forgot/reset-password, `/accept-invite`), `AccountController` (self-service password change and profile name update), `PasskeysController` (register/list/delete the current user's passkeys), `RoutesController` (CRUD on routes + nested `POST /{id}/ticks`, `POST /{id}/validate`, `POST /{id}/reject`, `POST /{id}/topos`, `POST /{id}/enrich` (admin-only, `Permissions.RouteEnrich` — enqueues route enrichment, plan 18, see Route enrichment below); `GET /` filters on `q`/`areaId`/`grade`/`orientation`/`gear`/`hasTopo`/`firstAscensionistId`, `POST`/`PUT` reject a grade that isn't a valid French-scale value via `Models/GradeValidator` (issue #152), `GET /grades` lists the distinct grades in use for the frontend's filter dropdown, and `GET /routes/by-slug-path/{*path}` resolves a route by its full shareable path — the trailing segment as the route slug, the rest walked via `AreaHierarchy.ResolveSlugPath` the same way `AreasController`'s equivalent action does — alongside, not replacing, the numeric `GET /{id}` (plan 21)), `ToposController` (`DELETE /{id}` only — upload lives on `RoutesController`), `AreaMediaController` (`DELETE /{id}` only — the area-media mirror of `ToposController`; upload lives on `AreasController.UploadAreaMedia`), `AreasController` (tree CRUD incl. `/roots`+`/{id}/children` for lazy-loaded management UI, `PUT /{id}/coordinates` for the map polygon, `POST /{id}/validate`, `POST /{id}/reject`), `AreaExpertsController` (self-service request/approve/reject flow for area-scoped route-validation rights — see below), `FirstAscensionistsController` (list/create/update/delete, `GET /profiles` and `GET /by-slug/{slug}` — the same records enriched with each one's route count and areas, for the frontend's "Sigue" section — plus `POST /{id}/validate`, `POST /{id}/reject` and `GET /pending` for its own `IValidatable` review queue, see below), `FirstAscensionistLinksController` (self-service claim/approve/reject flow — see below), `TicksController` (`GET /mine` — the current user's own paginated, filterable tick history, its `MyTickDto` rows carrying just enough of the route (incl. `Length`, plan 20) to render `TickedRouteCard` without a second round-trip; deletion), `UsersController` (`GET /` — admin-only paginated/filterable user list; `POST /invite` and `GET /my-invites` — gated on `user.invite`, which *every* role holds, so any user can invite up to a backend-managed per-role quota (`Invites:MaxForUser`/`MaxForModerator`, admins unbounded — issue #113); `my-invites` returns the caller's invitees plus `invitesLeft`/`maxInvites`, backing `/my-acordanza/my-invites`), `ContributionsController` (`GET /routes`, `GET /areas`, `GET /first-ascensionists` — a read model over the routes/areas/first-ascensionists the current user created plus each one's validation status, backing the "Contribuciones" page under "Mi acordanza"; belongs to no single resource, so it isn't folded into any of the three controllers above. One paginated endpoint per kind rather than one payload with all three (issue #149), since the page shows a single tab at a time and the other two kinds are never fetched until their tab is opened; the paths carry no `mine` segment because every action derives its filter from `GetUserId(User)` and never accepts an id from the client. Ordering is `CreatedAt` descending with an `Id` tie-break — `CreatedAt` alone isn't a total order, and without the tie-break a tied row could appear on two pages and another on none). All routes require `[Authorize]` (JWT bearer); write actions additionally require `[Authorize(Policy = Permissions.X)]` — see Authorization below.
- **Validation visibility** (issue #72, plan 11) — `GET /routes`/`/routes/grades`, `GET /areas`/`/areas/roots`/`/areas/{id}/children`, `GET /first-ascensionists`/`/first-ascensionists/profiles` and `GET /areas/by-slug-path/*`'s `children` projection all filter to `Models/ValidationVisibility.cs`'s rule — `x.ValidationStatus == Approved || x.AddedByUserId == callerId` — so a pending/rejected record stays reachable only to its author and to reviewers. Detail-by-id/slug reads (`GET /routes/{id}`, `GET /first-ascensionists/by-slug/{slug}`, the area itself in `GET /areas/by-slug-path/*`) are deliberately **not** gated — this is a private app where every account can already read everything, and a pending record is only reachable by guessing its id/slug; gating "lists" but not "details" is the line the plan draws. A route's embedded `FirstAscensionists` credits are never filtered either, even when the opener record itself is pending. Three new query-string affordances carry the exceptions:
  - **`?includeUnvalidated=true`** on `GET /areas`, `/areas/roots`, `/areas/{id}/children` and `GET /first-ascensionists` — skips the filter for the management screens (`/manage/areas`, `/manage/first-ascensionists`) that exist to *fix* records, including rejected ones; `403`s unless the caller holds the matching `.validate` permission (`area.validate`/`first-ascensionist.validate` — not `.edit`, since `first-ascensionist.edit` is also granted dynamically to any user linked to their own opener record, which would let them enumerate every unvalidated one).
  - **`?openedByMe=true`** on `GET /routes` — "Mis aperturas" (`/my-acordanza/my-openings`): filters to routes the caller is credited as a first ascensionist on and bypasses the visibility filter entirely, since these are the caller's own credits regardless of who created the route or its status.
  - **`GET /routes/pending`** and **`GET /areas/pending`** — the review queue's own view of not-yet-decided records (`RoutePendingDto`/`AreaPendingDto`), replacing what used to be `PendingTasksContext` downloading the entire routes/areas tables and filtering client-side. `GET /routes/pending` has no policy attribute — narrowed per-caller by `AreaExpertAuthorizer.BuildAreaCheckAsync(User, Permissions.RouteValidate)` the same way `ValidateRoute`/`RejectRoute` already are, so a caller with neither the role permission nor an approved area expertise gets `[]`. `GET /areas/pending` is plain `[Authorize(Policy = Permissions.AreaValidate)]` (area validation has no area-expert path — see `ValidateArea`/`RejectArea`).
  - Routes now auto-validate on create when the creator can validate them (`RoutesController.CreateRoute`, mirroring `AreasController.CreateArea`/`FirstAscensionistsController.CreateFirstAscensionist`) — via `AreaExpertAuthorizer.CanActOnAreaAsync(User, Permissions.RouteValidate, route.AreaId)` rather than a bare claim check, since route validation is area-scoped. Without this a moderator's own new route would vanish from "Busca" the instant they saved it.
  - The tree is **not** walked for visibility — a route's or area's own status decides it, never a parent's; `AreaHierarchyService`'s snapshot stays complete regardless (it's an internal resolution structure for breadcrumbs/slug paths, not a display list).
- `Models/` — `ApplicationUser` (extends `IdentityUser`; email *is* the username, but `Name` (max 20 chars) is the only user-facing display value — email is PII and must never be shown to other users; `PasswordHash == null` marks an invited-but-not-yet-accepted account; `ConfirmedAt` is set once, the moment the account gets a usable password — by `AuthController.AcceptInvite` (inside its transaction) for invited accounts and by `Program.cs`'s `create-user` branch for CLI-provisioned ones — and stays null forever for pre-existing accounts with no recoverable confirmation date, rather than being backfilled with a guess), `ClimbingRoute`, `Area` and `FirstAscensionist` all implement `IValidatable` (`ValidationStatus` — a `ReviewStatus` reused from the request-review flows below, string-converted like theirs — plus `DecidedAt`/`DecidedByUserId`/`RejectionReason`), sharing one three-state validation lifecycle via the static `Validation` helper (`Models/Validation.cs`): `Validation.MarkValidated` sets `Approved` and clears any prior `RejectionReason`, `Validation.MarkRejected` sets `Rejected` plus the reason, `Validation.InvalidateIfChanged` resets to `Pending` and clears the decision — but only when the controller determines the edit actually changed something, so a no-op re-save doesn't spuriously send a validated record back to the queue. The same three entities also share `Models/ValidationVisibility.cs` — three `Expression<Func<T, bool>>` predicates (one per entity, not a shared generic — EF Core's translation of member access through a generic interface constraint isn't reliable) encoding the one publication-gate rule browse endpoints filter on; see "Validation visibility" above (`ClimbingRoute`'s `Orientation`/`Gear` are free-form-ish string fields, not a fixed route "type" — see `frontend/src/api/types.ts`'s `orientationLabels`/`gearLabels`). `ClimbingRoute`, `Area` and `FirstAscensionist` also each carry `AddedByUserId`/`AddedBy`/`CreatedAt` (creator attribution feeding `ContributionsController`) — non-nullable only on `ClimbingRoute`, whose column predates this and always has real data; on `Area`/`FirstAscensionist` it's nullable, since pre-existing rows have no recoverable creator and simply never show up in anyone's contributions list. `ClimbingRoute` (`Slug` is a path-safe form of `Name`, unique per `AreaId` — scoped to the route's own area rather than globally like `FirstAscensionist.Slug` or per-parent like `Area.Slug`, since `Name` has no uniqueness constraint at all and a global namespace would hit the "-2"/"-3" collision suffix constantly on common route names; regenerated whenever `Name` or `AreaId` changes (`RoutesController.GenerateUniqueRouteSlugAsync`), same rationale as `FirstAscensionist.Slug` — nothing is keyed on this column the way `Area.Slug` doubles as the topo blob-storage prefix, so a corrected name or a moved route shouldn't leave a stale URL behind; backs the shareable `/routes/{area-slug-path}/{route-slug}` URL, the area segment resolved live from `AreaId` via `AreaHierarchy.SlugPath` and never itself stored — plan 21), `Area` (a tree via nullable `ParentAreaId`; `Slug` is a path-safe form of `Name` used as the topo blob-storage prefix; `Polygon` (a JSON-owned list of `GeoPoint`) plus its recomputed `CentroidLat`/`CentroidLng` back the map view), `FirstAscensionist` (a route's opener/establisher; `Slug` is a path-safe form of `Name` backing `/fa/{slug}` (issue #137) — unlike `Area.Slug`, which freezes at creation because it also doubles as the topo blob-storage prefix, this one is regenerated whenever `Name` changes (`FirstAscensionistsController.GenerateUniqueSlugAsync`), since nothing else is keyed on it and a corrected name shouldn't leave a stale URL behind; names aren't unique here (unlike `Area`'s per-parent uniqueness), so the "-2"/"-3" suffix loop is the primary disambiguator, not just a diacritics fallback; optional `UserId` link to an `ApplicationUser`, set only via an approved `FirstAscensionistLinkRequest`; a pending/rejected record is hidden from `/fa` and pickers for everyone but its author — see "Validation visibility" above — but stays embedded, unfiltered, in every route payload that credits it), `FirstAscensionistLinkRequest` / `AreaExpert` (near-identical self-service request/approve/reject shapes, both implementing `IReviewableRequest` — shared `ReviewStatus` (`Pending`/`Approved`/`Rejected`), with `DecidedAt`/`DecidedByUserId`/`RejectionReason` tracking who resolved it and why; see `Services/ReviewRequestService.cs` below for the shared approve/reject/cancel primitive built on the interface), `Topo` (an uploaded route photo: `BlobName`/`ContentType`/`FileName` plus who uploaded it, cascades with its `ClimbingRoute`), `AreaMedia` (the same shape hung off an `Area` instead — a sector photo; shares `Topo`'s blob container and `MediaUploadService` upload path, differing only in blob-name prefix, and is surfaced through the same `TopoDto`/SAS-URL machinery), `Tick` (a logged ascent, belongs to one `ClimbingRoute` and one `ApplicationUser`), `PasskeyCredential` (a registered WebAuthn credential, cascades on user delete).
- `Dtos/` — request/response records per resource. Controllers project EF entities into these directly in LINQ `Select` calls rather than mapping in a separate layer.
- `Data/AppDbContext.cs` — `IdentityDbContext<ApplicationUser>` plus one `DbSet` per app model. Indexes on `Grade`/`AreaId`/`Tick.RouteId`/`Topo.RouteId`; `ApplicationUser.NormalizedEmail` is unique; `Area` has case-exact-unique `(ParentAreaId, Name)` and `(ParentAreaId, Slug)` (nulls treated as equal, so two root areas still collide); `AreaExpert`/`FirstAscensionistLinkRequest` each have a unique filtered index on their `(xId, UserId)` pair scoped to `Status = 'Pending'`. `ClimbingRoute`/`Area`/`FirstAscensionist`'s `AddedBy`/`DecidedBy`, `Tick.Climber`, and `Topo.UploadedBy` use `DeleteBehavior.Restrict` (deleting a user doesn't cascade); `Tick.Route`, `Topo.Route`, `PasskeyCredential.User`, and both `AreaExpert`'s/`FirstAscensionistLinkRequest`'s FKs to their subject + requesting user cascade. Tables are split across three Postgres schemas via `OnModelCreating`: `identity` (the built-in `AspNetUsers`/`AspNetRoles`/... tables), `auth` (`PasskeyCredentials`), and `core` (everything else app-specific).
- `Services/` — `JwtTokenService` (issues the bearer token, embedding role-derived and dynamic permission claims — see Authorization below); `BlobStorageService` (blob storage primitives: upload/delete/SAS-URL — see Storage below); `MediaUploadService` (the shared image-upload flow on top of `BlobStorageService` — content-type/size validation, the numbered-blob-name race loop, and DB-save-vs-blob-orphan cleanup; used by both `RoutesController.UploadTopo` and `AreasController.UploadAreaMedia`, which stay responsible for their own `usedBlobNames` query and blob-name prefix so the service itself stays DB-agnostic); `AreaHierarchyService` (a scoped, once-per-request in-memory snapshot of the area tree; all tree walks — descendant expansion for filters, top-level ancestor, name breadcrumbs and slug paths for DTOs/blob prefixes, slug-path resolution — live on the `AreaHierarchy` snapshot it returns, shared by the routes/areas/ticks controllers and `AreaExpertAuthorizer`); `IEmailSender`/`ConsoleEmailSender`/`ResendEmailSender`/`EmailTemplates` (see Email below); `InviteTokenProvider` (the invite-only, 7-day-lifespan Identity token provider plus the `InviteTokens` name/purpose/lifespan constants — see Auth model below); `Slugify` (name → path-safe slug, used for both `Area.Slug` and topo blob names); `LinkRules` (route link trim/cap-10/max-length/http(s)-allowlist/dedupe — hoisted out of `RoutesController` (plan 18) so both human-entered links (`CreateRoute`/`UpdateRoute`) and worker-found ones (`RouteEnrichmentService`) share the same stored-XSS guard); `RouteEnrichmentQueue`/`EnrichmentQueueProcessor`/`RouteEnrichmentService`/`IRouteEnrichmentProvider`+`ITopoVerificationProvider` (route enrichment — see Route enrichment below); `ReviewRequestService` (the atomic approve/reject/cancel primitive shared by `AreaExpertsController` and `FirstAscensionistLinksController` — a single conditional `ExecuteUpdateAsync`/`ExecuteDeleteAsync` scoped to `Status == Pending`, generic over `IReviewableRequest`, disambiguating 0-rows-affected into `AlreadyResolved` vs `NotFound`; `FirstAscensionistLinksController.Approve` keeps its extra transaction + linking UPDATE + auto-reject-on-conflict fallback inline — genuinely different shape, not pushed into the shared primitive); `Notifications.BestEffortAsync` (the try/catch-and-log wrapper both controllers' decision-notification emails go through, so a delivery failure can't fail the decision itself).
- `Authorization/` — the RBAC plumbing: `Permissions.cs` (flat `{entity}.{action}` constants — `area`/`route`/`tick`/`first-ascensionist` × `create`/`edit`/`validate`/`delete`, plus `route.enrich` (admin-only by construction — in `Permissions.All` but not `RolePermissions`' user/moderator sets nor `DynamicPermissions`, see Route enrichment below), `user.manage` and `user.invite` (the latter held by *every* role — see `UsersController` above), `area-expert.request`/`.approve`, and `first-ascensionist-link.request`/`.approve`), `Roles.cs` (`admin`/`moderator`/`user`), `RolePermissions.cs` (the static, additive role→permission map — `user` ⊂ `moderator` ⊂ `admin`), `RoleSeeder.cs` (idempotently creates the 3 roles, backfills the `user` role onto any account with none, and retires the legacy `first-ascensionist` role onto any account still holding it — run on every startup), `DynamicPermissions.cs` (adds `route.edit`/`route.validate`/`first-ascensionist.edit` claims for any user linked to a `FirstAscensionist` record, on top of their role's permissions — used by both `JwtTokenService` and `AuthController.Me` so the JWT claims and the `/auth/me` response never drift apart), `AreaExpertAuthorizer.cs` (the shared "permission claim OR approved `AreaExpert` of the top-level area" check — see the next paragraph). Built on stock ASP.NET Core `Authorization` (one named policy per permission, registered in `Program.cs`, requiring a `permission` claim) — no external authorization package.
- `Migrations/` — EF Core migrations; regenerate with `dotnet ef migrations add` after any model or `OnModelCreating` change, don't hand-edit. Documented exceptions: `AddUniqueEmailAndPasskeys`, which hand-inserts a `migrationBuilder.Sql(...)` data backfill ahead of the generated unique-index creation; `ValidationRejectionAndContributors`, which hand-corrected a scaffolded `RenameColumn` that the diff engine pointed at the wrong new column (matched `ValidatedByUserId` to the new `RejectionReason` column instead of `DecidedByUserId`, since both were nullable `text`, which would have silently moved every existing decider's user id into a rejection-reason column) and hand-inserted a `migrationBuilder.Sql(...)` backfill for the new `ValidationStatus` column (its `AddColumn` default of `""` isn't a valid `ReviewStatus` name) — see that migration's comments for both; `BackfillValidationStatusApproved`, an empty (no schema change) migration whose `Up` is entirely a hand-written `migrationBuilder.Sql(...)` — issue #72 turned validation into a publication gate, and the prior migration's backfill only approved rows with a recorded decision, so this one-time sweep approves every pre-existing route/area/first-ascensionist row (leaving `DecidedAt`/`DecidedByUserId` null, since nobody actually reviewed them) so the gate ships without hiding the whole catalogue.

Approved `AreaExpert`s are a *separate*, narrower grant from the `DynamicPermissions` claim mechanism above: rather than a global claim, `Authorization/AreaExpertAuthorizer.cs` checks (per request, when the permission claim is absent) whether the caller is an approved expert of the subject's top-level area (covering all its subareas) — used with `route.validate` for route validation and `area.edit` for area media upload/delete; same "ownership scoped to a query, not a claim" pattern `DELETE /ticks/{id}` uses (see Auth model below). `AuthController.Me`/`MeResponse` still surfaces an `isAreaExpert` flag (any approved area, not per-area) purely so the frontend can decide whether to show the "pending tasks" bell — it grants nothing by itself.

Note: the retired `first-ascensionist` *role* and the `first-ascensionist.*` *permissions* (on the `FirstAscensionist` entity — a route's opener/establisher record) were unrelated namesakes; the permissions live on, now granted dynamically (see `DynamicPermissions` above) rather than through a role. `Permissions.FirstAscensionistValidate` in particular used to be declared in `Permissions.cs`/`RolePermissions.cs` (role-based — `moderator`/`admin`, not one of the dynamic grants above) but referenced by no endpoint; `FirstAscensionistsController`'s `POST /{id}/validate`, `POST /{id}/reject` and `GET /pending` are its first actual use.

Traces/metrics/logs export via OpenTelemetry (`builder.Services.AddOpenTelemetry()` in `Program.cs`) to whatever `OTEL_EXPORTER_OTLP_ENDPOINT`/`OTEL_EXPORTER_OTLP_HEADERS` point at (Grafana Cloud in production); unset locally, so the exporters just have nowhere to send and dev is unaffected.

### Auth model

Identity is used in "core" mode (`AddIdentityCore`, no cookie/UI scaffolding) purely for password hashing and user storage. Email is the username (`RequireUniqueEmail = true`; `UserName` and `Email` are always set to the same value). There is still no public HTTP registration endpoint — accounts are provisioned either via the `create-user` CLI branch at the top of `Program.cs` (`dotnet run -- create-user <email> <password> <name> [role]`, which runs before the normal web host pipeline is built), or in-app by any user holding `user.invite` via `UsersController.InviteUser`, which creates the account immediately (with no usable password) and emails a single-use link to `/accept-invite`. Password policy is relaxed (`RequiredLength = 8`, no complexity requirements) since accounts are hand-provisioned for a small trusted group.

Password reset (`AuthController.ForgotPassword`/`ResetPassword`) and invite acceptance (`AcceptInvite`) both ride ASP.NET Identity data-protection tokens, base64url-encoded for the URL, but through **two different providers with different lifespans**: reset uses the default one (1 hour, `DataProtectionTokenProviderOptions.TokenLifespan`, tightened from Identity's 1-day default); invites use the dedicated `InviteTokenProvider` (`Services/InviteTokenProvider.cs`, registered under `InviteTokens.ProviderName` in `Program.cs`), whose lifespan is **7 days** because an invite is asynchronous — the recipient isn't sitting at the keyboard. That 7-day window is load-bearing beyond the link itself: `UsersController.InviteUser` uses `InviteTokens.Lifespan` to decide whether someone else's still-pending invite to the same email may be taken over. The provider needs its own concrete type *and* options type — Identity resolves a named provider by concrete DI type, so registering `DataProtectorTokenProvider<ApplicationUser>` under a second name would silently hand back the same 1-hour singleton the default provider already uses (see that file's header comment). `ValidateToken` accepts either provider's token, read-only (`VerifyUserTokenAsync`, unlike `ResetPasswordAsync`, doesn't consume it), so both `ResetPasswordScreen` and `AcceptInviteScreen` can show a dead-link error before rendering the form. Tokens are single-use (`ResetPasswordAsync` rotates the user's `SecurityStamp` on success). `ForgotPassword` always returns `{ ok: true }` regardless of whether the account exists, so it can't be used to enumerate registered emails, and is rate-limited per-IP (`forgot-password` policy, 3/15min) to bound both abuse and Resend's free-tier quota.

Passkey (WebAuthn/FIDO2) second-factor login is **opt-in per user**, implemented manually (not via ASP.NET Identity's built-in 2FA, which assumes `SignInManager`/cookies this app doesn't use) with `Fido2.AspNet`: a user with no registered passkey logs in with just a password; a user with one or more registered via `PasskeysController` gets a `mfaRequired` response from `POST /api/auth/login` carrying WebAuthn assertion options and a `sessionId`, and must complete `POST /api/auth/login/passkey` with the browser's assertion before a JWT is issued. WebAuthn challenges are cached in-process (`IMemoryCache`, 5 min TTL) between the options/complete steps — fine for a single-instance deployment, but would need a distributed cache if ever scaled to multiple replicas.

Everyone with an account can read all routes, but ticks are private per user: `GET /routes`/`GET /routes/{id}` never expose who else ticked a route or their notes/ratings, only a `HasTick` flag scoped to the caller; a user's own tick history is only reachable via `GET /ticks/mine`. Write access is otherwise role-based (see `Authorization/` above) and not generally ownership-based, but `DELETE /ticks/{id}` is one exception: `tick.delete` is broadly granted (every role has it, see `RolePermissions`), so on its own it wouldn't stop one user from deleting another's private tick by guessing its id — the endpoint additionally scopes its query to `ClimberUserId == <caller>`, same pattern as `PasskeysController`'s self-service delete (silently no-ops rather than deleting) and `AreaExpertsController.Cancel`.

### Email

`IEmailSender.SendAsync(to, subject, html)` is the only abstraction; `Program.cs` wires up `ResendEmailSender` (via the [Resend](https://resend.com) HTTP API) when `Resend:ApiKey` is configured, or `ConsoleEmailSender` (just logs the email) otherwise — so the invite/reset/notification flows can be exercised locally with zero email-provider setup. `Services/EmailTemplates.cs` holds one `(Subject, Html)`-returning method per email: `ResetPassword`, `InviteUser`, `NewUserRegistered` (sent to admins when an invite is accepted), `AreaExpertApproved`/`Rejected`, `FirstAscensionistLinkApproved`/`Rejected`. The approve/reject notifications in `AreaExpertsController`/`FirstAscensionistLinksController` are best-effort (`Services/Notifications.BestEffortAsync`) — a delivery failure must not fail the decision itself.

### Storage (topo images)

`BlobStorageService` stores route topo photos and area media images in a single Azure Blob Storage container (`Storage:ContainerName`, default `topos`); uploads route through `MediaUploadService` (`RoutesController.UploadTopo`/`AreasController.UploadAreaMedia`), while reads (`GetReadSasUrlAsync`) and deletes (`ToposController.DeleteTopo`, `AreaMediaController.DeleteAreaMedia`, plus the cascade cleanup in `RoutesController.DeleteRoute`/`AreasController.DeleteArea`) call `BlobStorageService` directly. Locally it authenticates via `Storage:ConnectionString` against an Azurite emulator (started by `docker-compose.yml`); in production (no connection string configured) it instead uses the container app's user-assigned managed identity against the real account (`Storage:AccountName`/`Storage:ManagedIdentityClientId`) — same dual-credential pattern `Program.cs` uses for Data Protection key persistence (also blob-backed, so keys survive Container Apps' scale-to-zero restarts). Blob names are `{area-slug-path}/{route-slug}-{NN}.{ext}` for topos and `{area-slug-path}/_media-{NN}.{ext}` for area media (see `MediaUploadService.UploadNumberedAsync`); the frontend never gets a direct blob URL — `TopoDto` carries a backend-issued, time-limited SAS URL instead (`MediaUploadService.ImageUrlLifetime`, 15 min).

### Route enrichment (plan 18)

`POST /routes/{id}/enrich[?force=true]` (`Permissions.RouteEnrich`, admin-only — see Authorization above) enqueues a `route-enrichment` Azure Storage Queue message (`Services/RouteEnrichmentQueue.cs`) and returns `202`; `CreateRoute` never enqueues — every enrichment is a deliberate, per-route act (a button in the frontend's `DetailModal`, or the `enqueue-enrichment` CLI command), not something that happens automatically on write. `404` if the route doesn't exist, `409` if `ClimbingRoute.EnrichedAt` is already set and `force` isn't `true`, `503` if the enqueue itself fails (nothing else happened in the request, so this isn't best-effort).

The worker side is a third `Program.cs` CLI branch, `process-enrichment` (shaped like `create-user` — runs before the web host pipeline, in production as an event-driven Container Apps Job that scales from zero on queue depth via KEDA and exits once drained): `Services/EnrichmentQueueProcessor.cs` drains the queue (batches of 8, 5-minute visibility timeout, deletes on success, leaves a failed message for redelivery, drops it as poison past 5 dequeue attempts), calling `Services/RouteEnrichmentService.cs` per message. That service calls `IRouteEnrichmentProvider.FindAsync` (real impl: `ClaudeRouteEnrichmentProvider` — one Messages API call on `claude-sonnet-5` with the server-side web search tool and structured outputs, reached through Azure AI Foundry so the worker authenticates via the container app's managed identity instead of a stored API key), filters the found links one at a time through `Services/LinkRules.cs` (the same allowlist/cap/dedupe `RoutesController.CreateRoute`/`UpdateRoute` use, hoisted out of the controller so both paths share it — resolved per-link here, not as one all-or-nothing batch, since a single junk URL from the model must not reject everything else it found) and appends them, then verifies any topo candidate with a second, cheap vision call (`ITopoVerificationProvider`/`ClaudeTopoVerificationProvider`, `claude-haiku-4-5`) before importing it through `MediaUploadService` exactly like a human `UploadTopo`. Writes go through `AppDbContext` directly, never `UpdateRoute`, so `Validation.InvalidateIfChanged` is structurally unreachable from this path — auto-appended links/topos can't bounce an approved route back to `Pending`. Without `Anthropic:FoundryResource` configured, `Program.cs` registers `NoOpRouteEnrichmentProvider`/`NoOpTopoVerificationProvider` instead — the queue/worker/endpoint stay fully exercisable locally (it just logs a skip and sets `EnrichedAt`), same philosophy as `ConsoleEmailSender`.

### OpenAPI document

`Program.cs` calls `AddOpenApi()`/`MapOpenApi()` (the latter dev-gated — this is a private API, not a published one) so the frontend can generate its API types from a real contract instead of the hand-mirrored DTOs it used before (see `frontend/CLAUDE.md`'s `api/generated.ts`). The document is checked in at `backend/Acordanza.Api/openapi/Acordanza.Api.json`, not regenerated on every `dotnet build`: `Acordanza.Api.csproj` sets `OpenApiGenerateDocumentsOnBuild=false` because generating it actually boots the app through the same top-level `Program.cs` that runs EF migrations against Postgres and provisions the blob container on startup — wiring that into routine builds would make every `dotnet build` depend on `docker compose up -d`. Regenerate on demand instead, same prerequisites as `dotnet run` (Postgres/Azurite up, `Jwt:Key` configured):

```
ASPNETCORE_ENVIRONMENT=Development dotnet build -p:OpenApiGenerateDocumentsOnBuild=true
```

`AddOpenApi` also registers a schema transformer that strips the `| string` alternative .NET's Web JSON defaults (`JsonNumberHandling.AllowReadingFromString`) would otherwise add to every numeric property's schema — without it, every id/count/rating in the generated frontend types would be `number | string` instead of `number`. CI's `openapi-contract-check` job (`.github/workflows/ci-cd.yml`) regenerates both this document and the frontend's `generated.ts` and fails on any diff, so a DTO change with a stale generated type can't merge.

### Configuration

`Jwt:Key` is read from user-secrets/environment, never checked into `appsettings.json`. `Cors:AllowedOrigins` (array) must include the frontend's origin — defaults to `http://localhost:5173` in `appsettings.json`; the same array is reused as the Fido2 `Origins` allowlist. `Fido2:ServerDomain` (the bare domain, no scheme/port — e.g. `localhost` in dev) and `Fido2:ServerName` configure the WebAuthn relying party. `Frontend:BaseUrl` is used to build reset-password/invite/accept-invite links sent by email. `Storage:ContainerName`/`Storage:DataProtectionContainerName` plus either `Storage:ConnectionString` (local) or `Storage:AccountName`+`Storage:ManagedIdentityClientId` (production) configure blob storage — see Storage above. `Resend:ApiKey`/`Resend:FromEmail`/`Resend:FromName` configure email — see Email above. `Invites:MaxForUser` (default 5) and `Invites:MaxForModerator` (default 10) cap how many accounts a non-admin may ever invite; admins are unbounded and the values are read per-request via `GetInviteLimit()`, so the quota is tunable by configuration rather than by redeploying — see `UsersController` above. `Storage:EnrichmentQueueName` (default `route-enrichment`) and `Anthropic:FoundryResource` (not a secret — just the Foundry resource name, used to build `https://{resource}.services.ai.azure.com/anthropic/`; auth is Entra ID via the managed identity, never a stored API key) configure route enrichment — see Route enrichment above.
