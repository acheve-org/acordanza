# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Applies to `backend/Acordanza.Api/` — the ASP.NET Core (.NET 10) Web API. See the root `CLAUDE.md` for how this fits with the frontend.

## Commands

All run from `backend/Acordanza.Api/`:

```
dotnet build                                                      # compile
dotnet run                                                        # run the API on http://localhost:5073
dotnet run -- create-user <email> <password> <name> [role]        # provision an account (only way to create one — no HTTP registration); name max 20 chars; role defaults to 'user' (other roles: 'moderator', 'admin')
dotnet ef migrations add <Name>                                   # add a migration after changing a model/AppDbContext
dotnet ef database update                                         # apply pending migrations
```

First-time setup (once per machine): `dotnet user-secrets set "Jwt:Key" "$(openssl rand -base64 48)"`. The connection string in `appsettings.json` assumes the `docker-compose.yml` Postgres defaults (`localhost:5432`, db/user/password `acordanza`); `appsettings.Development.json` likewise assumes its Azurite container (topo images, Data Protection keys — see Storage below) is up, so `docker compose up -d` (from the repo root) must be running before `dotnet run`.

Migrations run automatically on startup (`db.Database.MigrateAsync()` in `Program.cs`) as well as before the `create-user` CLI path — you don't need to run `dotnet ef database update` before every `dotnet run`, only when you want the schema applied without booting the full app.

No test project exists yet.

## Architecture

Flat, controller-per-resource structure — there is no service/repository layer; controllers talk to `AppDbContext` directly via EF Core:

- `Controllers/` — `AuthController` (login incl. passkey second factor, `/auth/me`, forgot/reset-password, `/accept-invite`), `AccountController` (self-service password change and profile name update), `PasskeysController` (register/list/delete the current user's passkeys), `RoutesController` (CRUD on routes + nested `POST /{id}/ticks`, `POST /{id}/validate`, `POST /{id}/topos`; `GET /` filters on `q`/`areaId`/`grade`/`orientation`/`gear`/`tag`/`hasTopo`/`firstAscensionistId`, and `GET /grades` lists the distinct grades in use for the frontend's filter dropdown), `ToposController` (`DELETE /{id}` only — upload lives on `RoutesController`), `AreasController` (tree CRUD incl. `/roots`+`/{id}/children` for lazy-loaded management UI, `PUT /{id}/coordinates` for the map polygon, `POST /{id}/validate`), `AreaExpertsController` (self-service request/approve/reject flow for area-scoped route-validation rights — see below), `FirstAscensionistsController` (list/create/update/delete, plus `GET /profiles` and `GET /{id}` — the same records enriched with each one's route count and areas, for the frontend's "Sigue" section), `FirstAscensionistLinksController` (self-service claim/approve/reject flow — see below), `TicksController` (`GET /mine` — the current user's own paginated, filterable tick history; deletion), `UsersController` (admin: paginated/filterable user list, `POST /invite`). All routes require `[Authorize]` (JWT bearer); write actions additionally require `[Authorize(Policy = Permissions.X)]` — see Authorization below.
- `Models/` — `ApplicationUser` (extends `IdentityUser`; email *is* the username, but `Name` (max 20 chars) is the only user-facing display value — email is PII and must never be shown to other users; `PasswordHash == null` marks an invited-but-not-yet-accepted account), `ClimbingRoute` (has a nullable `ValidatedAt`/`ValidatedByUserId`, cleared on edit; `Orientation`/`Gear` are free-form-ish string fields, not a fixed route "type" — see `frontend/src/api/types.ts`'s `orientationLabels`/`gearLabels`), `Area` (a tree via nullable `ParentAreaId`; `Slug` is a path-safe form of `Name` used as the topo blob-storage prefix; `Polygon` (a JSON-owned list of `GeoPoint`) plus its recomputed `CentroidLat`/`CentroidLng` back the map view), `FirstAscensionist` (a route's opener/establisher; optional `UserId` link to an `ApplicationUser`, set only via an approved `FirstAscensionistLinkRequest`), `FirstAscensionistLinkRequest` / `AreaExpert` (near-identical self-service request/approve/reject shapes — `Status` is `Pending`/`Approved`/`Rejected`, with `DecidedAt`/`DecidedByUserId`/`RejectionReason` tracking who resolved it and why), `Topo` (an uploaded route photo: `BlobName`/`ContentType`/`FileName` plus who uploaded it, cascades with its `ClimbingRoute`), `Tick` (a logged ascent, belongs to one `ClimbingRoute` and one `ApplicationUser`), `PasskeyCredential` (a registered WebAuthn credential, cascades on user delete).
- `Dtos/` — request/response records per resource. Controllers project EF entities into these directly in LINQ `Select` calls rather than mapping in a separate layer.
- `Data/AppDbContext.cs` — `IdentityDbContext<ApplicationUser>` plus one `DbSet` per app model. Indexes on `Grade`/`AreaId`/`Tick.RouteId`/`Topo.RouteId`; `ApplicationUser.NormalizedEmail` is unique; `Area` has case-exact-unique `(ParentAreaId, Name)` and `(ParentAreaId, Slug)` (nulls treated as equal, so two root areas still collide); `AreaExpert`/`FirstAscensionistLinkRequest` each have a unique filtered index on their `(xId, UserId)` pair scoped to `Status = 'Pending'`. `ClimbingRoute.AddedBy`/`ValidatedBy`, `Tick.Climber`, `Topo.UploadedBy`, and every `DecidedBy` use `DeleteBehavior.Restrict` (deleting a user doesn't cascade); `Tick.Route`, `Topo.Route`, `PasskeyCredential.User`, and both `AreaExpert`'s/`FirstAscensionistLinkRequest`'s FKs to their subject + requesting user cascade. Tables are split across three Postgres schemas via `OnModelCreating`: `identity` (the built-in `AspNetUsers`/`AspNetRoles`/... tables), `auth` (`PasskeyCredentials`), and `core` (everything else app-specific).
- `Services/` — `JwtTokenService` (issues the bearer token, embedding role-derived and dynamic permission claims — see Authorization below); `BlobStorageService` (topo image storage — see Storage below); `AreaHierarchyService` (a scoped, once-per-request in-memory snapshot of the area tree; all tree walks — descendant expansion for filters, top-level ancestor, name breadcrumbs and slug paths for DTOs/blob prefixes, slug-path resolution — live on the `AreaHierarchy` snapshot it returns, shared by the routes/areas/ticks controllers and `AreaExpertAuthorizer`); `IEmailSender`/`ConsoleEmailSender`/`ResendEmailSender`/`EmailTemplates` (see Email below); `Slugify` (name → path-safe slug, used for both `Area.Slug` and topo blob names).
- `Authorization/` — the RBAC plumbing: `Permissions.cs` (flat `{entity}.{action}` constants — `area`/`route`/`tick`/`first-ascensionist` × `create`/`edit`/`validate`/`delete`, plus `user.manage`, `area-expert.request`/`.approve`, and `first-ascensionist-link.request`/`.approve`), `Roles.cs` (`admin`/`moderator`/`user`), `RolePermissions.cs` (the static, additive role→permission map — `user` ⊂ `moderator` ⊂ `admin`), `RoleSeeder.cs` (idempotently creates the 3 roles, backfills the `user` role onto any account with none, and retires the legacy `first-ascensionist` role onto any account still holding it — run on every startup), `DynamicPermissions.cs` (adds `route.edit`/`route.validate`/`first-ascensionist.edit` claims for any user linked to a `FirstAscensionist` record, on top of their role's permissions — used by both `JwtTokenService` and `AuthController.Me` so the JWT claims and the `/auth/me` response never drift apart), `AreaExpertAuthorizer.cs` (the shared "permission claim OR approved `AreaExpert` of the top-level area" check — see the next paragraph). Built on stock ASP.NET Core `Authorization` (one named policy per permission, registered in `Program.cs`, requiring a `permission` claim) — no external authorization package.
- `Migrations/` — EF Core migrations; regenerate with `dotnet ef migrations add` after any model or `OnModelCreating` change, don't hand-edit (the one documented exception is `AddUniqueEmailAndPasskeys`, which hand-inserts a `migrationBuilder.Sql(...)` data backfill ahead of the generated unique-index creation — see that migration's comments).

Approved `AreaExpert`s are a *separate*, narrower grant from the `DynamicPermissions` claim mechanism above: rather than a global claim, `Authorization/AreaExpertAuthorizer.cs` checks (per request, when the permission claim is absent) whether the caller is an approved expert of the subject's top-level area (covering all its subareas) — used with `route.validate` for route validation and `area.edit` for area media upload/delete; same "ownership scoped to a query, not a claim" pattern `DELETE /ticks/{id}` uses (see Auth model below). `AuthController.Me`/`MeResponse` still surfaces an `isAreaExpert` flag (any approved area, not per-area) purely so the frontend can decide whether to show the "pending tasks" bell — it grants nothing by itself.

Note: the retired `first-ascensionist` *role* and the `first-ascensionist.*` *permissions* (on the `FirstAscensionist` entity — a route's opener/establisher record) were unrelated namesakes; the permissions live on, now granted dynamically (see `DynamicPermissions` above) rather than through a role.

Traces/metrics/logs export via OpenTelemetry (`builder.Services.AddOpenTelemetry()` in `Program.cs`) to whatever `OTEL_EXPORTER_OTLP_ENDPOINT`/`OTEL_EXPORTER_OTLP_HEADERS` point at (Grafana Cloud in production); unset locally, so the exporters just have nowhere to send and dev is unaffected.

### Auth model

Identity is used in "core" mode (`AddIdentityCore`, no cookie/UI scaffolding) purely for password hashing and user storage. Email is the username (`RequireUniqueEmail = true`; `UserName` and `Email` are always set to the same value). There is still no public HTTP registration endpoint — accounts are provisioned either via the `create-user` CLI branch at the top of `Program.cs` (`dotnet run -- create-user <email> <password> <name> [role]`, which runs before the normal web host pipeline is built), or in-app by an admin via `UsersController.InviteUser`, which creates the account immediately (with no usable password) and emails a single-use link to `/accept-invite`. Password policy is relaxed (`RequiredLength = 8`, no complexity requirements) since accounts are hand-provisioned for a small trusted group.

Password reset (`AuthController.ForgotPassword`/`ResetPassword`) and invite acceptance (`AcceptInvite`) both ride ASP.NET Identity's built-in password-reset token (`GeneratePasswordResetTokenAsync`/`ResetPasswordAsync`), base64url-encoded for the URL; `ValidateToken` lets the frontend check a link is still live before rendering the form (read-only — doesn't consume the token). Tokens are single-use (`ResetPasswordAsync` rotates the user's `SecurityStamp` on success) and expire after 1 hour (`DataProtectionTokenProviderOptions.TokenLifespan`, tightened from Identity's 1-day default). `ForgotPassword` always returns `{ ok: true }` regardless of whether the account exists, so it can't be used to enumerate registered emails, and is rate-limited per-IP (`forgot-password` policy, 3/15min) to bound both abuse and Resend's free-tier quota.

Passkey (WebAuthn/FIDO2) second-factor login is **opt-in per user**, implemented manually (not via ASP.NET Identity's built-in 2FA, which assumes `SignInManager`/cookies this app doesn't use) with `Fido2.AspNet`: a user with no registered passkey logs in with just a password; a user with one or more registered via `PasskeysController` gets a `mfaRequired` response from `POST /api/auth/login` carrying WebAuthn assertion options and a `sessionId`, and must complete `POST /api/auth/login/passkey` with the browser's assertion before a JWT is issued. WebAuthn challenges are cached in-process (`IMemoryCache`, 5 min TTL) between the options/complete steps — fine for a single-instance deployment, but would need a distributed cache if ever scaled to multiple replicas.

Everyone with an account can read all routes, but ticks are private per user: `GET /routes`/`GET /routes/{id}` never expose who else ticked a route or their notes/ratings, only a `HasTick` flag scoped to the caller; a user's own tick history is only reachable via `GET /ticks/mine`. Write access is otherwise role-based (see `Authorization/` above) and not generally ownership-based, but `DELETE /ticks/{id}` is one exception: `tick.delete` is broadly granted (every role has it, see `RolePermissions`), so on its own it wouldn't stop one user from deleting another's private tick by guessing its id — the endpoint additionally scopes its query to `ClimberUserId == <caller>`, same pattern as `PasskeysController`'s self-service delete (silently no-ops rather than deleting) and `AreaExpertsController.Cancel`.

### Email

`IEmailSender.SendAsync(to, subject, html)` is the only abstraction; `Program.cs` wires up `ResendEmailSender` (via the [Resend](https://resend.com) HTTP API) when `Resend:ApiKey` is configured, or `ConsoleEmailSender` (just logs the email) otherwise — so the invite/reset/notification flows can be exercised locally with zero email-provider setup. `Services/EmailTemplates.cs` holds one `(Subject, Html)`-returning method per email: `ResetPassword`, `InviteUser`, `NewUserRegistered` (sent to admins when an invite is accepted), `AreaExpertApproved`/`Rejected`, `FirstAscensionistLinkApproved`/`Rejected`. The approve/reject notifications in `AreaExpertsController`/`FirstAscensionistLinksController` are best-effort (try/catch + log) — a delivery failure must not fail the decision itself.

### Storage (topo images)

`BlobStorageService` stores route topo photos in an Azure Blob Storage container (`Storage:ContainerName`, default `topos`); `RoutesController.UploadTopo`/`ToposController.DeleteTopo` are the only callers. Locally it authenticates via `Storage:ConnectionString` against an Azurite emulator (started by `docker-compose.yml`); in production (no connection string configured) it instead uses the container app's user-assigned managed identity against the real account (`Storage:AccountName`/`Storage:ManagedIdentityClientId`) — same dual-credential pattern `Program.cs` uses for Data Protection key persistence (also blob-backed, so keys survive Container Apps' scale-to-zero restarts). Blob names are `{area-slug-path}/{route-slug}-{NN}.{ext}` (see `RoutesController`'s blob-naming helpers); the frontend never gets a direct blob URL — `TopoDto` carries a backend-issued, time-limited SAS URL instead (`TopoUrlLifetime`, 15 min).

### Configuration

`Jwt:Key` is read from user-secrets/environment, never checked into `appsettings.json`. `Cors:AllowedOrigins` (array) must include the frontend's origin — defaults to `http://localhost:5173` in `appsettings.json`; the same array is reused as the Fido2 `Origins` allowlist. `Fido2:ServerDomain` (the bare domain, no scheme/port — e.g. `localhost` in dev) and `Fido2:ServerName` configure the WebAuthn relying party. `Frontend:BaseUrl` is used to build reset-password/invite/accept-invite links sent by email. `Storage:ContainerName`/`Storage:DataProtectionContainerName` plus either `Storage:ConnectionString` (local) or `Storage:AccountName`+`Storage:ManagedIdentityClientId` (production) configure blob storage — see Storage above. `Resend:ApiKey`/`Resend:FromEmail`/`Resend:FromName` configure email — see Email above.
