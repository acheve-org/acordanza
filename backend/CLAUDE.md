# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Applies to `backend/` — three .NET 10 projects (plan 22): `Acordanza.Core` (a plain class library — `Models/`, `Data/AppDbContext.cs`, `Migrations/`, plus the handful of services both other projects use), `Acordanza.Api` (`Microsoft.NET.Sdk.Web` — the ASP.NET Core Web API), and `Acordanza.Worker` (`Microsoft.NET.Sdk.Worker` — the drain-and-exit process behind route enrichment and route import, see Route enrichment and Route import below). Api and Worker both reference Core and never each other — they meet at the Storage Queue and at Core's shared EF model, never in-process. See the root `CLAUDE.md` for how this fits with the frontend.

## Commands

API, from `backend/Acordanza.Api/`:

```
dotnet build                                                      # compile
dotnet run                                                        # run the API on http://localhost:5073
dotnet run -- create-user <email> <password> <name> [role]        # provision an account (only way to create one — no HTTP registration); name max 20 chars; role defaults to 'user' (other roles: 'moderator', 'admin')
dotnet run -- enqueue-enrichment <routeId> [--force]               # enqueue route enrichment (plan 18) without the HTTP layer — local smoke-test / operator escape hatch
dotnet ef migrations add <Name> --project ../Acordanza.Core --startup-project .   # add a migration after changing a model/AppDbContext — both live in Core, but the tooling (Microsoft.EntityFrameworkCore.Design) stays on the API, the startup project
dotnet ef database update --project ../Acordanza.Core --startup-project .        # apply pending migrations
```

Worker, from `backend/Acordanza.Worker/`:

```
dotnet build      # compile
dotnet run        # drain the route-enrichment and route-import queues once each, then exit — what the Container Apps Job runs in production; no args, no CLI branches (it's a dedicated binary now, not a shared one)
```

First-time setup (once per machine): `dotnet user-secrets set "Jwt:Key" "$(openssl rand -base64 48)"` in `backend/Acordanza.Api/` — the worker has no `Jwt:Key` and needs none (see Route enrichment below). The connection string in each project's `appsettings.json` assumes the `docker-compose.yml` Postgres defaults (`localhost:5432`, db/user/password `acordanza`); each `appsettings.Development.json` likewise assumes its Azurite container (topo images, Data Protection keys, and the route-enrichment/route-import queues — see Storage below) is up, so `docker compose up -d` (from the repo root) must be running before either `dotnet run`. To exercise the worker's `dotnet run`/the API's `enqueue-enrichment` for real (not the no-op fallback — see Route enrichment below), a contributor also needs `Anthropic:FoundryResource` configured and their own `az login` session to carry the **Cognitive Services User** role on the Foundry resource — Storage/queue is Azurite-emulated locally, but Foundry has no emulator, so this makes a real call against the real Azure resource.

Migrations run automatically on startup — `db.Database.MigrateAsync()` in both `Acordanza.Api/Program.cs` (also ahead of the `create-user` CLI path) and `Acordanza.Worker/Program.cs`, each process racing safely under EF's migration lock — so you don't need to run `dotnet ef database update` before every `dotnet run`, only when you want the schema applied without booting either app.

Three test projects (xUnit v3 + Shouldly), one per production project, split along the same reference boundary as Core/Api/Worker themselves (plan 27, worker-test-split — before this, `Acordanza.Api.Tests` alone referenced both `Acordanza.Api` and `Acordanza.Worker` and held everything, including tests of plain `Acordanza.Core` types that had nothing to do with either process):

- **`backend/Acordanza.Core.Tests/`** — pure unit tests of `Acordanza.Core` types only: `Models/GradeValidatorTests`, `Models/ValidationTests`, `Services/AreaHierarchyTests`, `Services/LinkRulesTests`, `Services/SlugifyTests`. No Docker, no `DbContext`/`HttpContext`, no `[Trait("Category", "Integration")]` — every test here is unit-tier.
- **`backend/Acordanza.Api.Tests/`** — the API's own suite, referencing only `Acordanza.Api`, in two tiers:
  - **Unit tests** — pure classes with no `DbContext`/`HttpContext` (`Authorization/RolePermissions`, `Authorization/Permissions`). No Docker or database needed. Run with `dotnet test Acordanza.slnx --filter "Category!=Integration"` (or the equivalent plain `dotnet test --filter ...` from `backend/Acordanza.Api.Tests/`) — milliseconds, since Testcontainers/`WebApplicationFactory` are never instantiated when nothing needs them.
  - **Integration tests** (`Infrastructure/`, plus everything tagged `[Trait("Category", "Integration")]`) — real HTTP requests through `WebApplicationFactory<Program>` against a real Postgres + Azurite pair started per test run via Testcontainers, reset to a clean slate between tests with Respawn (see `Infrastructure/ApiFixture.cs`). Needs Docker running locally. `Infrastructure/TestUsers.cs` seeds a user in a role (plus the two dynamic-grant variants: first-ascensionist-linked, area-expert) and logs them in for real through `POST /api/auth/login`, so the JWT claims under test are the ones production issues — never minted directly. `Infrastructure/SeedData.cs` holds composable area/route/first-ascensionist seeding helpers. `Controllers/RouteEnrichmentTests` only covers the HTTP trigger (`POST /routes/{id}/enrich`) — the write paths that used to live alongside it now belong to `Acordanza.Worker.Tests` below, since they exercise worker code the API host doesn't even run.
- **`backend/Acordanza.Worker.Tests/`** — the worker's own suite, referencing only `Acordanza.Worker`, mirroring `Acordanza.Api.Tests`' shape but with its own fixture (`Infrastructure/WorkerFixture.cs`, `[Trait("Category", "Integration")]` via `Infrastructure/WorkerTestBase.cs`): no `WebApplicationFactory`/`Program` host to boot (the worker has none worth booting in a test — it's drain-and-exit), so the fixture builds `Acordanza.Worker.Services.ServiceCollectionExtensions.AddEnrichmentWorker`'s DI graph directly on a plain `ServiceCollection` against its own Postgres + Azurite Testcontainers pair, migrates the schema, and provisions the blob container/queue itself (the API's `Program.cs` normally does that, but this fixture never boots it). `Services/WorkerConfigurationTests` (unit-tier, no Docker) resolves that same DI graph from a `HostApplicationBuilder` carrying only the worker's Terraform env, so a config key the job isn't given fails a fast test instead of a live job execution. `Services/RouteEnrichmentServiceTests`/`Services/EnrichmentQueueProcessorTests` and `Services/RouteImportServiceTests`/`Services/UrlImportServiceTests`/`Services/RouteImportQueueProcessorTests` (integration-tier) construct `RouteEnrichmentService`/`EnrichmentQueueProcessor`/`RouteImportService`/`RouteImportQueueProcessor` directly with fake providers — no real Claude call is ever made in CI; `Services/EnrichmentGroundingTests`, `Services/RouteImportAcceptanceTests`/`Services/WebPageAcceptanceTests` and `Services/PrivateAddressesTests`/`Services/PageFetcherTests`/`Services/PageParsingTests` (unit-tier) pin the deterministic half of each pipeline (`Canonical`/`Ground`/`RetrievedUrls`/`IsIncomplete`, plan 29 §1–§2; each reader's `Accept`, plan 30 §3 and plan 31 §5 — where every constraint on the extraction lives, since structured outputs support neither `pattern` nor `minLength` nor numeric bounds). `Services/EnrichmentGoldenSetTests` and `Services/RouteImportGoldenSetTests` are a **third tier of their own**, `[Trait("Category", "Enrichment")]`: hand-run measurement harnesses that make real Foundry calls against `Services/GoldenSet.json` and `Services/RouteImportGoldenSet.json` (both checked in empty — a human fills them) and report, respectively, link precision plus the "correctly returned nothing" rate, and gate precision/recall plus extraction accuracy. The route-import set names blobs rather than embedding images: the repo is public and these are third-party scans (plan 30 §5). A pass costs roughly $15 for the enrichment set and under a dollar for the topo one. Integration tests are not opted *into* by a filter, they are simply not filtered *out*, so a new trait would run on every push — hence **both** CI test jobs (`.github/workflows/ci-cd.yml`) exclude `Category=Enrichment` explicitly, and getting that wrong is the one way this harness costs more than it saves. `Infrastructure/SeedData.cs` here is deliberately smaller than the API's: the worker never authenticates anyone, so it seeds a bare `ApplicationUser` row (just enough to satisfy the `AddedByUserId`/`SubmittedByUserId` foreign keys) rather than going through `TestUsers`/login.

Run everything (all three projects, both tiers each) with plain `dotnet test Acordanza.slnx` from the repo root, or `dotnet test` from within any one project's directory to run just that project.

Both integration fixtures (`ApiFixture`, `WorkerFixture`) configure their graph entirely through **process environment variables** (`ConnectionStrings__Default`/`ConnectionStrings:Default`, `Storage__ConnectionString`, `Jwt__Key`, ...) or an in-memory `IConfiguration` built the same shape — `Program.cs` reads these off `builder.Configuration` *before* `builder.Build()`, earlier than `WebApplicationFactory`'s configuration hooks can reach, so env vars are the only seam that lands in time for `ApiFixture`. This is process-global, which is why each fixture is an xunit.v3 **assembly fixture** (`[assembly: AssemblyFixture(typeof(...))]`) scoped to its own project, not per-class: two differently-configured hosts must never exist side by side, and tests don't run in parallel within either assembly (`[assembly: CollectionBehavior(DisableTestParallelization = true)]`) for the same reason. The env vars leak into the test process only, not the developer's shell — a `dotnet test` run and a `dotnet run` in the same shell session don't affect each other.

## Architecture

Flat, controller-per-resource structure — there is no service/repository layer; controllers talk to `AppDbContext` directly via EF Core:

- `Controllers/` — one controller per resource. All routes require `[Authorize]` (JWT bearer); write actions additionally require `[Authorize(Policy = Permissions.X)]` — see Authorization below.

  | Controller | Endpoints | Notes |
  |---|---|---|
  | `AuthController` | login (+ passkey 2nd factor), `/auth/me`, forgot/reset-password, `/accept-invite` | |
  | `AccountController` | self-service password change, profile name update | |
  | `PasskeysController` | register/list/delete the caller's passkeys | |
  | `RoutesController` | CRUD, `POST /{id}/ticks`\|`/validate`\|`/reject`\|`/topos`\|`/enrich`, `GET /grades`\|`/aid-grades`\|`/by-slug-path/{*path}` | `/enrich` is admin-only (`Permissions.RouteEnrich`, plan 18, see Route enrichment below); see behavior notes below for the filter/validation rules |
  | `ToposController` | `DELETE /{id}` only | upload lives on `RoutesController` |
  | `RouteImportsController` | `POST /image`, `POST /url`, `GET /mine`, `DELETE /{id}` | hand the worker a photo/URL to read a route off (plans 30/31, see Route import below); delete is own-row cleanup of a `Discarded`/`Failed` row only, plan 33 |
  | `AreaMediaController` | `DELETE /{id}` only | area-media mirror of `ToposController`; upload lives on `AreasController.UploadAreaMedia` |
  | `AreasController` | tree CRUD, `/roots`+`/{id}/children`, `GET /tree`, `PUT /{id}/coordinates`, `/validate`, `/reject` | see behavior notes below for `GET /tree` |
  | `AreaExpertsController` | self-service request/approve/reject | area-scoped route-validation rights, see below |
  | `FirstAscensionistsController` | list/create/update/delete, `GET /profiles`\|`/by-slug/{slug}`, `/validate`, `/reject`, `GET /pending` | `/profiles`/`/by-slug` back the frontend's "Sigue" section |
  | `FirstAscensionistLinksController` | self-service claim/approve/reject | see below |
  | `TicksController` | `GET /mine`, delete | `MyTickDto` rows carry just enough of the route (incl. `Length`, plan 20) to render `TickedRouteCard` without a second round-trip |
  | `UsersController` | `GET /` (admin-only), `POST /invite`, `GET /my-invites` | `user.invite` is held by *every* role, quota-capped per role (`Invites:MaxForUser`/`MaxForModerator`, admins unbounded — issue #113); `my-invites` returns the caller's invitees plus `invitesLeft`/`maxInvites` |
  | `ContributionsController` | `GET /routes`, `/areas`, `/first-ascensionists` | see behavior notes below |

  Behavior notes that don't fit the table:

  - **`RoutesController`** — `GET /` filters on `q`/`areaId`/`grade`/`orientation`/`gear`/`hasTopo`/`firstAscensionistId`; `orientation` is `string[]?` (plan 28), bound from repeated `?orientation=north&orientation=south` query params and matched with `Contains` (`= ANY(@p)`, one round trip), OR-ed together the same way the frontend's compass-rose filter lets a climber pick several shade-facing sectors at once — an unknown value 400s with the same message `ValidateOrientation` returns on write, keeping the read and write paths consistent. Only `Name`/`AreaId` are required (plan 34) — `POST`/`PUT` reject a *present* grade that isn't a valid French-scale value via `Models/GradeValidator` (issue #152) or a *present* aid grade that isn't a valid A0–A5/C0–C5 value via `Models/AidGradeValidator`, but a route with neither is legal. `GET /routes/by-slug-path/{*path}` resolves a route by its full shareable path — the trailing segment as the route slug, the rest walked via `AreaHierarchy.ResolveSlugPath` the same way `AreasController`'s equivalent action does — alongside, not replacing, the numeric `GET /{id}` (plan 21).
  - **`AreasController`** — `GET /tree` is the whole area tree flat and geometry-free, `{Id, Name, ParentAreaId, RouteCount, ValidationStatus}`, for `AreaPicker`/`TreeSelect` to hold client-side (plan 35 §1); `RouteCount` is the area's own routes only, each filtered by `ValidationVisibility.Routes` — the client rolls subtree totals up itself.
  - **`ContributionsController`** — a read model over the routes/areas/first-ascensionists the current user created plus each one's validation status, backing the "Contribuciones" page under "Mi acordanza"; belongs to no single resource, so it isn't folded into any of the controllers above. One paginated endpoint per kind rather than one payload with all three (issue #149), since the page shows a single tab at a time and the other two kinds are never fetched until their tab is opened; the paths carry no `mine` segment because every action derives its filter from `GetUserId(User)` and never accepts an id from the client. Ordering is `CreatedAt` descending with an `Id` tie-break — `CreatedAt` alone isn't a total order, and without the tie-break a tied row could appear on two pages and another on none.
- **Validation visibility** (issue #72, plan 11) — `GET /routes`/`/routes/grades`, `GET /areas`/`/areas/roots`/`/areas/{id}/children`/`/areas/tree` (plan 35 §1 — `RouteCount` on each node is also filtered, through `ValidationVisibility.Routes`), `GET /first-ascensionists`/`/first-ascensionists/profiles` and `GET /areas/by-slug-path/*`'s `children` projection all filter to `Models/ValidationVisibility.cs`'s rule — `x.ValidationStatus == Approved || x.AddedByUserId == callerId` — so a pending/rejected record stays reachable only to its author and to reviewers. Detail-by-id/slug reads (`GET /routes/{id}`, `GET /first-ascensionists/by-slug/{slug}`, the area itself in `GET /areas/by-slug-path/*`) are deliberately **not** gated — this is a private app where every account can already read everything, and a pending record is only reachable by guessing its id/slug; gating "lists" but not "details" is the line the plan draws. A route's embedded `FirstAscensionists` credits are never filtered either, even when the opener record itself is pending. Three new query-string affordances carry the exceptions:
  - **`?includeUnvalidated=true`** on `GET /areas`, `/areas/roots`, `/areas/{id}/children` and `GET /first-ascensionists` — skips the filter for the management screens (`/manage/areas`, `/manage/first-ascensionists`) that exist to *fix* records, including rejected ones; `403`s unless the caller holds the matching `.validate` permission (`area.validate`/`first-ascensionist.validate` — not `.edit`, since `first-ascensionist.edit` is also granted dynamically to any user linked to their own opener record, which would let them enumerate every unvalidated one).
  - **`?openedByMe=true`** on `GET /routes` — "Mis aperturas" (`/my-acordanza/my-openings`): filters to routes the caller is credited as a first ascensionist on and bypasses the visibility filter entirely, since these are the caller's own credits regardless of who created the route or its status.
  - **`GET /routes/pending`** and **`GET /areas/pending`** — the review queue's own view of not-yet-decided records (`RoutePendingDto`/`AreaPendingDto`), replacing what used to be `PendingTasksContext` downloading the entire routes/areas tables and filtering client-side. `GET /routes/pending` has no policy attribute — narrowed per-caller by `AreaExpertAuthorizer.BuildAreaCheckAsync(User, Permissions.RouteValidate)` the same way `ValidateRoute`/`RejectRoute` already are, so a caller with neither the role permission nor an approved area expertise gets `[]`. `GET /areas/pending` is plain `[Authorize(Policy = Permissions.AreaValidate)]` (area validation has no area-expert path — see `ValidateArea`/`RejectArea`).
  - Routes now auto-validate on create when the creator can validate them (`RoutesController.CreateRoute`, mirroring `AreasController.CreateArea`/`FirstAscensionistsController.CreateFirstAscensionist`) — via `AreaExpertAuthorizer.CanActOnAreaAsync(User, Permissions.RouteValidate, route.AreaId)` rather than a bare claim check, since route validation is area-scoped. Without this a moderator's own new route would vanish from "Busca" the instant they saved it.
  - The tree is **not** walked for visibility — a route's or area's own status decides it, never a parent's; `AreaHierarchyService`'s snapshot stays complete regardless (it's an internal resolution structure for breadcrumbs/slug paths, not a display list).
- `Acordanza.Core/Models/` — shared with `Acordanza.Worker` (plan 22: Core holds what both processes use, and nothing else — see backend's split rationale in `.claude/plans/22-worker-project-split.md`).

  | Model | What it is | Notes |
  |---|---|---|
  | `ApplicationUser` | extends `IdentityUser` | `Name` (max 20 chars) is the only user-facing display value — email is PII, never shown to other users; `PasswordHash == null` marks an invited-but-not-yet-accepted account; `ConfirmedAt` is set once, by `AuthController.AcceptInvite` or `Program.cs`'s `create-user` branch, and stays null forever for pre-existing accounts with no recoverable confirmation date |
  | `ClimbingRoute` | a route | `Slug` unique per `AreaId` (see slug notes below) |
  | `Area` | a tree via nullable `ParentAreaId` | `Slug` doubles as the topo blob-storage prefix, so it's frozen at creation (see slug notes below); `Polygon` (a JSON-owned list of `GeoPoint`) plus recomputed `CentroidLat`/`CentroidLng` back the map view |
  | `FirstAscensionist` | a route's opener/establisher | `Slug` backs `/fa/{slug}` (issue #137, see slug notes below); optional `UserId` link to an `ApplicationUser`, set only via an approved `FirstAscensionistLinkRequest`; a pending/rejected record is hidden from `/fa` and pickers for everyone but its author, but stays embedded, unfiltered, in every route payload that credits it |
  | `FirstAscensionistLinkRequest` / `AreaExpert` | near-identical self-service request/approve/reject shapes | both implement `IReviewableRequest` — shared `ReviewStatus` (`Pending`/`Approved`/`Rejected`), `DecidedAt`/`DecidedByUserId`/`RejectionReason`; see `Services/ReviewRequestService.cs` below for the shared approve/reject/cancel primitive |
  | `Topo` | an uploaded route photo | `BlobName`/`ContentType`/`FileName` plus who uploaded it, cascades with its `ClimbingRoute` |
  | `RouteImport` | a request to read a route off a photo or URL the user supplied | plans 30/31; `RouteImportKind`/`RouteImportStatus` are string-converted like `ReviewStatus`, and the four states are load-bearing: `Discarded` is the reader answering "this isn't a usable topo"/"this page isn't about a route", `Failed` is the pipeline breaking, and only the second is worth retrying |
  | `AreaMedia` | a sector photo | the same shape as `Topo` hung off an `Area` instead — shares `Topo`'s blob container and `MediaUploadService` upload path, differing only in blob-name prefix, surfaced through the same `TopoDto`/SAS-URL machinery |
  | `Tick` | a logged ascent | belongs to one `ClimbingRoute` and one `ApplicationUser` |
  | `PasskeyCredential` | a registered WebAuthn credential | cascades on user delete |

  **Validation lifecycle** — `ClimbingRoute`, `Area` and `FirstAscensionist` all implement `IValidatable` (`ValidationStatus` — a `ReviewStatus` reused from the request-review flows above, string-converted like theirs — plus `DecidedAt`/`DecidedByUserId`/`RejectionReason`), sharing one three-state lifecycle via the static `Validation` helper (`Models/Validation.cs`): `Validation.MarkValidated` sets `Approved` and clears any prior `RejectionReason`, `Validation.MarkRejected` sets `Rejected` plus the reason, `Validation.InvalidateIfChanged` resets to `Pending` and clears the decision — but only when the controller determines the edit actually changed something, so a no-op re-save doesn't spuriously send a validated record back to the queue. The same three entities also share `Models/ValidationVisibility.cs` — three `Expression<Func<T, bool>>` predicates (one per entity, not a shared generic — EF Core's translation of member access through a generic interface constraint isn't reliable) encoding the one publication-gate rule browse endpoints filter on; see "Validation visibility" above (`ClimbingRoute`'s `Orientation`/`Gear` are still free-form-ish string fields at this layer, not a fixed route "type" column — `RoutesController`'s create/update/search paths validate them against the `Orientation`/`Gear` enums in `Acordanza.Api/Dtos/RouteEnums.cs` instead (DUP-12), and its read-side DTOs expose those enums rather than bare strings, but no EF conversion/migration was introduced; see `frontend/src/api/types.ts`'s `orientationLabels`/`gearLabels`). The same three entities also each carry `AddedByUserId`/`AddedBy`/`CreatedAt` (creator attribution feeding `ContributionsController`) — non-nullable only on `ClimbingRoute`, whose column predates this and always has real data; on `Area`/`FirstAscensionist` it's nullable, since pre-existing rows have no recoverable creator and simply never show up in anyone's contributions list.

  **Slug scoping differs per entity, deliberately** — `ClimbingRoute.Slug` is unique per `AreaId` (scoped to the route's own area rather than globally like `FirstAscensionist.Slug` or per-parent like `Area.Slug`, since `Name` has no uniqueness constraint at all and a global namespace would hit the "-2"/"-3" collision suffix constantly on common route names), regenerated whenever `Name` or `AreaId` changes (`RoutesController.GenerateUniqueRouteSlugAsync`) — nothing is keyed on this column the way `Area.Slug` doubles as the topo blob-storage prefix, so a corrected name or a moved route shouldn't leave a stale URL behind; it backs the shareable `/routes/{area-slug-path}/{route-slug}` URL, the area segment resolved live from `AreaId` via `AreaHierarchy.SlugPath` and never itself stored (plan 21). `FirstAscensionist.Slug`, unlike `Area.Slug`, is regenerated whenever `Name` changes (`FirstAscensionistsController.GenerateUniqueSlugAsync`), since nothing else is keyed on it and a corrected name shouldn't leave a stale URL behind; names aren't unique here (unlike `Area`'s per-parent uniqueness), so the "-2"/"-3" suffix loop is the primary disambiguator, not just a diacritics fallback.
- `Dtos/` — request/response records per resource. Controllers project EF entities into these directly in LINQ `Select` calls rather than mapping in a separate layer.
- `Acordanza.Core/Data/AppDbContext.cs` — `IdentityDbContext<ApplicationUser>` plus one `DbSet` per app model. Indexes on `Grade`/`AreaId`/`Tick.RouteId`/`Topo.RouteId`; `ApplicationUser.NormalizedEmail` is unique; `Area` has case-exact-unique `(ParentAreaId, Name)` and `(ParentAreaId, Slug)` (nulls treated as equal, so two root areas still collide); `AreaExpert`/`FirstAscensionistLinkRequest` each have a unique filtered index on their `(xId, UserId)` pair scoped to `Status = 'Pending'`. `ClimbingRoute`/`Area`/`FirstAscensionist`'s `AddedBy`/`DecidedBy`, `Tick.Climber`, and `Topo.UploadedBy` use `DeleteBehavior.Restrict` (deleting a user doesn't cascade); `Tick.Route`, `Topo.Route`, `PasskeyCredential.User`, and both `AreaExpert`'s/`FirstAscensionistLinkRequest`'s FKs to their subject + requesting user cascade. Tables are split across three Postgres schemas via `OnModelCreating`: `identity` (the built-in `AspNetUsers`/`AspNetRoles`/... tables), `auth` (`PasskeyCredentials`), and `core` (everything else app-specific).
- `Acordanza.Core/Services/` — the services both `Acordanza.Api` and `Acordanza.Worker` actually use, no more (plan 22's rule — see §2 of the plan for what was deliberately kept out, e.g. all of `Authorization/`, which the worker has no use for):

  | `MediaUploadService` | the shared image-upload flow on top of `BlobStorageService` — content-type/size validation, the numbered-blob-name race loop, DB-save-vs-blob-orphan cleanup; `UploadNumberedAsync` takes a `Stream`+content-type rather than an `IFormFile` (Core carries no ASP.NET Core reference) — `ValidateImage(IFormFile?)` lives on the API instead, in `Services/ImageValidation.cs`, since validating an *upload* is an HTTP concept |

  | `LinkRules` | route link trim/cap-10/max-length/http(s)-allowlist/dedupe — hoisted out of `RoutesController` (plan 18) so both human-entered links (`CreateRoute`/`UpdateRoute`) and worker-found ones (`RouteEnrichmentService`) share the same stored-XSS guard |

  | `RouteSlugs.GenerateUniqueAsync` | the per-area route-slug uniqueness loop, hoisted out of `RoutesController` when plan 30 gave the worker a second route-creating path — same reason `LinkRules` was hoisted in plan 18 |
- `Acordanza.Api/Services/` — `JwtTokenService` (issues the bearer token, embedding role-derived and dynamic permission claims — see Authorization below); `ImageValidation.ValidateImage(IFormFile?)` (the two upload controllers' entry check, ahead of `MediaUploadService.UploadNumberedAsync` in Core); `IEmailSender`/`ConsoleEmailSender`/`ResendEmailSender`/`EmailTemplates` (see Email below); `InviteTokenProvider` (the invite-only, 7-day-lifespan Identity token provider plus the `InviteTokens` name/purpose/lifespan constants — see Auth model below); `RouteEnrichmentQueue`/`RouteImportQueue` (the *enqueue* side of each pipeline only — see Route enrichment and Route import below; the API never drains); `ReviewRequestService` (the atomic approve/reject/cancel primitive shared by `AreaExpertsController` and `FirstAscensionistLinksController` — a single conditional `ExecuteUpdateAsync`/`ExecuteDeleteAsync` scoped to `Status == Pending`, generic over `IReviewableRequest`, disambiguating 0-rows-affected into `AlreadyResolved` vs `NotFound`; `FirstAscensionistLinksController.Approve` keeps its extra transaction + linking UPDATE + auto-reject-on-conflict fallback inline — genuinely different shape, not pushed into the shared primitive); `Notifications.BestEffortAsync` (the try/catch-and-log wrapper both controllers' decision-notification emails go through, so a delivery failure can't fail the decision itself).
- `Acordanza.Worker/Services/` — the *drain* side of both pipelines, and nothing else (see Route enrichment and Route import below): `EnrichmentQueueProcessor`, `RouteEnrichmentService`, `IRouteEnrichmentProvider`+`ITopoVerificationProvider`; `RouteImportQueueProcessor`, `RouteImportService` (the shared spine) behind `IImportReader`'s two implementations `TopoImageReader`/`WebPageReader`, `ITopoImportGateProvider`+`ITopoExtractionProvider`+`TopoImportFewShotSet` (the Image kind) and `IPageExtractionProvider`+`PageFetcher`+`PrivateAddresses`+`PageText`+`PageImages` (the Url kind) — all providers with their `NoOp*`/`Claude*` implementations; `ServiceCollectionExtensions.AddEnrichmentWorker` — the worker's entire DI graph as one `IServiceCollection` extension method, called by both `Program.cs` and the integration tests (see Testing above), so there's one definition of "what the worker is."
- `Authorization/` — the RBAC plumbing: `Permissions.cs` (flat `{entity}.{action}` constants — `area`/`route`/`tick`/`first-ascensionist` × `create`/`edit`/`validate`/`delete`, plus `route.enrich` (admin-only by construction — in `Permissions.All` but not `RolePermissions`' user/moderator sets nor `DynamicPermissions`, see Route enrichment below), `user.manage` and `user.invite` (the latter held by *every* role — see `UsersController` above), `area-expert.request`/`.approve`, and `first-ascensionist-link.request`/`.approve`), `Roles.cs` (`admin`/`moderator`/`user`), `RolePermissions.cs` (the static, additive role→permission map — `user` ⊂ `moderator` ⊂ `admin`), `RoleSeeder.cs` (idempotently creates the 3 roles, backfills the `user` role onto any account with none, and retires the legacy `first-ascensionist` role onto any account still holding it — run on every startup), `DynamicPermissions.cs` (adds `route.edit`/`route.validate`/`first-ascensionist.edit` claims for any user linked to a `FirstAscensionist` record, on top of their role's permissions — used by both `JwtTokenService` and `AuthController.Me` so the JWT claims and the `/auth/me` response never drift apart), `AreaExpertAuthorizer.cs` (the shared "permission claim OR approved `AreaExpert` of the top-level area" check — see the next paragraph). Built on stock ASP.NET Core `Authorization` (one named policy per permission, registered in `Program.cs`, requiring a `permission` claim) — no external authorization package.
- `Acordanza.Core/Migrations/` — EF Core migrations; regenerate with `dotnet ef migrations add --project ../Acordanza.Core --startup-project .` (from `backend/Acordanza.Api/` — see Commands above) after any model or `OnModelCreating` change, don't hand-edit. `AppDbContext` and `Migrations/` live in the same project, so the default migrations assembly follows the context and no `MigrationsAssembly(...)` call is needed; `Microsoft.EntityFrameworkCore.Design` stays a package reference on `Acordanza.Api` only (the startup project, where the tooling requires it), not on Core. Documented exceptions: `AddUniqueEmailAndPasskeys`, which hand-inserts a `migrationBuilder.Sql(...)` data backfill ahead of the generated unique-index creation; `ValidationRejectionAndContributors`, which hand-corrected a scaffolded `RenameColumn` that the diff engine pointed at the wrong new column (matched `ValidatedByUserId` to the new `RejectionReason` column instead of `DecidedByUserId`, since both were nullable `text`, which would have silently moved every existing decider's user id into a rejection-reason column) and hand-inserted a `migrationBuilder.Sql(...)` backfill for the new `ValidationStatus` column (its `AddColumn` default of `""` isn't a valid `ReviewStatus` name) — see that migration's comments for both; `BackfillValidationStatusApproved`, an empty (no schema change) migration whose `Up` is entirely a hand-written `migrationBuilder.Sql(...)` — issue #72 turned validation into a publication gate, and the prior migration's backfill only approved rows with a recorded decision, so this one-time sweep approves every pre-existing route/area/first-ascensionist row (leaving `DecidedAt`/`DecidedByUserId` null, since nobody actually reviewed them) so the gate ships without hiding the whole catalogue; `OptionalRouteGradeAndLength` (plan 34), which appends one hand-inserted `migrationBuilder.Sql(...)` after the scaffolded `AlterColumn`/`AddColumn` operations, backfilling `Length = 0` rows to `NULL` now that the column can say "unknown" properly — `RouteImportService.AcceptableLength`'s former sentinel, which the scaffolded diff has no way to know about.

Approved `AreaExpert`s are a *separate*, narrower grant from the `DynamicPermissions` claim mechanism above: rather than a global claim, `Authorization/AreaExpertAuthorizer.cs` checks (per request, when the permission claim is absent) whether the caller is an approved expert of the subject's top-level area (covering all its subareas) — used with `route.validate` for route validation and `area.edit` for area media upload/delete; same "ownership scoped to a query, not a claim" pattern `DELETE /ticks/{id}` uses (see Auth model below). `AuthController.Me`/`MeResponse` still surfaces an `isAreaExpert` flag (any approved area, not per-area) purely so the frontend can decide whether to show the "pending tasks" bell — it grants nothing by itself.

Note: the retired `first-ascensionist` *role* and the `first-ascensionist.*` *permissions* (on the `FirstAscensionist` entity — a route's opener/establisher record) were unrelated namesakes; the permissions live on, now granted dynamically (see `DynamicPermissions` above) rather than through a role. `Permissions.FirstAscensionistValidate` in particular used to be declared in `Permissions.cs`/`RolePermissions.cs` (role-based — `moderator`/`admin`, not one of the dynamic grants above) but referenced by no endpoint; `FirstAscensionistsController`'s `POST /{id}/validate`, `POST /{id}/reject` and `GET /pending` are its first actual use.

Traces/metrics/logs export via OpenTelemetry (`builder.Services.AddOpenTelemetry()` in `Program.cs`) to whatever `OTEL_EXPORTER_OTLP_ENDPOINT`/`OTEL_EXPORTER_OTLP_HEADERS` point at (Grafana Cloud in production); unset locally, so the exporters just have nowhere to send and dev is unaffected.

### Auth model

Identity is used in "core" mode (`AddIdentityCore`, no cookie/UI scaffolding) purely for password hashing and user storage. Email is the username (`RequireUniqueEmail = true`; `UserName` and `Email` are always set to the same value). There is still no public HTTP registration endpoint — accounts are provisioned either via the `create-user` CLI branch at the top of `Program.cs` (`dotnet run -- create-user <email> <password> <name> [role]`, which runs before the normal web host pipeline is built), or in-app by any user holding `user.invite` via `UsersController.InviteUser`, which creates the account immediately (with no usable password) and emails a single-use link to `/accept-invite`. Password policy is relaxed (`RequiredLength = 8`, no complexity requirements) since accounts are hand-provisioned for a small trusted group.

Password reset (`AuthController.ForgotPassword`/`ResetPassword`) and invite acceptance (`AcceptInvite`) both ride ASP.NET Identity data-protection tokens, base64url-encoded for the URL, but through **two different providers with different lifespans**: reset uses the default one (1 hour, `DataProtectionTokenProviderOptions.TokenLifespan`, tightened from Identity's 1-day default); invites use the dedicated `InviteTokenProvider` (`Services/InviteTokenProvider.cs`, registered under `InviteTokens.ProviderName` in `Program.cs`), whose lifespan is **7 days** because an invite is asynchronous — the recipient isn't sitting at the keyboard. That 7-day window is load-bearing beyond the link itself: `UsersController.InviteUser` uses `InviteTokens.Lifespan` to decide whether someone else's still-pending invite to the same email may be taken over. The provider needs its own concrete type *and* options type — Identity resolves a named provider by concrete DI type, so registering `DataProtectorTokenProvider<ApplicationUser>` under a second name would silently hand back the same 1-hour singleton the default provider already uses (see that file's header comment). `ValidateToken` accepts either provider's token, read-only (`VerifyUserTokenAsync`, unlike `ResetPasswordAsync`, doesn't consume it), so both `ResetPasswordScreen` and `AcceptInviteScreen` can show a dead-link error before rendering the form. Tokens are single-use (`ResetPasswordAsync` rotates the user's `SecurityStamp` on success). `ForgotPassword` always returns `{ ok: true }` regardless of whether the account exists, so it can't be used to enumerate registered emails, and is rate-limited per-IP (`forgot-password` policy, 3/15min) to bound both abuse and Resend's free-tier quota.

Passkey (WebAuthn/FIDO2) second-factor login is **opt-in per user**, implemented manually (not via ASP.NET Identity's built-in 2FA, which assumes `SignInManager`/cookies this app doesn't use) with `Fido2.AspNet`: a user with no registered passkey logs in with just a password; a user with one or more registered via `PasskeysController` gets a `mfaRequired` response from `POST /api/auth/login` carrying WebAuthn assertion options and a `sessionId`, and must complete `POST /api/auth/login/passkey` with the browser's assertion before a JWT is issued. WebAuthn challenges are cached in-process (`IMemoryCache`, 5 min TTL) between the options/complete steps — fine for a single-instance deployment, but would need a distributed cache if ever scaled to multiple replicas.

Everyone with an account can read all routes, but ticks are private per user: `GET /routes`/`GET /routes/{id}` never expose who else ticked a route or their notes/ratings, only a `HasTick` flag scoped to the caller; a user's own tick history is only reachable via `GET /ticks/mine`. Write access is otherwise role-based (see `Authorization/` above) and not generally ownership-based, but `DELETE /ticks/{id}` is one exception: `tick.delete` is broadly granted (every role has it, see `RolePermissions`), so on its own it wouldn't stop one user from deleting another's private tick by guessing its id — the endpoint additionally scopes its query to `ClimberUserId == <caller>`, same pattern as `PasskeysController`'s self-service delete (silently no-ops rather than deleting) and `AreaExpertsController.Cancel`.

### Email

`IEmailSender.SendAsync(to, subject, html)` is the only abstraction; `Program.cs` wires up `ResendEmailSender` (via the [Resend](https://resend.com) HTTP API) when `Resend:ApiKey` is configured, or `ConsoleEmailSender` (just logs the email) otherwise — so the invite/reset/notification flows can be exercised locally with zero email-provider setup. `Services/EmailTemplates.cs` holds one `(Subject, Html)`-returning method per email: `ResetPassword`, `InviteUser`, `NewUserRegistered` (sent to admins when an invite is accepted), `AreaExpertApproved`/`Rejected`, `FirstAscensionistLinkApproved`/`Rejected`. The approve/reject notifications in `AreaExpertsController`/`FirstAscensionistLinksController` are best-effort (`Services/Notifications.BestEffortAsync`) — a delivery failure must not fail the decision itself.

### Storage (topo images)

`BlobStorageService` stores route topo photos and area media images in a single Azure Blob Storage container (`Storage:ContainerName`, default `topos`), which also carries the `_imports/` staging prefix for route import and the `_fewshot/` example set (see Route import below); uploads route through `MediaUploadService` (`RoutesController.UploadTopo`/`AreasController.UploadAreaMedia`), while reads (`GetReadSasUrlAsync`) and deletes (`ToposController.DeleteTopo`, `AreaMediaController.DeleteAreaMedia`, plus the cascade cleanup in `RoutesController.DeleteRoute`/`AreasController.DeleteArea`) call `BlobStorageService` directly. Locally it authenticates via `Storage:ConnectionString` against an Azurite emulator (started by `docker-compose.yml`); in production (no connection string configured) it instead uses the container app's user-assigned managed identity against the real account (`Storage:AccountName`/`Storage:ManagedIdentityClientId`) — same dual-credential pattern `Program.cs` uses for Data Protection key persistence (also blob-backed, so keys survive Container Apps' scale-to-zero restarts). Blob names are `{area-slug-path}/{route-slug}-{NN}.{ext}` for topos and `{area-slug-path}/_media-{NN}.{ext}` for area media (see `MediaUploadService.UploadNumberedAsync`); the frontend never gets a direct blob URL — `TopoDto` carries a backend-issued, time-limited SAS URL instead (`MediaUploadService.ImageUrlLifetime`, 15 min).

### Route enrichment (plan 18)

`POST /routes/{id}/enrich[?force=true]` (`Permissions.RouteEnrich`, admin-only) enqueues a `route-enrichment` queue message and returns `202` (`404` unknown route, `409` already enriched without `force`, `503` enqueue failure); `CreateRoute` never enqueues — every enrichment is a deliberate per-route act. `Acordanza.Worker`'s `EnrichmentQueueProcessor`/`RouteEnrichmentService` drain the queue and call Claude (via Azure AI Foundry, `IChatClient`, `claude-opus-5` with web search + web fetch) to find links and a topo for the route, filtering results through `Acordanza.Core/Services/LinkRules.cs` and a second cheap vision call (`ITopoVerificationProvider`, `claude-haiku-4-5`) before writing anything — all through `AppDbContext` directly, never `RoutesController.CreateRoute`/`UpdateRoute`, so `Validation.InvalidateIfChanged` is structurally unreachable from this path. Without `Anthropic:FoundryResource` configured, no-op providers keep the whole queue/worker/endpoint loop exercisable locally.

See `backend/docs/route-enrichment.md` for the full design: the shared `IChatClient` transport all five worker Claude call sites use (`AnthropicChatExtensions.WithAnthropicRequest`/`RawStopReason`/`RawContent`, plan 32), and the plan 29 retune — grounding filter (nothing appended that the model didn't demonstrably retrieve), the evidence/confidence gate, per-host/per-run caps, the reachability check, and `stop_reason` handling — read it before touching either file.

### Route import (plans 30 and 31)

Two ways to get a route into the log without typing it: upload a topo photo (`POST /route-imports/image`, multipart) or paste a page URL (`POST /route-imports/url`, JSON), both `[Authorize(Policy = Permissions.RouteCreate)]` and rate-limited (`route-import`, 10/hour). Each returns `202` with a `RouteImport` row; `GET /route-imports/mine` lists the caller's own, `DELETE /route-imports/{id}` cleans up a `Discarded`/`Failed` row only (never the route/topo/link it may have produced). The worker drains a `route-import` queue message through `IImportReader` (`TopoImageReader` for photos, `WebPageReader` for URLs) into the shared `RouteImportService`, which matches-or-creates the route, attaches the topo, appends only the URL the user actually submitted as a link, matches (never creates) first ascensionists, and never auto-approves — every created route lands `Pending` for a human to review. The sector always comes from the submitter's form, never inferred from the photo or page.

See `backend/docs/route-import.md` for the full design: the SSRF-guarded fetch (`PageFetcher`'s `ConnectCallback`, redirect/size/content-type limits — the actual security boundary, since a non-admin can trigger a fetch from inside the worker's trust boundary), the acceptance predicate (`TopoImageReader.Accept`/`WebPageReader.Accept`, `PrintedGrade` parsing of non-French grade notations), the blob staging/promotion flow, and why each of the constraints above (sector never inferred, nothing auto-approved, only the submitted URL is ever written) is load-bearing rather than incidental.

The API and the worker share only `Acordanza.Core` (`Models/`, `Data/AppDbContext.cs`, `Migrations/`, plus the services listed under Architecture above) — there is no project reference between them, so a controller reaching into the enrichment pipeline, or the worker reaching into an ASP.NET filter, is a compile error, not a code-review catch. Each has its own config contract: the API needs `Jwt:*`/`Cors:*`/`Fido2:*`/`Resend:*`/`Storage:DataProtectionContainerName` and the worker needs none of that — its Terraform (`infra/terraform/container_app_job.tf`) hands it exactly `ConnectionStrings__Default`, `Storage__{AccountName,ContainerName,EnrichmentQueueName,RouteImportQueueName,ManagedIdentityClientId}`, `Anthropic__{FoundryResource,ManagedIdentityClientId}` and `OTEL_*`, checked by `Acordanza.Worker.Tests/Services/WorkerConfigurationTests.cs` (see Testing above). The identity client id is deliberately written twice, once per section, rather than shared: it is the same user-assigned identity either way, but the Foundry client has no business reading a `Storage__` key to find it. The worker's OpenTelemetry resource name (`acordanza-enrichment-worker`) is set in code (`AddEnrichmentWorker`'s `ResourceBuilder.AddService` call), not through `OTEL_RESOURCE_ATTRIBUTES`'s `service.name` — an explicit `AddService` call always wins over the env var, so setting both would just be a second, silently-losing place to write the name (this used to mean every worker log/trace arrived in Grafana Cloud mislabelled as the API).

### OpenAPI document

`Program.cs` calls `AddOpenApi()`/`MapOpenApi()` (the latter dev-gated — this is a private API, not a published one) so the frontend can generate its API types from a real contract instead of the hand-mirrored DTOs it used before (see `frontend/CLAUDE.md`'s `api/generated.ts`). The document is checked in at `backend/Acordanza.Api/openapi/Acordanza.Api.json`, not regenerated on every `dotnet build`: `Acordanza.Api.csproj` sets `OpenApiGenerateDocumentsOnBuild=false` because generating it actually boots the app through the same top-level `Program.cs` that runs EF migrations against Postgres and provisions the blob container on startup — wiring that into routine builds would make every `dotnet build` depend on `docker compose up -d`. Regenerate on demand instead, same prerequisites as `dotnet run` (Postgres/Azurite up, `Jwt:Key` configured):

```
ASPNETCORE_ENVIRONMENT=Development dotnet build -p:OpenApiGenerateDocumentsOnBuild=true
```

`AddOpenApi` also registers a schema transformer that strips the `| string` alternative .NET's Web JSON defaults (`JsonNumberHandling.AllowReadingFromString`) would otherwise add to every numeric property's schema — without it, every id/count/rating in the generated frontend types would be `number | string` instead of `number`. CI's `openapi-contract-check` job (`.github/workflows/ci-cd.yml`) regenerates both this document and the frontend's `generated.ts` and fails on any diff, so a DTO change with a stale generated type can't merge.
