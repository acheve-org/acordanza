# Route enrichment (plan 18)

Full design detail for the route-enrichment worker pipeline, extracted from `backend/CLAUDE.md` to keep that file loadable without pulling in a subsystem most backend tasks never touch. See `backend/CLAUDE.md`'s "Route enrichment" section for the current-state summary and when to read this file.

### Route enrichment (plan 18)

`POST /routes/{id}/enrich[?force=true]` (`Permissions.RouteEnrich`, admin-only — see Authorization above) enqueues a `route-enrichment` Azure Storage Queue message (`Services/RouteEnrichmentQueue.cs`) and returns `202`; `CreateRoute` never enqueues — every enrichment is a deliberate, per-route act (a button in the frontend's `RouteDetailModal`, or the `enqueue-enrichment` CLI command), not something that happens automatically on write. `404` if the route doesn't exist, `409` if `ClimbingRoute.EnrichedAt` is already set and `force` isn't `true`, `503` if the enqueue itself fails (nothing else happened in the request, so this isn't best-effort).

The worker side is `Acordanza.Worker`, a dedicated project and image (plan 22 — it started as a third `Program.cs` CLI branch on the API image, `process-enrichment`, but that shared one configuration contract between two processes with different needs, which is what caused the job to be unable to start at all: the shared prelude read `Jwt:Key` unconditionally, which the job's Terraform never set). `Acordanza.Worker/Program.cs` is `Host.CreateApplicationBuilder(args)` → `AddEnrichmentWorker` → migrate → drain → exit, no args and no CLI branches — it's the whole binary now, not a subcommand of one. In production it runs as an event-driven Container Apps Job that scales from zero on queue depth via KEDA and exits once drained. `Acordanza.Worker/Services/EnrichmentQueueProcessor.cs` drains the queue (batches of 8, 5-minute visibility timeout, deletes on success, leaves a failed message for redelivery, drops it as poison past 5 dequeue attempts), calling `Acordanza.Worker/Services/RouteEnrichmentService.cs` per message. That service calls `IRouteEnrichmentProvider.FindAsync` (real impl: `ClaudeRouteEnrichmentProvider` — one Messages API call on `claude-opus-5` at `effort: high` with the server-side web search **and web fetch** tools plus structured outputs, reached through Azure AI Foundry so the worker authenticates via the container app's managed identity instead of a stored API key; the model string must stay equal to the Foundry deployment name in `infra/terraform/ai_foundry.tf`, which is what it's sent as), filters the found links one at a time through `Acordanza.Core/Services/LinkRules.cs` (the same allowlist/cap/dedupe `RoutesController.CreateRoute`/`UpdateRoute` use, hoisted out of the controller so both paths share it — resolved per-link here, not as one all-or-nothing batch, since a single junk URL from the model must not reject everything else it found) and appends them, then verifies any topo candidate with a second, cheap vision call (`ITopoVerificationProvider`/`ClaudeTopoVerificationProvider`, `claude-haiku-4-5`) before importing it through `MediaUploadService` exactly like a human `UploadTopo`.

**All five Claude call sites in the worker share one transport** (plan 32): `ClaudeRouteEnrichmentProvider`, `ClaudeTopoVerificationProvider`, `ClaudeTopoImportGateProvider`, `ClaudeTopoExtractionProvider` and `ClaudePageExtractionProvider` each take a constructor-injected **`IChatClient`** (Microsoft.Extensions.AI) rather than building their own `IAnthropicClient` — `FoundryClient.CreateChatClient` wraps the same Foundry client `FoundryClient.Create` always built, and `AddEnrichmentWorker` registers it once as `AddChatClient(...).UseOpenTelemetry(sourceName: "acordanza-enrichment-worker").UseLogging()`, so the middleware pipeline wraps every call site at once (the tracer provider's matching `.AddSource("Experimental.Microsoft.Extensions.AI")` is what keeps those spans from being generated and silently dropped). Registered only on the Foundry-configured branch — the five `NoOp*` providers take no client. Everything expressible portably goes through `ChatOptions`: model id, max tokens, messages, vision content (`DataContent`), and the JSON schema (`ChatResponseFormat.ForJsonSchema`). Three things have no correct portable mapping and live behind one shared seam, `Services/AnthropicChatExtensions.cs`:

- **`WithAnthropicRequest(modelId, effort, params tools)`** — the request-side fragment (`ChatOptions.RawRepresentationFactory`), which *merges* with the portable `ResponseFormat` rather than clobbering it. It sets `output_config.effort` (portable `ChatOptions.Reasoning.Effort` serializes as legacy `thinking.budget_tokens` for Anthropic, a different field entirely), guarded by `ClaudeModelCapabilities.SupportsEffort` — still the single source of truth for which models 400 on it — and declares the exact Anthropic tool variants (`HostedWebSearchTool` downgrades to a search tool with no `MaxUses`/`UserLocation`/`BlockedDomains`, which is most of enrichment's search tuning). **Every** provider calls it, even the two whose model skips effort and the three that carry no tools, so a model swap touches one uniform call site. It also throws if `ChatOptions.MaxOutputTokens` is unset: the client is deliberately built with no default model or token budget (two models, four budgets across the five providers), and `max_tokens` is required on the wire.
- **`RawStopReason()`** — `ChatResponse.FinishReason` collapses `pause_turn` and `end_turn` into the same `"stop"`, so every `ClaudeRouteEnrichmentProvider.IsIncomplete(...)` check reads the raw `stop_reason` string instead. Trusting the portable value would restore exactly the silent "tool loop exhausted, nothing found, route marked enriched" no-op plan 29 diagnosed.
- **`RawContent()`** — `web_search_tool_result`/`web_fetch_tool_result` are Anthropic server-tool shapes with no portable content type, so enrichment's grounding reads them off `ChatResponse.RawRepresentation`. `RetrievedUrls` itself is unchanged. Usage's `server_tool_use.web_search_requests` (the searches count in the usage log line) is the one other field sourced this way, inline.

`Acordanza.Worker.Tests/Services/ClaudeModelCapabilitiesTests` asserts the helper directly, which is why it now covers all five providers' effort behaviour rather than the two that used to expose a `BuildRequestParams`. Adding a sixth Claude call site means injecting `IChatClient` and calling `WithAnthropicRequest` — not constructing a client.

Plan 29 retuned all of that after its first real use, and the shape of the retune is worth knowing before touching either file:

- **Nothing is appended that the model didn't demonstrably retrieve.** `FindAsync` collects every URL out of the response's `web_search_tool_result`/`web_fetch_tool_result` blocks and drops any structured-output link that isn't in that set (`Ground`, compared through `Canonical` — lowercased scheme/host, no fragment, no trailing slash, tracking parameters stripped). A hallucinated URL becomes zero links rather than one bad link. This filter lives in the provider, not the service, because the provider is the only thing holding the raw response; the seam stays "here are links we stand behind".
- **The model must show its work.** The schema is an array of `{ url, title, kind, evidence, confidence }`, and `RouteEnrichmentService.SelectCandidates` keeps only `confidence == "high"` with a non-empty `evidence` quote, ordered `topo → guidebook → first-ascent → video → sector`. The prompt states the negative contract explicitly: a page about a same-named route in another area is a miss, returning nothing is the common correct answer, the quote must be copied and must name both the route and its sector.
- **Two caps beyond `LinkRules`, both worker-side** (`ApplyCaps`): at most one link per host and four per run. `LinkRules.MaxLinks` stays 10 because it is the *human-entry* contract shared with `RoutesController` — tightening it would silently constrain the edit form.
- **Survivors are checked for reachability** (`IsReachableHtmlPageAsync`: 5s, `ResponseHeadersRead`, 2xx + `text/html`) before they're appended.
- **The topo has two outcomes, not one.** `topoImageUrl` (only obtainable at all because web fetch can open a page — web search returns text and never an `<img src>`, which is why plan 18's version never once imported a topo) downloads → vision-checks → imports; `topoPageUrl` with no image URL is appended as a `topo`-kind link instead. Auto-importing a third-party topo scan under `route.AddedByUserId` remains the highest-risk write here, and switching the default to link-only is one branch in `EnrichAsync`.
- **`stop_reason` is checked** (`IsIncomplete`): `pause_turn`, `max_tokens` and `refusal` log a warning and return `Completed: false`, which is what leaves `EnrichedAt` **null** so re-pressing the button works instead of needing `force=true` to retry an environmental failure. `MaxTokens` is 8192 and not optional — the request omits `thinking`, which on Opus 5 means adaptive thinking is *on*, and `max_tokens` bounds thinking and response text together.
- **Appended links carry `Link.Source = LinkSource.Enrichment`** (`RoutesController` writes `Human` on both create and update). This gates nothing and never touches `ValidationStatus` — it exists so a bad link is identifiable: the detail modal badges it, and a bad batch is one `WHERE "Source" = 'Enrichment'` away from being deleted. The read DTOs carry `List<RouteLinkDto>` (`{ url, source }`) while `UpsertRouteRequest.Links` stays `List<string>?` — deliberately asymmetric, since a request body has no business asserting its own provenance and accepting one would make `Source` forgeable.
- **The whole decision chain is logged as one line per run** (`enrichment stages route=... grounded=... valid=... reachable=... appended=...`), which is what says whether to tune the prompt or the filter. Writes go through `AppDbContext` directly, never `UpdateRoute`, so `Validation.InvalidateIfChanged` is structurally unreachable from this path — auto-appended links/topos can't bounce an approved route back to `Pending`. Without `Anthropic:FoundryResource` configured, `AddEnrichmentWorker` registers `NoOpRouteEnrichmentProvider`/`NoOpTopoVerificationProvider` instead — the queue/worker/endpoint stay fully exercisable locally (it just logs a skip and sets `EnrichedAt`), same philosophy as `ConsoleEmailSender`.
