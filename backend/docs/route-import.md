# Route import (plans 30 and 31)

Full design detail for the route-import pipeline (photo/URL → route), extracted from `backend/CLAUDE.md` to keep that file loadable without pulling in a subsystem most backend tasks never touch. See `backend/CLAUDE.md`'s "Route import" section for the current-state summary and when to read this file.

### Route import (plans 30 and 31)

Two ways to get a route into the log without typing it: upload a photo of a topo (the **Image** kind, plan 30) or paste the URL of a page about the route (the **Url** kind, plan 31). `POST /api/route-imports/image` (multipart: `file` + `areaId`) and `POST /api/route-imports/url` (JSON: `{ url, areaId }`) each return `202` with a `RouteImport` row; `GET /api/route-imports/mine` is the submitter's own list of both, backing `/my-acordanza/my-imports`. `DELETE /api/route-imports/{id}` (plan 33) removes one of the submitter's own rows — cleanup, not undo: it never touches the `ClimbingRoute`/`Topo`/`Link` the row may have produced (`Route` is already `SetNull` on delete, below), and only ever accepts `Discarded`/`Failed` rows — `Pending` might still be mid-flight in the worker and `Completed` is the only record of how a route came to exist, so both 409. Deleting a `Failed` Image row also deletes its still-staged blob eagerly rather than waiting on the 7-day lifecycle sweep. Two sub-paths rather than plan 31 §1's single content-type-switched endpoint for one reason only: an OpenAPI operation is keyed by path *and* method, so two actions on one `POST` produce one documented operation and silently drop the other — the generated frontend types would then describe half an API and `openapi-contract-check` would pass anyway.

All three are `[Authorize(Policy = Permissions.RouteCreate)]` — deliberately **not** a new permission and **not** `route.enrich`: that one is admin-only because plan 18's spend was unbounded per run and the button was an optional extra, whereas here the call *is* the feature, costs about $0.10 (roughly double plans 30/31's $0.05 estimate, which priced the extraction on Sonnet 5 — see the model note below), and the write lands as `Pending` for review. Someone trusted to create a route by typing it is trusted to create one by photographing it or by pasting the post about it. The bound is a per-IP rate-limit policy (`route-import`, 10/hour, registered alongside `forgot-password` in `Program.cs`) rather than a role, shared by both kinds — which also caps how many outbound fetches one caller can ask the worker to make. Its permit limit is readable from `RateLimits:RouteImportPerHour` **only** so `ApiFixture` can raise it: the limiter is process-global and partitions on an IP that is always `"unknown"` under `WebApplicationFactory`, so at the production value the suite would 429 on its ninth import request rather than on anything real.

`RouteImport` (`Acordanza.Core/Models/RouteImport.cs`) is the keystone of the design, not accounting. Enrichment gets away with a null result because the route still exists and an admin pressed the button while looking at it; here the submission *is* the entire artifact, and a user who waits two minutes for silence has been given a broken feature. So one table buys user-visible state, a retry, a stated reason, the orphan-blob cleanup story, and a labelled dataset that accumulates for free. `Outcome` is user-facing and therefore **Spanish** (the strings all live in `RouteImportOutcomes`); `Status` is `Pending`/`Completed`/`Discarded`/`Failed`, and the last two are distinct on purpose — `Discarded` is the reader saying "this isn't a usable topo" / "this page isn't about a climbing route" (a real answer), `Failed` is the pipeline breaking (Foundry timeout, poison message, blob gone, fetch error), which *is* worth retrying. Delete behaviours: `Area` cascades, `SubmittedBy` is `Restrict` (matching `Topo.UploadedBy`), `Route` is `SetNull` so deleting a bad machine-created route leaves the import's history intact rather than erasing the evidence of how it got there.

**One table, three nullable columns, not table-per-hierarchy** (plan 31 §1). `Kind` (`Image`/`Url`) plus `BlobName`/`ContentType`/`FileName` (Image) and `SourceUrl` (Url); everything else — the sector, the submitter, the status vocabulary, the outcome, the matched route — is shared. TPH would buy compile-time separation at the price of a discriminator EF manages, two `DbSet`s, and two shapes for every read DTO and every page that lists imports, while what actually varies is three nullable strings. The invariant it would enforce for free is a one-line check constraint instead (`CK_RouteImport_KindPayload`), visible in the schema. `SubmittedBy`, not plan 30's `UploadedBy`: nobody uploads a URL. The rename landed as a hand-written migration (`RenameTopoImportsToRouteImports`) rather than the scaffolded drop-and-recreate — plan 30's table had already shipped with real rows in it; see that migration's comment.

**The sector comes from the form, never from the model — for both kinds.** `ClimbingRoute.AreaId` is a required FK into a tree, and fuzzy-matching "Sector Los Bloques" against the area table is the most error-prone inference in the flow and the one whose failure is most expensive — a route filed under the wrong sector is worse than no route. A blog post makes this *more* true, not less: crag naming in prose is unreliable in exactly the way that defeats matching. The submitter picks it, which also makes every *other* answer better: the breadcrumb is passed into the extraction prompt as given context, the same lesson plan 29 §2 learned about first ascensionists. The Url kind's prompt does ask for `sectorMentioned`, but only as a **cross-check**: a page naming a crag that appears nowhere in the picked breadcrumb gets a note in `Outcome` and nothing else happens — a false discard here would be both infuriating and frequent.

**Blob layout (Image kind only).** Blob Storage has no rename, so the API writes `_imports/{guid}.{ext}` in the existing `topos` container (same container, distinct prefix — a second container would need its own Terraform resource, role assignment and ensure-exists call for no isolation this app needs), and a successful run re-uploads those bytes through `MediaUploadService.UploadNumberedAsync` under the route's proper prefix exactly like a human `UploadTopo`, deletes the staged blob, and repoints `RouteImport.BlobName` at the promoted name. A discard deletes the staged blob immediately but keeps the row and its reason — the image costs money to keep, the explanation is what the user needs. Orphans from a crashed run are swept by an Azure Storage lifecycle rule on the `_imports/` prefix (delete after 7 days, `infra/terraform/storage.tf`), so there is no cleanup code to get wrong. A Url import stages nothing: its artifact is the URL on the row, and a topo it finds is downloaded straight off the page into the same attach path.

**A second queue, not a second message type.** `route-import` alongside `route-enrichment` on the same storage account: `EnrichmentQueueProcessor` treats an undeserializable message as poison, which a second shape on one queue would trip, and each wants its own visibility timeout (five minutes for a web-search loop, two for an import). Both import *kinds* ride this one queue, though — `RouteImportMessage(int ImportId)` is the whole wire contract, and which reader runs is a column on the row. Both `QueueClient`s live in the same DI container, so the route-import one is registered **keyed** (`RouteImportKeys.QueueServiceKey`) — a second unkeyed registration would silently shadow the enrichment client depending on registration order. Still **one job and one binary**: `azurerm_container_app_job.enrichment` carries a KEDA scale rule per queue, and `Acordanza.Worker/Program.cs` drains both in sequence and exits.

**The two kinds converge on one spine** (plan 31 §2). `IImportReader` is the seam: `TopoImageReader` (Image) and `WebPageReader` (Url), each returning a `RouteReading(Route, Topo, DiscardReason, Failed)`. `RouteImportService` consumes a reading and knows nothing about images or HTTP — it does match-or-create, attaches the topo, appends the link, matches first ascensionists and writes the outcome, once, for both kinds. `RouteReading` is also what keeps the `Discarded`/`Failed` distinction honest: the reader is the only thing that can tell them apart, and the record forces it to say which.

**The Image kind: two calls** (`TopoImageReader`).

- **The gate** — `ITopoImportGateProvider`/`ClaudeTopoImportGateProvider`, `claude-haiku-4-5` (the deployment enrichment's topo check already uses), structured output `{ isTopo, reason }`. A `false` short-circuits the run into `Discarded` before the expensive call. This is a *different question* from the one `ITopoVerificationProvider` answers ("is this a topo on which route X is identifiably marked"), which needs a route that doesn't exist yet — hence a sibling interface, not a widened one.
- **The extraction** — `ITopoExtractionProvider`/`ClaudeTopoExtractionProvider`, `claude-opus-5` (the enrichment deployment, shared). The reason it isn't Haiku is **resolution**, not intelligence: images are downsampled server-side to a per-tier long edge (1568 px on Haiku, 2576 px on Opus 5), so a 4000 px phone photo of a guidebook page reaches Haiku at 1568 px no matter what is sent. Plenty for a binary "is there a line drawn on this rock"; very possibly the difference between a correct extraction and a garbled one for reading `La Loca 6b+ 25m` off small print. Plans 30/31 specified `claude-sonnet-5` for this and for the Url kind's extraction below, and **there is no such deployment** — the subscription has no GlobalStandard quota for the sonnet family (the same constraint that once pinned enrichment to sonnet-4-5). Opus 5 sits in the same 2576 px image tier, so the resolution argument transfers intact; what changes is price ($5/$25 per MTok against $3/$15) and one thing that isn't optional: `MaxTokens` on both extraction calls is sized for **thinking plus payload**, since the requests omit `thinking` and adaptive thinking is on by default on Opus 5 — the same trap documented for enrichment above.

**The Url kind: one call, plus a cheap image sweep** (`WebPageReader`, plan 31 §5). A gate as a *separate* call earns nothing here — both calls would carry the same page text at the same price per token — so `isClimbingRoute` is a field in the same schema. `IPageExtractionProvider`/`ClaudePageExtractionProvider` runs on the same `claude-opus-5` deployment as the topo extraction above (this plan adds no Foundry resource) and declares **no tools at all**: we did the fetching, so there is no server-side tool spend, no `pause_turn` out of a tool loop, and structurally no way for the model to return a URL we didn't hand it. Afterwards the page's images are swept — ordered candidates, first hit wins, the rest never downloaded — through enrichment's existing `ITopoVerificationProvider`, which is exactly the right question ("is this a topo on which *this* route is marked") now that the extraction has produced a name and grade. Typical cost is one or two Haiku calls; the worst case is eight.

**The fetch is ours, and it is the security boundary** (plan 31 §3). The worker runs inside a Container Apps environment whose managed identity holds Storage Blob/Queue Data Contributor and Cognitive Services User, so "fetch this URL for me" from a non-admin user is a request to open a connection from inside that trust boundary — and the metadata endpoint, the Postgres host and everything else on the environment's network are a private IP away. `PageFetcher` wraps one named `HttpClient` (`import-fetch`) whose `SocketsHttpHandler` is the guard:

- **`ConnectCallback`, not a resolve-then-check.** Checking DNS separately from connecting leaves a rebinding window the attacker controls the TTL of; connecting to an `IPAddress` we vetted ourselves closes it, because the stack never gets a second resolve. `PrivateAddresses.IsPublic` is the rule — pure, static, and unit-tested at both ends of every blocked range, IPv4 and IPv6, including the `::ffff:169.254.169.254` mapped form that is the one that gets missed.
- **Redirects are followed by hand**, max 3 hops, http(s) only, each hop a fresh request through the same client so the callback vets it too.
- **`text/html` only**, 10-second overall timeout, and the body read through a **2 MB cap enforced while reading** — a server can lie about `Content-Length` or omit it, and `CopyToAsync` into an unbounded `MemoryStream` is the failure that follows.
- **The same client downloads the images** (5 MB cap). An `<img src>` on a fetched page is exactly as attacker-supplied as the page URL was, so a second unguarded client would reopen everything this closes.

The API's own validation of a submitted URL is deliberately **syntactic only** (`LinkRules.Resolve`, http(s), length, trimmed): any network check it makes is advisory by the time the worker connects. What it buys is telling the user their typo is a typo now rather than after a two-minute wait.

`PageText.Extract` and `PageImages.Extract` (plan 31 §4) are the two pure, no-I/O halves of the HTML handling — regex rather than a parser dependency, on plan 29 §4's supply-chain grounds and because the failure mode here is "we miss an image", not "we do something unsafe". `PageText` strips scripts/styles/comments/tags, decodes entities, collapses whitespace and caps at 30 000 characters; under ~200 characters is a stated discard (the JS-rendered/paywalled case) rather than an empty page for the model to hallucinate into. `PageImages` orders `og:image`/`twitter:image` first, then `<img>` in document order reading `src`, the largest `srcset` entry and the lazy-load attributes blogspot and wordpress use, resolves against `<base href>` or the post-redirect URI, drops `data:` URIs and obvious furniture, dedupes through `UrlCanonicalizer.Canonical` (hoisted out of `ClaudeRouteEnrichmentProvider` into `Acordanza.Core` so the API's duplicate-submission check shares it), and caps at 8.

**The acceptance predicate is where every constraint lives** — `TopoImageReader.Accept` and `WebPageReader.Accept`, both pure statics — because structured outputs support neither `pattern` nor `minLength` nor numeric bounds. A candidate is accepted when `confidence == "high"` and `evidence` is non-empty; the grade is no longer part of that gate (plan 34) — a human may save a route with no grade at all, so a photo or page that doesn't state one is written through with `Grade`/`AidGrade` both null rather than discarded. **The model is told to copy the grade, never to convert it** — Spanish sources are usually French-scale, but UIAA (`V+`) and YDS (`5.11a`) appear, and a converted grade is a guess wearing the costume of data; a string `PrintedGrade.Parse` can't resolve is a note (`RouteImportOutcomes.GradeNotUnderstood`, carrying the raw text) on an otherwise-accepted candidate, not a discard. Copying it verbatim means a multi-pitch source hands over its whole grade line rather than a grade (`MD+ 6c/A1 (6a+ obl)` — an alpine difficulty grade this log has no field for, the free grade, the aid grade, and the obligatory grade), so `Services/PrintedGrade.cs` sits between the raw string and `GradeValidator`/`AidGradeValidator`: outside the brackets it reads **strictly** (every token must be a French grade, an aid grade, a `french/aid` pair, or one of a named set of decorations — alpine difficulty, seriousness/equipment rating, obligatory marker — so `E2 5b` and `V+` stay unresolved instead of being mined for a French-looking substring, and two different French grades, e.g. a range like `6a/6b`, stay unresolved rather than a coin flip), inside them **leniently** (an obligatory grade is taken only when the source labelled it one; `6c (6a+)` yields `6c` and no obligatory grade). Worker-side rather than in Core beside `GradeValidator`, per plan 22's rule — the human-entry path in `RoutesController` must go on rejecting a whole grade line typed into the grade box. `RouteCandidate.ObligatoryGrade` is written to `ClimbingRoute.ObligatoryGrade` on **create only**: filling it on a matched route would be editing a human's route data from a photograph, which is what `RouteImportService`'s gap-filling (formerly `GradeDisagreement`, now three-way over `Grade`/`AidGrade`/`Length`: fill a route's null field from the candidate and say so, note a disagreement between two present values, stay silent when the candidate has nothing to add) exists to avoid for `ObligatoryGrade` specifically. `multipleRoutes: true` with no clearly dominant route is likewise a discard, not a coin flip. `stop_reason` is checked exactly as plan 29 §2 does, and `max_tokens`/`refusal` produce `Failed`, not `Discarded`. `Length` is nullable (plan 34) — null when the source doesn't state one or states something implausible, no sentinel involved.

**Match or create.** With the sector given, matching is deterministic: `Slugify.ToSlug(extractedName)` against `ClimbingRoute.Slug` **within the given area exactly**, not its descendants. On a match the topo is attached even if the route already has topos (enrichment skips in that case because nobody asked; here a human deliberately submitted), `Topo.UploadedByUserId` is the actual submitter, and neither `Grade` nor `Description` nor `ValidationStatus` is touched — a grade disagreement is recorded in `Outcome` for a human to decide on, because silently correcting a human-entered grade from a photograph or a blog post is the wrong default in a catalogue whose whole point is that people entered it. On no match a route is created **through `AppDbContext` directly, never `RoutesController.CreateRoute`**, so `Validation.MarkValidated` is structurally out of the path: `CreateRoute` auto-approves when the creator can validate the area, and an admin pasting a link must still get a route somebody has *read* before it goes live. The worker never approves. `AddedByUserId` is the submitter, so the route lands in their `/my-acordanza/contributions` and stays visible to them under plan 11's rule while it waits in `/manage/pending-tasks`.

**What a Url import may write, and what it may not.** The page is untrusted text entering a model that writes rows, and three structural bounds keep the blast radius small — chosen, not inherited: the sector is never inferred, nothing is ever approved, and **the only link ever written is the URL the user submitted**, never one found on the page or mentioned by the model (`LinkSource.Import`, a code-only enum addition — the column is `HasConversion<string>` with a store-side default). That last rule costs nothing and removes link-spam-by-injection entirely. **First ascensionists are matched, never created**: a blog post naming the openers is the most valuable thing a page carries that a photo does not, but creating `FirstAscensionist` rows from a model's reading of an attacker-controllable page is a write into a directory with its own section, claim flow and review queue. Names are slugified and matched exactly; misses are noted in `Outcome` so a human can add them and re-import; a name matching more than one record (the `-2` suffix family, detected by re-slugifying each candidate's *name* rather than trusting the globally-unique slug) is skipped as ambiguous rather than guessed. **Duplicate submissions short-circuit**: before calling anything, the worker looks for an existing `Completed` Url import with the same canonical `SourceUrl` whose route still exists, and completes against it for free.

**Few-shot examples** (Image kind's gate only) live in blob storage, not the repo (`TopoImportFewShotSet`, `Storage:FewShotPrefix`, default `_fewshot/`): `{prefix}gate/topo/*` and `{prefix}gate/not-topo/*`, where the prefix *is* the label, so there's no manifest to drift. In-repo embedded resources would be nicer — versioned with the prompt, reviewable in the same PR — but these are third-party topo scans and this repository is public. The set is downloaded once per process (a singleton cache, capped at six per label so an over-filled prefix can't quietly turn a $0.002 gate into a $0.40 one) and degrades to a zero-shot gate if listing fails. Prompt caching is deliberately **not** used: Haiku 4.5's minimum cacheable prefix is 4096 tokens, which six examples would clear, but the default 5-minute TTL would essentially never hit on sporadic uploads and the 1-hour TTL needs three reads to break even.

Every run logs one line — `route import stage=… kind=… extracted=… matched=… created=…`, plus the Url kind's `fetch=… text=… topoFound=…` — the analogue of enrichment's stage counts, and the thing that says whether to tune a prompt or a filter. Without `Anthropic:FoundryResource` the providers register as no-ops, so the whole submit → queue → worker → row loop stays exercisable locally against Azurite; for the Url kind the fetch and the HTML parsing run for real either way, since neither needs Foundry. Every no-op returns `Completed: false` (⇒ `Failed`) rather than a negative answer (⇒ `Discarded`), because an unconfigured environment is the pipeline never having looked, which is exactly what `Failed` means.
