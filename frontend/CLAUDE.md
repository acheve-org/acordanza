# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Applies to `frontend/` — the React + TypeScript client, built with Vite, package-managed with Bun. See the root `CLAUDE.md` for how this fits with the backend.

## Commands

All run from `frontend/`, using `bun`, not `npm`/`yarn`:

```
bun install
bun dev              # dev server on http://localhost:5173
bun run build        # tsc -b (typecheck) then vite build -> dist/
bun run lint         # oxlint
bun run preview      # preview a production build
bun run test         # vitest run
bun run test:watch   # vitest, watch mode
```

Needs `frontend/.env` (copy from `.env.example`) with `VITE_API_URL`, pointing at the backend (`http://localhost:5073/api` by default). Vitest (jsdom + `@testing-library/react`) is configured via the `test` block in `vite.config.ts`, with global `describe`/`it`/`expect` (see `tsconfig.app.json`'s `vitest/globals` type) and jest-dom matchers loaded in `src/test/setup.ts`. `vite.config.ts`'s `test.execArgv: ['--no-experimental-webstorage']` is load-bearing, not decorative: Node 22+'s own global `localStorage`/`sessionStorage` (non-functional without `--localstorage-file`) otherwise shadows jsdom's real per-window implementation and breaks anything touching `localStorage` (`AuthContext`'s session persistence, most directly) with `Cannot read properties of undefined` — see the testing section below for the rest of the harness (MSW, `renderWithProviders`, contract-typed factories).

## Architecture

`react-router` (`BrowserRouter` in `main.tsx`) drives routing. `App.tsx` special-cases two pathnames (`/reset-password`, `/accept-invite`) as reachable while fully logged out, *before* the auth gate — everything else gates on auth state (`LoginScreen` while logged out, nothing while `loading`), then renders `AppLayout` (header/user menu) with nested routes under it: `/` → `pages/HomePage.tsx` (the hub over the app's four sections — see the root `CLAUDE.md`), `/routes` → `pages/SearchPage.tsx` (the routes list, "Busca"), `/routes/new` and `/routes/:id/edit` → `pages/RouteFormPage.tsx`, `/explore` → `pages/ExplorePage.tsx` ("Explora"), `/first-ascensionists`(`/:id`) → `pages/FirstAscensionistsDirectoryPage.tsx`/`FirstAscensionistPage.tsx` ("Sigue"), `/settings` → `pages/SettingsPage.tsx`, plus the `/my-acordanza` and `/manage` shells below. The four top-nav items (Busca/Explora/Sigue/Mi acordanza) must stay in step with `HomePage`'s four cards. `/map` (the pre-#108 map path) redirects to `/explore`. No global state library for client/UI state; that's local `useState` per page, plus two contexts (auth, pending-tasks). Server data is fetched with `@tanstack/react-query` (`QueryClientProvider` in `main.tsx`, `staleTime: 0` and `refetchOnWindowFocus: false`) — see the data-fetching bullet below; this conversion is in progress page-by-page, so some pages still hand-roll fetch/refresh (issue: unify frontend data fetching). `pages/` holds route-level screens; `components/` holds shared pieces reused across them.

- `context/AuthContext.tsx` — session state. Holds `username`/JWT, persists `{ token, username }` to `localStorage` (`acordanza.auth`), and pushes the token into the API client via `setAuthToken`. On mount it validates a stored token against `GET /auth/me` and drops it silently on failure; the same response also seeds `hasPermission`/`isAreaExpert`/`isFirstAscensionist`. Login is two-step when the account has a registered passkey: `login(email, password)` returns a `PasskeyChallenge` instead of completing when the backend responds `mfaRequired`; `completeLoginWithPasskey(challenge)` runs the WebAuthn assertion via `@github/webauthn-json`'s `get()` and finishes the session. `LoginScreen` drives this — on `mfaRequired` it shows a "usa tu llave de acceso" step and auto-triggers the assertion. `LoginScreen` also has a "forgot password" mode (local state, not a route) that calls `authApi.forgotPassword`; the email it triggers links to `/reset-password`, handled by `pages/ResetPasswordScreen.tsx`.
- `context/PendingTasksContext.tsx` — aggregates everything the current user can review (unvalidated routes they can validate — role-based or, via `isAreaExpert`, area-scoped; unvalidated areas; pending area-expert requests; pending first-ascensionist-link requests; pending first ascensionists, gated on `Permissions.firstAscensionistValidate`) into one `total` count, shown as the header bell badge and the `/manage/pending-tasks` nav item. Fetches all five categories with `Promise.allSettled` (one category's failure shouldn't blank the others) and is gated so pages with nothing to review never issue the requests. Routes/areas are fetched via the dedicated `GET /routes/pending`/`GET /areas/pending` endpoints (server-narrowed to just the pending, reviewable-by-this-caller rows), not `GET /routes`/`GET /areas` filtered client-side — since validation gates those two endpoints' visibility now (see backend `CLAUDE.md`), filtering client-side would also mean paying for a whole-table download just to render a badge count. This also dropped the `allAreas`/`areasById` state that used to exist solely so `PendingTasksPage` could resolve a pending area's breadcrumb — `AreaPendingDto.namePath` is resolved server-side instead.
- `api/client.ts` — thin `fetch` wrapper (`api.get/post/put/delete/postForm`) that attaches `Authorization: Bearer` when a token is set and throws `ApiError` (with parsed `{ error }` body) on non-OK responses; `postForm` (multipart, used for topo uploads) skips the JSON `Content-Type` so the browser sets its own boundary. One `api/*.ts` file per backend resource (`routes`, `areas`, `areaExperts`, `firstAscensionists`, `firstAscensionistLinks`, `ticks`, `topos`, `users`, `account`, `passkeys`, `auth`) builds on it; `api/permissions.ts` mirrors `backend/Acordanza.Api/Authorization/Permissions.cs` — keep the two in sync by hand when adding a permission (generating this one too was considered and rejected as disproportionate). `api/queryKeys.ts` is the one place react-query key shapes live (e.g. `queryKeys.routes(filters)`, `queryKeys.route(id)`) — add an entry as each page converts rather than inlining key arrays at the call site; `api/errorMessage.ts` (`errorMessage(err, fallback)`) is the shared `ApiError` → Spanish string helper for both query/mutation errors and locally-caught ones.
- `api/generated.ts` — generated, not hand-edited: `openapi-typescript` run against the backend's checked-in OpenAPI document (`backend/Acordanza.Api/openapi/Acordanza.Api.json`) via `bun run generate-api` (`frontend/package.json`; internally `bunx openapi-typescript@<pinned version> ... -o src/api/generated.ts` — `bunx`, not a `bun add`-ed devDependency, because `openapi-typescript` only supports `typescript@^5.x` and this workspace is on `typescript@^7`; a shared/hoisted install crashes at runtime, so it gets its own isolated resolution instead). Re-run it after any backend DTO change (see backend `CLAUDE.md`'s OpenAPI section) and commit the diff — CI's `openapi-contract-check` job fails the build if a regenerate would produce one you didn't commit. `api/types.ts` re-exports the pieces of `components['schemas']` the frontend uses under the app's existing type names (`RouteSummary`, `AreaDetail`, ...) so call sites never reference `generated.ts` directly; it also keeps a few things hand-written that generation can't produce: client-only shapes with no backend DTO (`RouteFilters`, `TickFilters`, `UserFilters`, `AreaBounds`), and narrowed literal-union types where the backend's contract is a closed set but the column is a plain string — the shared `RequestStatus` alias at the top of the file covers both the request-review flows' `status` (`AreaExpert`, `FirstAscensionistLinkRequestSummary`) and the validation lifecycle's `validationStatus` (`RouteSummary`, `RouteDetail`, `AreaSummary`, `AreaDetail`, `FirstAscensionistProfile`, `Contribution`). Two label maps sit on `RequestStatus`: `reviewStatusLabels` ("Pendiente de aprobación"/"Aprobado"/"Rechazado", for the self-service request pages) and `validationStatusLabels` ("Pendiente de validación"/"Validado"/"Rechazado", for `DetailModal`/`AreaPage`/`PendingTasksPage`/`MyContributionsPage`) — kept separate because the wording differs even though the underlying three states are the same; don't merge them into one map.
- `components/` — one file per shared UI piece. Route browsing: `Filters` (search/area/grade/orientation/gear/tag/hasTopo, debounced 250ms in `SearchPage`'s effect; the grade options come from `GET /routes/grades`, since grades are free text on the backend), `RoutesList`/`RouteCard` (`RouteCard` shows a check icon when `hasTick`, never a count — ticks are private, see backend `CLAUDE.md`; it also shows a `Chip status={route.validationStatus}` when the route isn't approved, so a route the caller can see purely because they authored it — pending or rejected, everywhere else invisible — doesn't read as a bug; `AreaPicker` does the analogous thing by appending `validationStatusLabels[...]` to a non-approved option's label), `DetailModal` (route detail incl. topo photos and the validate/reject actions — "Rechazar" opens the shared `RejectReasonModal`; ticks aren't listed here — only a button opening `AddTickModal`), `AddTickModal`, `TickedRouteCard` (a row in `MyTicksPage`'s history). Route/area pickers used by `RouteFormPage`: `AreaPicker`, `FirstAscensionistPicker`. Areas management (`AreasPage`/`MyAreasPage`): `AreaTree` (lazy-loaded via `GET /areas/roots`+`/{id}/children`), `AreaNameModal`, `AreaPolygonModal` (draws `Area.Polygon` on the map, `leaflet-draw`). `AreaTree` and `AreaPolygonModal` both pass `includeUnvalidated: true` — the management screens exist to fix records including rejected ones, so they opt out of the approved-or-mine visibility filter every other reader gets by default (backend `CLAUDE.md`'s "Validation visibility"); safe unconditionally here since `/manage/areas` already gates on `area.edit`, which is only ever granted alongside `area.validate`. `AreaMap` — the `/map` view, `react-leaflet` + `leaflet`, fetches areas bounded to the visible viewport. Approval-queue pieces shared between `PendingTasksPage` and elsewhere: `PendingRequestsList` (generic approve/reject list — `PendingAreaExpertRequests`/`PendingFirstAscensionistLinkRequests` are thin wrappers supplying the subject field and API calls), `RequestAreaExpertModal`, `RequestFirstAscensionistLinkModal`, `RejectReasonModal` (the shared "reason required" form every reject flow uses — request-review decisions and, now, `IValidatable` rejections alike). `InviteUserModal` (`UsersPage`), `LoginScreen`, `LoadingBar`.
- `pages/MyTicksPage.tsx` (`/my-acordanza/my-routes`, "Mis vías") is the current user's own tick history — infinite-scroll paginated via `GET /ticks/mine`, filtered by the same q/areaId/gear/tag shape `Filters` uses. Don't confuse it with `pages/MyOpeningsPage.tsx` (`/my-acordanza/my-openings`, "Mis aperturas"), which lists routes the user opened as first ascensionist, via `listMyOpenings()` (`GET /routes?openedByMe=true`) — server-side filtered and exempt from validation visibility (these are the caller's own credits regardless of who created the route or its status), so this page no longer downloads every route and filters client-side. `pages/ClaimFirstAscensionistPage.tsx` and `pages/MyAreasPage.tsx` are the self-service request UIs (first-ascensionist link, area-expert) for `FirstAscensionistLinksController`/`AreaExpertsController`. `pages/MyContributionsPage.tsx` (`/my-acordanza/contributions`, "Contribuciones", `api/contributions.ts`) is a different thing again: not a request flow, but a read-only three-tab view (Vías/Sectores/Aperturistas, via `GET /contributions/mine`) over the validation status — pending/approved/rejected, with the rejection reason when applicable — of everything the current user has *created*, using `useQuery` from the start rather than the legacy `useState`/`useEffect` pattern below.
- `pages/FirstAscensionistsDirectoryPage.tsx` (`/first-ascensionists`, "Sigue") lists aperturistas with a debounced name search, each card showing how much they've opened and where (`GET /first-ascensionists/profiles`); `pages/FirstAscensionistPage.tsx` (`/first-ascensionists/:id`) is one opener's page — their profile plus the routes they opened (`GET /routes?firstAscensionistId=`), reusing `RoutesList`/`DetailModal` the same way `AreaPage` does. Don't confuse either with `pages/FirstAscensionistsPage.tsx` (`/manage/first-ascensionists`), the moderator/admin CRUD table over the same records — read-only browsing lives under "Sigue", editing under "Gestionar". `FirstAscensionistsPage` calls `listFirstAscensionists(q, true)` — `includeUnvalidated: true`, same opt-in `AreaTree`/`AreaPolygonModal` use, safe here since the page is already gated on `first-ascensionist.delete`, only ever granted alongside `first-ascensionist.validate`.
- `pages/ExplorePage.tsx` (`/explore`, "Explora") — `AreaMap` plus a paginated list of top-level zones linking into `/areas/*`.
- `pages/MyAcordanzaLayout.tsx` (`/my-acordanza`) — left-nav shell for a user's own stuff, reached from the top nav's "Mi acordanza" item. Structurally identical to `pages/ManageLayout.tsx` (`/manage`, reached via "Gestionar", shown only if the user can edit areas or manage users): both are `<Outlet>`-based parent routes sharing the `.side-nav-layout`/`.side-nav`/`.side-nav-item`/`.side-nav-content` CSS in `styles.css`. Pages nested under either (`MyAreasPage`, `ClaimFirstAscensionistPage`, `MyContributionsPage`, `MyTicksPage`, `MyOpeningsPage`, `AreasPage`, `UsersPage`, `PendingTasksPage`) render bare — no own `<main>`/page-padding wrapper, no "Volver" link — since the shared shell's `.side-nav-content` supplies layout and its persistent aside nav already provides a way back. `UsersPage` (admin-only, `Permissions.userManage`) lists/filters/paginates accounts and opens `InviteUserModal`; each row also shows who invited the account and when, plus its confirmation date, whichever of those the account actually has (a "Sin confirmar" chip stands in for a missing confirmation date on accounts that haven't accepted their invite yet).
- `pages/RouteFormPage.tsx` (`/routes/new`, `/routes/:id/edit`) — a full page, not a modal, since it also hosts topo photo upload/removal when editing; shared between create/edit via the `editing` (route `id` present) branch.
- `pages/AcceptInviteScreen.tsx`/`pages/ResetPasswordScreen.tsx` — both reachable while logged out (see `App.tsx` above), both call `POST /auth/validate-token` on mount to show a dead-link error immediately rather than only on submit, and both complete via the same backend password-reset-token mechanism (see backend `CLAUDE.md`'s Auth model).
- `pages/SettingsPage.tsx` — profile name editing, password change (both `api/account.ts`), and passkey management (`api/passkeys.ts`): list/register/delete. Registration calls `@github/webauthn-json`'s `create()` with the options the backend returns, wrapped as `{ publicKey: options }` — the backend's Fido2NetLib option objects already serialize to the same WebAuthn-L3 JSON shape the library expects, no manual base64url handling needed.
- Server data fetching is converting to react-query, page by page: a page calls `useQuery({ queryKey: queryKeys.x(...), queryFn: ... })` instead of `useState` + `useEffect(fetch).then(setX)`, and a mutation (`useMutation`) invalidates the relevant query keys on success (`queryClient.invalidateQueries({ queryKey: [...] })`) instead of calling a hand-rolled `refresh*` function — this is the same "always re-fetch after a mutation, never patch local state" discipline the app already had, just expressed as query keys instead of bespoke refresh functions. `pages/SearchPage.tsx` is the converted example (list + detail + delete/validate/tick/topo mutations); most other pages (and `PendingTasksContext`) still use the older hand-rolled `useState`/`useEffect`/`refresh*` pattern described below until they convert too — don't be surprised to find both styles side by side.
- The pre-react-query pattern, still in use on unconverted pages: data is never cached beyond the current render — every mutation is followed by an explicit re-fetch (e.g. `refreshRoutes()`/`refreshDetail()`, `PendingTasksContext.refresh()`) rather than local state patching.
- **Modal/dropdown data is fetched by the thing that needs it, when it opens** — never by the page behind it. A page must not prefetch a list whose only consumer is a modal it might open (that's a request every visitor pays for so the few who open the modal save a spinner). So `RequestAreaExpertModal`/`RequestFirstAscensionistLinkModal` fetch their own pickers' options on mount, `AreaPolygonModal` fetches the polygons it draws, and `AreaPicker`/`FirstAscensionistPicker` fetch via `Combobox`'s `onOpen` — their mount-time fetch is skipped entirely unless there's already a selection whose label needs resolving. Corollary: don't give a page a "is the modal worth showing" check that needs the modal's data (the modal renders its own empty state instead), and keep list endpoints backing a tree/row slim enough that the row itself needs no extra fetch — `GET /areas/roots` carries a `hasPolygon` flag so `AreaTree` can label its polygon button without loading any vertices.

## Styling

Tokens (colors, fonts, radii, spacing) and the shared component set — `Button`, `Chip`, `EmptyState`, `GradePill`, `Modal`/`ModalActions`/`ConfirmModal`, `Pagination`, `List`/`ListRow`, `Badge`, `RemoveButton`, `Combobox` — live in the sibling `design-system/` workspace package (`acordanza-design-system`; see the root `CLAUDE.md` and `/DESIGN.md`), imported as `import { X } from 'acordanza-design-system'` and, for its CSS, `@import 'acordanza-design-system/styles.css'` at the top of `src/styles.css`. `src/styles.css` itself is plain CSS (no CSS-in-JS, no Tailwind) that only covers app-shell/page layout and pieces not yet promoted to the design system (forms, the picker "create new" sub-form). It's a light theme, not dark — driven by the same CSS custom properties the design system defines (`--bg`, `--accent`, `--font-display`, etc.). Extend the theme by adding/reusing those variables rather than hardcoding colors in component-scoped styles (styling is global, not per-component); new reusable UI belongs in `design-system/src/components/`, not `styles.css`.

## Linting & types

`oxlint` (`.oxlintrc.json`) enforces `react/rules-of-hooks` as an error; TypeScript is strict (`noUnusedLocals`, `noUnusedParameters`, `verbatimModuleSyntax` — type-only imports must use `import type`).

## Testing

`src/test/` holds the harness shared by every page/component test, colocated as `X.test.tsx` next to `X.tsx`:

- `server.ts`/`setup.ts` — an MSW `setupServer()` with **`onUnhandledRequest: 'error'`**. This is doing real work, not just hygiene: it's what mechanically enforces the "modal/dropdown data is fetched by the thing that needs it, when it opens" rule above — an accidental page-level prefetch shows up as a failing test (an unhandled request), not a review comment. There are no default handlers; every test registers exactly the routes it needs via `server.use(...)`.
- `apiUrl.ts` — the `http://localhost:5073/api` base `api/client.ts` falls back to when `VITE_API_URL` isn't set (the case in the test environment, since no `.env` is loaded); handlers match requests against it.
- `factories.ts` — one `make*` factory per DTO the suite constructs (`makeRoute`, `makeArea`, `makeMeResponse`, …), each a `Partial<T>`-overridable object typed off `api/generated.ts`'s `components['schemas']` rather than hand-rolled. This is deliberate: test files live under `src`, so the existing `tsc -b` in `bun run build` typechecks them too — a backend DTO change that regenerates `generated.ts` breaks the *mocks* at build time, not just the app. Combined with CI's `openapi-contract-check` job (which fails if `generated.ts` is stale), the loop closes: mocks can't silently drift from the real API contract the way hand-written fixtures would.
- `renderWithProviders.tsx` — wraps a subject in the three things pages assume: a fresh `QueryClient` (`retry: false`, so a mocked-error test fails fast instead of retrying for seconds), a `MemoryRouter` (`initialEntries` configurable), and auth state. Auth state has two modes:
  - **Default: a direct `AuthContext` value.** `auth: {...}` overrides merge over a logged-in-as-plain-user default (see `makeAuthValue`) — no network calls, so permission-matrix tests (`DetailModal.test.tsx`, `Filters.test.tsx`, `ManageLayout.test.tsx`) just vary `permissions`/`isAreaExpert`/etc. and assert what renders. `AuthContext` is exported from `context/AuthContext.tsx` (`const` → `export const`, no other change) for exactly this reason — it's a smaller, more honest change than restructuring the provider to take injected state.
  - **`useRealAuthProvider: true` mounts the actual `AuthProvider`** (`localStorage` + `GET /auth/me`) — the only way to test the bootstrap/login/logout state machine itself: dropping an invalid stored token silently, the two-step passkey login (`AuthContext.test.tsx`, `LoginScreen.test.tsx`), `logout()` clearing the shared query cache. `auth` overrides are ignored in this mode since the provider computes its own state. Mock `@github/webauthn-json`'s `get()` for passkey flows — the real WebAuthn API doesn't exist in jsdom.

Working agreement:

- **Bug fix** → a failing test that reproduces it, first. This is where the suite pays for itself fastest, and it's the one thing a screenshot can never do: prove the bug is gone *and* stay behind to prove it stays gone.
- **New endpoint** → a row in the backend's authorization-matrix tests (`backend/Acordanza.Api.Tests/`), plus a happy path and one edge case.
- **New page or component** → at minimum, it renders with realistic contract-typed data, and any permission-gated action is covered both ways (rendered and hidden). Testing what the UI *shows* is not a substitute for the backend enforcing it, and vice versa — neither test layer covers what the other does.
- Not a coverage target. Coverage percentages push tests toward trivial pages and away from the authorization matrix, which is where the value actually is.

Leaflet map rendering (`AreaMap`, `AreaPolygonModal`) is out of scope for this layer — jsdom has no real layout, so testing it here means mocking so much the test ends up asserting the mocks. Cover the surrounding logic (viewport-bounded fetching, the polygon payload sent on save) and leave rendering to manual/`run-acordanza` checking. Full end-to-end journeys likewise live outside this suite, in the `run-acordanza` skill (Playwright, deliberately tiny) — this layer carries the regression load instead.

`design-system/` carries its own, separate Vitest + Testing Library setup (own `vite.config.ts` `test` block, own `src/test/setup.ts`) — see `/DESIGN.md`'s Components section.
