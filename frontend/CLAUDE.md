# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Applies to `frontend/` — the React + TypeScript client, built with Vite, package-managed with Bun. See the root `CLAUDE.md` for how this fits with the backend.

## Commands

All run from `frontend/`, using `bun`, not `npm`/`yarn`:

```
bun install
bun dev              # dev server on http://localhost:5173
bun run build        # tsc -b (typecheck) then vite build -> dist/
bun run lint         # oxlint
bun run preview      # preview a production build
bun run test         # vitest run
bun run test:watch   # vitest, watch mode
```

Needs `frontend/.env` (copy from `.env.example`) with `VITE_API_URL`, pointing at the backend (`http://localhost:5073/api` by default). Vitest (jsdom + `@testing-library/react`) is configured via the `test` block in `vite.config.ts`, with global `describe`/`it`/`expect` (see `tsconfig.app.json`'s `vitest/globals` type) and jest-dom matchers loaded in `src/test/setup.ts`. `vite.config.ts`'s `test.execArgv: ['--no-experimental-webstorage']` is load-bearing, not decorative: Node 22+'s own global `localStorage`/`sessionStorage` (non-functional without `--localstorage-file`) otherwise shadows jsdom's real per-window implementation and breaks anything touching `localStorage` (`AuthContext`'s session persistence, most directly) with `Cannot read properties of undefined` — see the testing section below for the rest of the harness (MSW, `renderWithProviders`, contract-typed factories).

## Architecture

`react-router` (`BrowserRouter` in `main.tsx`) drives routing. `App.tsx` special-cases two pathnames (`/reset-password`, `/accept-invite`) as reachable while fully logged out, *before* the auth gate — everything else gates on auth state (`LoginScreen` while logged out, nothing while `loading`), then renders `AppLayout` (header, via `components/MainNav.tsx` for the section links plus the user menu) with nested routes under it. `pages/ManageLayout.tsx` and `pages/MyAcordanzaLayout.tsx` both build their left nav on `components/SideNav.tsx`, the shared `<aside>` shell (title + collapsible items). No global state library for client/UI state; that's local `useState` per page, plus two contexts (auth, pending-tasks). Server data is fetched with `@tanstack/react-query` (`QueryClientProvider` in `main.tsx`, `staleTime: 0` and `refetchOnWindowFocus: false`) — see the data-fetching bullet below. `pages/` holds route-level screens; `components/` holds shared pieces reused across them.

| Path | Page | Notes |
|---|---|---|
| `/` | `HomePage` | the hub over the app's four sections — see the root `CLAUDE.md` |
| `/routes` | `SearchPage` | "Busca" |
| `/routes/new`, `/routes/:id/edit` | `RouteFormPage` | |
| `/explore` | `ExplorePage` | "Explora" |
| `/fa`, `/fa/:slug` | `FirstAscensionistsDirectoryPage`/`FirstAscensionistPage` | "Sigue"; `/first-ascensionists*` redirects here |
| `/settings` | `SettingsPage` | |
| `/my-acordanza/*`, `/manage/*` | see the `pages/` bullet below | the two left-nav shells |
| `/map` | redirects to `/explore` | the pre-#108 map path |
| `/reset-password`, `/accept-invite` | reachable while logged out | special-cased before the auth gate, see above |

A route's shareable detail URL (`/routes/{area-slug-path}/{route-slug}`, plan 21) is a react-router "background location" overlay, not a route of its own: `App.tsx` renders its main `<Routes>` against `location.state?.backgroundLocation ?? location` (so the page behind the overlay — whichever of the six contexts it was opened from — stays mounted, filters/scroll untouched) and, only when `backgroundLocation` is present, a second small `<Routes>` on top matches `routes/*` to `components/RouteDetailOverlay.tsx`. `routes/*` also joins the route tree itself as a catch-all *below* the static `routes`/`routes/new`/`routes/:id/edit` routes (which still rank above any splat), rendering plain `SearchPage` for a fresh visit (a pasted link, a reload) with no `backgroundLocation` in history state yet — `SearchPage` then synthesizes that state itself on mount (`navigate(..., { replace: true, state: { backgroundLocation: { pathname: '/routes' } } })`) so `RouteDetailOverlay` is still the only component that ever opens the route-detail modal, regardless of how the URL was reached. The four top-nav items (Busca/Explora/Sigue/Mi acordanza) must stay in step with `HomePage`'s four cards.

Shared hooks:

| Hook | Purpose |
|---|---|
| `useDisclosure` | open/toggle/close state shared by all three menus (top nav, side nav, user menu) — outside-click and Escape (which also returns focus to the trigger) close it, and it closes on `useLocation().pathname` change so picking a link or hitting the browser back button dismisses the popup too |
| `useDebouncedValue` | debounces a filter/search value so the query keyed on it can't be raced (see the data-fetching bullet below) |
| `useSubmit` | the state machine every form modal's submit shares (clear the error, disable submit while in flight, turn a thrown `ApiError` into Spanish copy via `errorMessage`, run `onSuccess` only when the call actually succeeds) — used by `AddTickModal`, `AreaNameModal`, `AreaPolygonModal`, `ChangeEmailModal`, `FirstAscensionistNameModal`, `InviteUserModal`, `RejectReasonModal`, `RequestAreaExpertModal`, `RequestFirstAscensionistLinkModal`. It deliberately has no `finally` resetting `submitting`: a successful submit means the modal is about to unmount (or its parent closes it), so clearing state after that point is at best pointless and at worst a state update on an unmounted component — don't "fix" this back in |
| `useViewportAreas` | (plan 37) `AreaMap`'s old debounced/guarded viewport fetch, lifted out so `ExplorePage` can share one `areas` array between the map and its list — same debounced-`fetchHandle`-ref + `requestId`-guard shape as before, still not on `useDebouncedValue` (it debounces map *events*, not a state value, same reasoning as the data-fetching bullet below) |
| `useGeolocation` | (plan 37) a one-time `getCurrentPosition` snapshot (`idle`/`pending`/`granted`/`denied`/`unsupported`, auto-requested on mount, `request()` exposed again for `AreaMap`'s "locate me" button) — no `watchPosition`, this isn't live tracking |

- `context/AuthContext.tsx` — session state. Holds `username`/JWT, persists `{ token, username }` to `localStorage` (`acordanza.auth`), and pushes the token into the API client via `setAuthToken`. On mount it validates a stored token against `GET /auth/me` and drops it silently on failure; the same response also seeds `hasPermission`/`isAreaExpert`/`isFirstAscensionist`. Login is two-step when the account has a registered passkey: `login(email, password)` returns a `PasskeyChallenge` instead of completing when the backend responds `mfaRequired`; `completeLoginWithPasskey(challenge)` runs the WebAuthn assertion via `@github/webauthn-json`'s `get()` and finishes the session. `LoginScreen` drives this — on `mfaRequired` it shows a "usa tu llave de acceso" step and auto-triggers the assertion. `LoginScreen` also has a "forgot password" mode (local state, not a route) that calls `authApi.forgotPassword`; the email it triggers links to `/reset-password`, handled by `pages/ResetPasswordScreen.tsx`.
- `context/PendingTasksContext.tsx` — aggregates everything the current user can review (unvalidated routes they can validate — role-based or, via `isAreaExpert`, area-scoped; unvalidated areas; pending area-expert requests; pending first-ascensionist-link requests; pending first ascensionists, gated on `Permissions.firstAscensionistValidate`) into one `total` count, shown as the header bell badge and the `/manage/pending-tasks` nav item. Fetches all five categories as five independent `useQuery` calls, each `enabled` on its own permission gate (so pages with nothing to review never issue that category's request) and, being independent queries rather than one combined fetch, one category's failure can't blank the others' already-loaded counts. Routes/areas are fetched via the dedicated `GET /routes/pending`/`GET /areas/pending` endpoints (server-narrowed to just the pending, reviewable-by-this-caller rows), not `GET /routes`/`GET /areas` filtered client-side — since validation gates those two endpoints' visibility now (see backend `CLAUDE.md`), filtering client-side would also mean paying for a whole-table download just to render a badge count. This also dropped the `allAreas`/`areasById` state that used to exist solely so `PendingTasksPage` could resolve a pending area's breadcrumb — `AreaPendingDto.namePath` is resolved server-side instead.
- `api/client.ts` — thin `fetch` wrapper (`api.get/post/put/delete/postForm`) that attaches `Authorization: Bearer` when a token is set and throws `ApiError` (with parsed `{ error }` body) on non-OK responses; `postForm` (multipart, used for topo uploads) skips the JSON `Content-Type` so the browser sets its own boundary. One `api/*.ts` file per backend resource (`routes`, `areas`, `areaExperts`, `firstAscensionists`, `firstAscensionistLinks`, `ticks`, `topos`, `routeImports`, `users`, `account`, `passkeys`, `auth`) builds on it; `api/permissions.ts` is generated from `backend/Acordanza.Api/Authorization/Permissions.cs` (DUP-12) by `scripts/generate-permissions.ts` (`bun run generate-permissions`, no dependencies — the source is a flat `public const string X = "y.z";` list, not a real schema, so there's no `openapi-typescript`-style tool for it) — re-run it after adding/renaming a permission and commit the diff, same "regenerate and commit" contract as `generated.ts` below; CI's `openapi-contract-check` job fails the build if a regenerate would produce a diff you didn't commit. `api/queryKeys.ts` is the one place react-query key shapes live (e.g. `queryKeys.routes(filters)`, `queryKeys.route(id)`) — add an entry as each page converts rather than inlining key arrays at the call site; `api/errorMessage.ts` (`errorMessage(err, fallback)`) is the shared `ApiError` → Spanish string helper for both query/mutation errors and locally-caught ones, used at every call site that turns an `ApiError` into UI copy — the only exceptions branch on `err.status` (`AcceptInviteScreen`/`ResetPasswordScreen`'s dead-link check, `RouteDetailModal`'s enrichment-conflict check). `src/format.ts` (`formatDate`) is the analogous helper for dates: every date the UI renders is a day in a Spanish-only app, so it's always `toLocaleDateString('es-ES')`, never the browser's own locale — call `formatDate` instead of `toLocaleDateString` at a call site.
- `lib/analytics.ts` — thin wrapper over `@amplitude/analytics-browser`, gated on `VITE_AMPLITUDE_API_KEY` (unset locally, so every exported function no-ops). `main.tsx` calls `init()` once; `AuthContext` calls `identify(user.id)` after every successful `/auth/me` and `reset()` on logout; `App.tsx` calls `trackPageView(pathname)` on every route change.
- `api/generated.ts` — generated, not hand-edited: `openapi-typescript` run against the backend's checked-in OpenAPI document (`backend/Acordanza.Api/openapi/Acordanza.Api.json`) via `bun run generate-api` (`frontend/package.json`; internally `bunx openapi-typescript@<pinned version> ... -o src/api/generated.ts` — `bunx`, not a `bun add`-ed devDependency, because `openapi-typescript` only supports `typescript@^5.x` and this workspace is on `typescript@^7`; a shared/hoisted install crashes at runtime, so it gets its own isolated resolution instead). Re-run it after any backend DTO change (see backend `CLAUDE.md`'s OpenAPI section) and commit the diff — CI's `openapi-contract-check` job fails the build if a regenerate would produce one you didn't commit. `api/types.ts` re-exports the pieces of `components['schemas']` the frontend uses under the app's existing type names (`RouteSummary`, `AreaDetail`, ...) so call sites never reference `generated.ts` directly; it also keeps a few things hand-written that generation can't produce: client-only shapes with no backend DTO (`RouteFilters`, `TickFilters`, `UserFilters`, `AreaBounds`), and narrowed literal-union types where the backend's contract is a closed set but the column is a plain string — the shared `RequestStatus` alias at the top of the file covers both the request-review flows' `status` (`AreaExpert`, `FirstAscensionistLinkRequestSummary`) and the validation lifecycle's `validationStatus` (`RouteSummary`, `RouteDetail`, `AreaSummary`, `AreaDetail`, `FirstAscensionistProfile`, `Contribution`). Two label maps sit on `RequestStatus`: `reviewStatusLabels` ("Pendiente de aprobación"/"Aprobado"/"Rechazado", for the self-service request pages) and `validationStatusLabels` ("Pendiente de validación"/"Validado"/"Rechazado", for `RouteDetailModal`/`AreaPage`/`PendingTasksPage`/`MyContributionsPage`) — kept separate because the wording differs even though the underlying three states are the same; don't merge them into one map. `orientationLabels`/`orientations` (plan 28) now originate in `acordanza-design-system`'s `compass.ts` — the ordered list is also the component's geometry — and are re-exported here unchanged so every existing call site keeps working; `RouteFilters.orientation` is `Orientation[]` (a route itself still has exactly one orientation — the array is a filter shape, not a data-model change).
- `components/` — one file per shared UI piece: route browsing (`Filters`, `RoutesList`/`RouteCard`, `RouteDetailModal`, `RouteDetailOverlay`, `AddTickModal`, `TickedRouteCard`), route/area pickers (`AreaPicker`, `FirstAscensionistPicker`), areas management (`AreaTree`, `AreaNameModal`, `AreaPolygonModal`, `AreaMap`), approval-queue pieces (`PendingRequestsList` and its wrappers, `RequestAreaExpertModal`, `RequestFirstAscensionistLinkModal`, `RejectReasonModal`), plus `InviteUserModal`, `FirstAscensionistNameModal`, `Brand`, `LoginScreen`, `LoadingBar`. Two components (`AreaMap`, `AreaPolygonModal`) are deliberately `React.lazy`-imported since Leaflet is the app's heaviest dependency and only they need it — don't "simplify" either back to a static import. `lib/exploreAreas.ts` holds the framework-free viewport/grouping logic `AreaMap` and `ExplorePage` both run off, kept Leaflet-import-free on purpose.

  See `frontend/docs/components.md` for the full per-component reference — props/behavior contracts, which validation-visibility opt-outs each management screen uses, and the reasoning behind each "don't refactor this back" note.
- `pages/` — one file per route-level screen. `MyTicksPage` (`/my-acordanza/my-routes`, tick history) is not `MyOpeningsPage` (`/my-acordanza/my-openings`, routes opened as first ascensionist) — don't confuse the two. `MyContributionsPage` (`/my-acordanza/contributions`) is a read-only validation-status view, not a request flow. `FirstAscensionistsDirectoryPage`/`FirstAscensionistPage` (`/fa`, `/fa/:slug`) is the public directory; `FirstAscensionistsPage` (`/manage/first-ascensionists`) is the moderator/admin CRUD table over the same records — editing lives under "Gestionar", browsing under "Sigue". `ExplorePage` (`/explore`) is the map+list viewport-driven layout. `MyAcordanzaLayout`/`ManageLayout` are the two left-nav shells. `RouteFormPage` (`/routes/new`, `/routes/:id/edit`) handles create/edit in one page since it also hosts topo upload. `SettingsPage` covers profile/password/passkey management.

  See `frontend/docs/pages.md` for the full per-page reference — exact endpoints, query-param shapes, and page-specific UX decisions (why a `Discarded` import row re-uploads instead of re-enqueueing, why contribution tabs carry no count badges, etc.).
- Server data fetching is on `@tanstack/react-query` throughout (plan 25 finished the page-by-page conversion): a page calls `useQuery({ queryKey: queryKeys.x(...), queryFn: ... })` instead of `useState` + `useEffect(fetch).then(setX)`, and a mutation (`useMutation`) invalidates the relevant query keys on success (`queryClient.invalidateQueries({ queryKey: [...] })`) instead of a hand-rolled `refresh*` function — the same "always re-fetch after a mutation, never patch local state" discipline the app already had, just expressed as query keys instead of bespoke refresh functions. Mutations invalidate **by prefix** (e.g. `queryClient.invalidateQueries({ queryKey: ['area-experts'] })`, not the exact keyed-with-filters array), which is what lets a mutation on one page refresh another page's cache without either knowing about the other — approving an area-expert request on `/manage/pending-tasks` refreshes `/my-acordanza/my-areas` this way. `components/RouteDetailOverlay.tsx` (plan 21) is the sharpest example: the sole place a route's detail is ever fetched or mutated (its six mutations — delete/validate/reject/tick/topo-upload/topo-delete), shared by all six contexts that open it. Debounced search boxes (`UsersPage`, `FirstAscensionistsPage`, `FirstAscensionistsDirectoryPage`, `MyTicksPage`, `RequestFirstAscensionistLinkModal`) share `hooks/useDebouncedValue.ts` and key their query on the debounced value — a query keyed this way can't be raced by an earlier response landing after a later one, so none of these hand-roll an `active`/`cancelled`/requestId guard the way they used to.
- A few call sites deliberately stay off react-query, each for a stated reason rather than being unconverted leftovers: `AcceptInviteScreen`/`ResetPasswordScreen`/`ConfirmEmailChangeScreen` each do one fire-and-forget `POST /auth/validate-token` on mount, never refetched or invalidated by anything, so a query key would be ceremony around a single call; `RouteFormPage`'s load-for-edit fetch feeds form state the user immediately edits, and putting server state that's copied straight into local form state behind a cache risks a "the form reset while I was typing" bug (its submit is still a `useMutation`, invalidating `['routes']`, since a write has no such risk); `hooks/useViewportAreas.ts`'s viewport-bounded fetch (moved out of `AreaMap`, plan 37) keeps its own debounced `fetchHandle` ref over map *events*, not a state value — a different shape from the search-box debounce above, so it isn't on `useDebouncedValue`. `queryClient.ts`'s `staleTime: 0` and `refetchOnWindowFocus: false` also stay as they were — a deliberate UX call, not a gap in the conversion; revisit it separately if ever.
- **Modal/dropdown data is fetched by the thing that needs it, when it opens** — never by the page behind it. A page must not prefetch a list whose only consumer is a modal it might open (that's a request every visitor pays for so the few who open the modal save a spinner). So `RequestAreaExpertModal`/`RequestFirstAscensionistLinkModal` fetch their own pickers' options on mount, `AreaPolygonModal` fetches the polygons it draws, and `AreaPicker`/`FirstAscensionistPicker` fetch via `TreeSelect`'s/`Combobox`'s `onOpen` — their mount-time fetch is skipped entirely unless there's already a selection whose label needs resolving. Corollary: don't give a page a "is the modal worth showing" check that needs the modal's data (the modal renders its own empty state instead), and keep list endpoints backing a tree/row slim enough that the row itself needs no extra fetch — `GET /areas/roots` carries a `hasPolygon` flag so `AreaTree` can label its polygon button without loading any vertices. `components/RouteDetailOverlay.tsx` is the sharpest instance of this rule (plan 21): it's the sole owner of route-detail fetching (by `{area-slug-path}/{route-slug}`, not by id) for every context that can open it — `SearchPage`, `AreaPage`, `FirstAscensionistPage`, `MyOpeningsPage`, `PendingTasksPage`, `MyTicksPage` each just `navigate()` to the route's URL with `state: { backgroundLocation: location }` and never fetch or hold the detail themselves.

## Styling

Tokens (colors, fonts, radii, spacing) and the shared component set — `Button`, `Chip`, `EmptyState`, `GradePill`, `Modal`/`ModalActions`/`ConfirmModal`, `Pagination`, `List`/`ListRow`, `Badge`, `RemoveButton`, `Combobox`, `CompassRose`/`CompassPicker`, `TreeSelect`, `Icon` — live in the sibling `design-system/` workspace package (`acordanza-design-system`; see the root `CLAUDE.md` and `/DESIGN.md`), imported as `import { X } from 'acordanza-design-system'` and, for its CSS, `@import 'acordanza-design-system/styles.css'` at the top of `src/styles.css`. `src/styles.css` itself is plain CSS (no CSS-in-JS, no Tailwind) that only covers app-shell/page layout and pieces not yet promoted to the design system (forms, the picker "create new" sub-form). It's a light theme, not dark — driven by the same CSS custom properties the design system defines (`--bg`, `--accent`, `--font-display`, etc.). Extend the theme by adding/reusing those variables rather than hardcoding colors in component-scoped styles (styling is global, not per-component); new reusable UI belongs in `design-system/src/components/`, not `styles.css`.

The app has exactly one breakpoint, `@media (max-width: 720px)`, as a single block at the very bottom of `styles.css`. It must stay last: at equal specificity, a same-selector rule declared later in the cascade wins regardless of the media query, so every base rule a mobile rule overrides has to appear above that block in the file — a mobile rule added anywhere else silently loses. `design-system/src/components/Modal/Modal.css` repeats the same `720px` literal for its own mobile padding step-down (see below); it's a literal, not a shared custom property, because CSS custom properties can't be used in a media condition and a `@custom-media` plugin across two build pipelines isn't worth it for one number — keep the two in sync by hand.

Collapsing nav (top bar, `/manage`/`/my-acordanza` left nav) into a hamburger on mobile uses one CSS-only technique, no JS breakpoint: the links live in a wrapper (`.main-nav-items`, `.side-nav-items`, `.side-nav-header`) that's `display: contents` in the base rules — invisible to layout, so on desktop the links stay direct flex children of their parent and inherit its `gap` exactly as if the wrapper didn't exist — and becomes a real `display: none`/`.is-open{display:flex}` popup (class `nav-popup`) only inside the `720px` block. Don't "simplify" a `display: contents` rule to `display: flex`; that reintroduces a nested flex container and shifts desktop spacing.

## Linting & types

`oxlint` (`.oxlintrc.json`) enforces `react/rules-of-hooks` as an error; TypeScript is strict (`noUnusedLocals`, `noUnusedParameters`, `verbatimModuleSyntax` — type-only imports must use `import type`).

## Testing

`src/test/` holds the harness shared by every page/component test, colocated as `X.test.tsx` next to `X.tsx`:

- `server.ts`/`setup.ts` — an MSW `setupServer()` with **`onUnhandledRequest: 'error'`**. This is doing real work, not just hygiene: it's what mechanically enforces the "modal/dropdown data is fetched by the thing that needs it, when it opens" rule above — an accidental page-level prefetch shows up as a failing test (an unhandled request), not a review comment. There are no default handlers; every test registers exactly the routes it needs via `server.use(...)`.
- `apiUrl.ts` — the `http://localhost:5073/api` base `api/client.ts` falls back to when `VITE_API_URL` isn't set (the case in the test environment, since no `.env` is loaded); handlers match requests against it.
- `factories.ts` — one `make*` factory per DTO the suite constructs (`makeRoute`, `makeArea`, `makeMeResponse`, …), each a `Partial<T>`-overridable object typed off `api/generated.ts`'s `components['schemas']` rather than hand-rolled. This is deliberate: test files live under `src`, so the existing `tsc -b` in `bun run build` typechecks them too — a backend DTO change that regenerates `generated.ts` breaks the *mocks* at build time, not just the app. Combined with CI's `openapi-contract-check` job (which fails if `generated.ts` is stale), the loop closes: mocks can't silently drift from the real API contract the way hand-written fixtures would.
- `renderWithProviders.tsx` — wraps a subject in the three things pages assume: a fresh `QueryClient` (`retry: false`, so a mocked-error test fails fast instead of retrying for seconds), a `MemoryRouter` (`initialEntries` configurable), and auth state. Auth state has two modes:
  - **Default: a direct `AuthContext` value.** `auth: {...}` overrides merge over a logged-in-as-plain-user default (see `makeAuthValue`) — no network calls, so permission-matrix tests (`DetailModal.test.tsx`, `Filters.test.tsx`, `ManageLayout.test.tsx`) just vary `permissions`/`isAreaExpert`/etc. and assert what renders. `AuthContext` is exported from `context/AuthContext.tsx` (`const` → `export const`, no other change) for exactly this reason — it's a smaller, more honest change than restructuring the provider to take injected state.
  - **`useRealAuthProvider: true` mounts the actual `AuthProvider`** (`localStorage` + `GET /auth/me`) — the only way to test the bootstrap/login/logout state machine itself: dropping an invalid stored token silently, the two-step passkey login (`AuthContext.test.tsx`, `LoginScreen.test.tsx`), `logout()` clearing the shared query cache. `auth` overrides are ignored in this mode since the provider computes its own state. Mock `@github/webauthn-json`'s `get()` for passkey flows — the real WebAuthn API doesn't exist in jsdom.

Working agreement:

- **Bug fix** → a failing test that reproduces it, first. This is where the suite pays for itself fastest, and it's the one thing a screenshot can never do: prove the bug is gone *and* stay behind to prove it stays gone.
- **New endpoint** → a row in the backend's authorization-matrix tests (`backend/Acordanza.Api.Tests/`), plus a happy path and one edge case.
- **New page or component** → at minimum, it renders with realistic contract-typed data, and any permission-gated action is covered both ways (rendered and hidden). Testing what the UI *shows* is not a substitute for the backend enforcing it, and vice versa — neither test layer covers what the other does.
- Not a coverage target. Coverage percentages push tests toward trivial pages and away from the authorization matrix, which is where the value actually is.

Leaflet map rendering (`AreaMap`, `AreaPolygonModal`) is out of scope for this layer — jsdom has no real layout, so testing it here means mocking so much the test ends up asserting the mocks. Cover the surrounding logic (viewport-bounded fetching, the polygon payload sent on save) and leave rendering to manual/`run-acordanza` checking. Full end-to-end journeys likewise live outside this suite, in the `run-acordanza` skill (Playwright, deliberately tiny) — this layer carries the regression load instead.

`design-system/` carries its own, separate Vitest + Testing Library setup (own `vite.config.ts` `test` block, own `src/test/setup.ts`) — see `/DESIGN.md`'s Components section.
