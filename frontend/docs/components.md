# Shared components reference

Full per-component notes for `frontend/src/components/`, extracted from `frontend/CLAUDE.md` to keep that file loadable without pulling in every shared component's implementation detail on every frontend task. See `frontend/CLAUDE.md`'s Architecture section for the routing/data-fetching overview and when to read this file.

- `components/` — one file per shared UI piece. Route browsing: `Filters` (search/area/grade/aid grade/orientation/gear/hasTopo, debounced 250ms via `SearchPage`'s `useDebouncedValue`; the grade/aid-grade options come from `GET /routes/grades`/`GET /routes/aid-grades`, since the backend only reports grades actually in use rather than the full grammar it validates against — see `GradePill`'s `gradeBand`/`isAidGrade`; the grade `<select>` has a `"none"` sentinel option ("Sin grado") for gradeless routes (plan 34), matched server-side against `Grade == null`; the aid-grade `<select>` renders only when `GET /routes/aid-grades` returns a non-empty list, so a log with no aid routes yet doesn't grow a permanently empty filter, and gets no "sin grado artificial" option since nearly every route has no aid grade; orientation is a `CompassPicker` multi-select (plan 28), not a `<select>` — `filters.orientation` is `Orientation[]`, and the picker itself normalises every toggle back into canonical compass order so two differently-ordered selections hash to the same react-query key, see `api/queryKeys.ts`; a "Cualquiera" ghost button next to it clears back to `[]`, shown only when something is selected), `RoutesList`/`RouteCard` (`RoutesList`'s `onSelect` takes the clicked `RouteSummary`, not just its id — callers build the shareable detail URL from its `slug`/`areaSlugPath`, see `api/routes.ts`'s `routeDetailPath`, plan 21; `RouteCard` shows a `design-system` `Icon name="check"` when `hasTick`, never a count — ticks are private, see backend `CLAUDE.md`; it also shows a `Chip status={route.validationStatus}` when the route isn't approved, so a route the caller can see purely because they authored it — pending or rejected, everywhere else invisible — doesn't read as a bug; `AreaPicker` does the analogous thing via `TreeSelect`'s `suffix` prop, appending `validationStatusLabels[...]` to a non-approved node; the left accent border is colored by `gradeBand(route.grade)` — `grade-band-6`/`-7`/`-8-9` classes, ungraded/below-6a routes keep the default teal — and a secondary `.rc-meta` line folds in orientation/length/gear via the shared `RouteMeta` component (plan 20, extracted plan 28 since `RouteCard`/`TickedRouteCard` both had their own copy) — a small `CompassRose size="sm"` needle plus `orientationAbbr`/length/gear, rather than the full Spanish orientation word: at 18px an eight-wedge rose turns to mud, so the needle shape carries the direction and the abbreviation carries the exact value), `RouteDetailModal` (route detail incl. topo photos and the validate/reject actions — "Rechazar" opens the shared `RejectReasonModal`; ticks aren't listed here — only a button opening `AddTickModal`; the body below the head is a sequence of bordered `.detail-section` blocks — a stats row (grade/length/orientation/gear/obligatory grade), description, optional gear notes, `route.links` as external links, first-ascensionist credits, topos, and the tick button — rather than one undifferentiated scroll, plan 20; the orientation stat is a `CompassRose size="md"` needle above the full Spanish word, plan 28 (rewritten plan 36 — no more eight-wedge view at `md`, since the word beside it already said which one); rendered only by `RouteDetailOverlay` now, never directly by a page — plan 21), `RouteDetailOverlay` (the sole owner of route-detail fetching and its six mutations — see the "Modal/dropdown data" rule below), `AddTickModal`, `TickedRouteCard` (a row in `MyTicksPage`'s history; shares `RouteCard`'s grade-band accent and `RouteMeta` line — `MyTickDto.Length`, see backend `CLAUDE.md`). Route/area pickers used by `RouteFormPage`: `AreaPicker` (plan 35 — a thin wrapper around `acordanza-design-system`'s `TreeSelect`: one `useQuery` on `GET /areas/tree` holds the whole area tree client-side, `staleTime: 5 * 60_000` as a deliberate, commented exception to `queryClient.ts`'s global `staleTime: 0`, since the tree changes rarely and all four call sites share the key — whichever one opens first across the session pays for the rest, and every area mutation, including this component's own create below, still invalidates the `['areas']` prefix; `allowClear` alone distinguishes the two semantics — *filter* (`Filters`/`MyTicksPage`, clearable, the backend expands to descendants, so a "Incluye N subsectores" hint renders below the input whenever the selected area has children) from *assign* (`RouteFormPage`/`MyImportsPage`, the exact node, no hint); an LRU of up to 8 recently-picked area ids in `localStorage` under one global key (`acordanza.recentAreas`, not per call site, not cleared on logout) backs `TreeSelect`'s `headNodes`, padded with the highest-subtree-route-count roots when recents are thin; `allowCreate` wires `TreeSelect`'s `onCreateChild` (a "+" per row plus one at the popup's foot) straight into `areasApi.createArea` — the parent is implied by which affordance was clicked, so there's no `<select>` of every area to render), `FirstAscensionistPicker` — `RouteFormPage`'s own orientation field is a single-select `CompassPicker` (`multiple={false}`) plus a "Sin especificar" clear button, since `ClimbingRoute.Orientation` stays nullable and a route still has exactly one orientation (clicking the already-selected sector doesn't deselect it — that's native `radiogroup` behaviour, and clearing stays an explicit action). Areas management (`AreasPage`/`MyAreasPage`): `AreaTree` (lazy-loaded via `GET /areas/roots`+`/{id}/children`; its expand toggle and "Editar"/"Eliminar"/"+ Subsector" actions render via `Icon` now, plan 39 — the row toggle shares `TreeSelect`'s `chevron`/`icon-rotated` convention rather than a separate glyph), `AreaNameModal`, `AreaPolygonModal` (draws `Area.Polygon` on the map, `leaflet-draw`; `React.lazy`-imported by `AreaTree`, see below). `AreaTree` and `AreaPolygonModal` both pass `includeUnvalidated: true` — the management screens exist to fix records including rejected ones, so they opt out of the approved-or-mine visibility filter every other reader gets by default (backend `CLAUDE.md`'s "Validation visibility"); safe unconditionally here since `/manage/areas` already gates on `area.edit`, which is only ever granted alongside `area.validate`. `AreaMap` — `react-leaflet` + `leaflet`, plus `react-leaflet-cluster`/`leaflet.markercluster` clustering top-level markers (plan 37); rendered by `ExplorePage` (the pre-#108 `/map` path just redirects to `/explore` now). Since plan 37 it's a controlled component, not a self-fetching one: `ExplorePage` owns `useViewportAreas`/`useGeolocation` and passes `areas`/`selectedAreaId`/`flyTarget` down as props, `AreaMap` still keeps its own `center`/`zoom` state (fed by its `BoundsTracker`) purely to compute its own render groups via `lib/exploreAreas.ts`'s `deriveVisibleAreas` and report bounds upward via `onBoundsChange`. A `flyTarget` prop (`{ bounds }` or `{ center, zoom }`) drives an imperative `mapRef.current.fitBounds`/`flyTo` effect — `MapContainer`'s `ref` forwards straight to the underlying `L.Map` in `react-leaflet@5`. Selecting a list row or a map pin/polygon both update the same `selectedAreaId`/`onSelectArea` pair (marker/polygon `eventHandlers.click` on the map side, a `ref` map + `.openPopup()` effect keeping the two in sync), so the list and the map always agree on what's selected. `AreaMap` and `AreaPolygonModal` are both `React.lazy`-imported (behind a `Suspense` in `ExplorePage`/`AreaTree` respectively) rather than statically — Leaflet is ~75 kB gzip, the single heaviest dependency in the app, and these two components are the only ones that need it (plan 23); don't "simplify" either back to a static import, that quietly regresses the initial bundle for every visitor who never opens a map. `lib/exploreAreas.ts` holds the framework-free logic both `AreaMap` and `ExplorePage`'s list run off — `deriveVisibleAreas` (the same topLevel/active-area/subareas grouping `AreaMap` used to compute privately), `sortByDistance`, `boundsOfPolygon` — so the list can mirror exactly what's pinned on the map by construction, not by convention; it's plain TypeScript with no Leaflet import (only a type-only one) so importing it doesn't pull the lazy chunk into the main bundle. Approval-queue pieces shared between `PendingTasksPage` and elsewhere: `PendingRequestsList` (generic approve/reject list — `PendingAreaExpertRequests`/`PendingFirstAscensionistLinkRequests` are thin wrappers supplying the subject field and API calls), `RequestAreaExpertModal`, `RequestFirstAscensionistLinkModal`, `RejectReasonModal` (the shared "reason required" form every reject flow uses — request-review decisions and, now, `IValidatable` rejections alike). `InviteUserModal` — shared by `UsersPage` and `MyInvitesPage`; the `allowRoleSelection` prop is what separates them (admins pick the new account's role, a plain inviter doesn't get the choice), so keep the role field behind that flag rather than forking the modal. `FirstAscensionistNameModal` (`FirstAscensionistsPage`'s rename/create dialog — the `AreaNameModal` counterpart; the pickers use their own inline "create new" sub-form instead, not this), `Brand` (the wordmark+mark used by `AppLayout` and `LoginScreen`), `LoginScreen`, `LoadingBar`.
