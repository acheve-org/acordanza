# Page-by-page reference

Per-page implementation notes for `frontend/src/pages/`, extracted from `frontend/CLAUDE.md` to keep that file loadable without pulling in every page's detail on every frontend task. See `frontend/CLAUDE.md`'s Architecture section for the routing overview and when to read this file.

- `pages/MyTicksPage.tsx` (`/my-acordanza/my-routes`, "Mis vías") is the current user's own tick history — infinite-scroll paginated via `GET /ticks/mine`, filtered by the same q/areaId/gear shape `Filters` uses. Don't confuse it with `pages/MyOpeningsPage.tsx` (`/my-acordanza/my-openings`, "Mis aperturas"), which lists routes the user opened as first ascensionist, via `listMyOpenings()` (`GET /routes?openedByMe=true`) — server-side filtered and exempt from validation visibility (these are the caller's own credits regardless of who created the route or its status), so this page no longer downloads every route and filters client-side. `pages/ClaimFirstAscensionistPage.tsx` and `pages/MyAreasPage.tsx` are the self-service request UIs (first-ascensionist link, area-expert) for `FirstAscensionistLinksController`/`AreaExpertsController`. `pages/MyContributionsPage.tsx` (`/my-acordanza/contributions`, "Contribuciones", `api/contributions.ts`) is a different thing again: not a request flow, but a read-only three-tab view (Vías/Sectores/Aperturistas) over the validation status — pending/approved/rejected, with the rejection reason when applicable — of everything the current user has *created*, using `useQuery` from the start rather than the legacy `useState`/`useEffect` pattern below. Each tab is its own paginated endpoint (`GET /contributions/{routes|areas|first-ascensionists}`, issue #149), reached through the single `listMyContributions(kind, page)` wrapper; the tab keys *are* the API's kind strings, and there's exactly one `useQuery` keyed on the active tab plus its page, so a tab that was never opened never issues a request (`MyContributionsPage.test.tsx` pins that mechanically via `onUnhandledRequest: 'error'`). Page state is per tab, so switching away and back returns to the page you left, and the tabs carry no count badges — a badge on an unvisited tab is exactly what would force its data to be fetched eagerly. `pages/MyInvitesPage.tsx` (`/my-acordanza/my-invites`, "Mis invitaciones", `GET /users/my-invites`) lists the accounts the caller has invited and their quota (`Te quedan N de M invitaciones.`, or unlimited when `invitesLeft` is `null` — admins), opening the shared `InviteUserModal`. Note this page is *not* permission-gated the way `/manage/users` is: `Permissions.userInvite` is held by every role (see backend `CLAUDE.md`), so inviting is an ordinary-user feature and only the quota — enforced server-side — limits it. `pages/MyImportsPage.tsx` (`/my-acordanza/my-imports`, "Mis importaciones", `api/routeImports.ts`, plans 30 and 31) is the submit form *and* the list of the caller's route imports in one page — deliberately one, since the list is the only place an outcome can appear and splitting them would split one flow across two screens. The form is a two-option switch (`.segmented-control`) — «Desde una foto» / «Desde un enlace» — over a shared sector picker, since the sector is required either way and is the one thing never inferred; the two modes post to `/route-imports/image` (multipart) and `/route-imports/url` (JSON) respectively. `RouteFormPage` links across to it ("¿Tienes una foto o un enlace? Crea la vía desde ahí"), since `/routes/new` is where someone with a topo in their hand — or a blog post open in another tab — actually starts. Submitting shows an inline "en unos minutos" note and nothing else: no polling, no progress bar — the work is asynchronous, the row is already in the list as «Leyendo», and a reload updates it, the same deliberate non-interactivity as plan 18's enrich button. A `Discarded` row offers "Volver a intentarlo", which sets the form up again rather than re-enqueueing: a link genuinely can be re-read (the URL is still on the row, and the user may want to fix it or the sector first) while a photo's staged image is deleted the moment a run discards it (backend `CLAUDE.md`'s Route import), so it's really a re-upload — one code path either way. A `Discarded`/`Failed` row also offers "Eliminar" (plan 33, `ConfirmModal`, same pattern as `FirstAscensionistsPage`'s delete) — cleanup of the row only, never of any route/topo/link it produced; `Pending`/`Completed` rows show neither button, matching what the backend will actually accept. `routeImportStatusLabels` in `api/types.ts` is a *third* label map alongside `reviewStatusLabels`/`validationStatusLabels`, separate for the same reason those two are: these four states are the import pipeline's, not a review's; `routeImportKindLabels` sits beside it for the «Foto»/«Enlace» prefix on each row.
- `pages/FirstAscensionistsDirectoryPage.tsx` (`/fa`, "Sigue") lists aperturistas with a debounced name search, each card showing how much they've opened and where (`GET /first-ascensionists/profiles`); `pages/FirstAscensionistPage.tsx` (`/fa/:slug`) is one opener's page — resolved via `GET /first-ascensionists/by-slug/{slug}` (`FirstAscensionist.Slug`, issue #137 — see backend `CLAUDE.md`) — plus the routes they opened (`GET /routes?firstAscensionistId=`, fetched with the id off the resolved profile) via `RoutesList`, whose row click navigates to the shared route-detail overlay the same way `AreaPage` does (see `components/RouteDetailOverlay.tsx`, plan 21). `App.tsx` redirects the pre-slug `/first-ascensionists*` paths to `/fa` — an old numeric link can only land on the directory, not the specific opener, since an id can't be mapped to a slug without a fetch. Don't confuse either with `pages/FirstAscensionistsPage.tsx` (`/manage/first-ascensionists`), the moderator/admin CRUD table over the same records — read-only browsing lives under "Sigue", editing under "Gestionar". `FirstAscensionistsPage` calls `listFirstAscensionists(q, true)` — `includeUnvalidated: true`, same opt-in `AreaTree`/`AreaPolygonModal` use, safe here since the page is already gated on `first-ascensionist.delete`, only ever granted alongside `first-ascensionist.validate`.
- `pages/ExplorePage.tsx` (`/explore`, "Explora", plan 37) — a viewport-driven two-column layout: `AreaMap` on the right, a list mirroring exactly what's currently pinned on the map on the left (own scroll region, the page itself never scrolls), sorted by distance from the map's current center. Each row's `leading` slot (plan 38) shows a depth icon — a mountain glyph in `--depth-root` blue for a root area, a pin glyph in `--depth-subarea` green for a subarea, the same tier-coloring `AreaMap`'s polygons use (`DEPTH_COLORS` in `lib/exploreAreas.ts`) — instead of a "Con sectores"/"Sin sectores" subtitle; a subarea row's subtitle is still the parent area's name (a disambiguating breadcrumb, since sibling subareas across different top-level areas can share a name). Selecting a row flies the map to that area (its polygon bounds, or a `SUBAREA_ZOOM` fly-to on its centroid when it has none); selecting a pin updates the list's selection the same way (`selectedAreaId`/`onSelectArea`, see `AreaMap` above). Geolocation (`useGeolocation`) auto-prompts on mount and flies the map to the resolved position at `DEFAULT_LOCATION_ZOOM`; denied/unsupported/still-pending, the map just stays on `AreaMap`'s existing Spain-wide default — no separate fallback view is computed. Below `720px` the map goes full-bleed and the list becomes a bottom sheet (`mobileListOpen`, plain `useState`, no outside-click/Escape semantics) collapsed to a handle strip by default; selecting a row also collapses it.
- `pages/MyAcordanzaLayout.tsx` (`/my-acordanza`) — left-nav shell for a user's own stuff, reached from the top nav's "Mi acordanza" item. Structurally identical to `pages/ManageLayout.tsx` (`/manage`, reached via "Gestionar", shown only if the user can edit areas or manage users): both are `<Outlet>`-based parent routes sharing the `.side-nav-layout`/`.side-nav`/`.side-nav-item`/`.side-nav-content` CSS in `styles.css`. Pages nested under either (`MyAreasPage`, `ClaimFirstAscensionistPage`, `MyContributionsPage`, `MyTicksPage`, `MyOpeningsPage`, `MyInvitesPage`, `AreasPage`, `UsersPage`, `PendingTasksPage`) render bare — no own `<main>`/page-padding wrapper, no "Volver" link — since the shared shell's `.side-nav-content` supplies layout and its persistent aside nav already provides a way back. `UsersPage` (admin-only, `Permissions.userManage`) lists/filters/paginates accounts and opens `InviteUserModal`; each row also shows who invited the account and when, plus its confirmation date, whichever of those the account actually has (a "Sin confirmar" chip stands in for a missing confirmation date on accounts that haven't accepted their invite yet).
- `pages/RouteFormPage.tsx` (`/routes/new`, `/routes/:id/edit`) — a full page, not a modal, since it also hosts topo photo upload/removal when editing; shared between create/edit via the `editing` (route `id` present) branch. Only Sector and Nombre are required fields (plan 34); everything else (grade, aid grade, obligatory grade, length, orientation, gear, recommended/optional gear, description, first ascensionists, links) sits behind a native `<details>`/`<summary>` "Más detalles" disclosure below them — a plain HTML element rather than a design-system component, since there's one use site and `<details>` gives keyboard operation and the ARIA role for free. It opens by default when editing a route that already has any of those fields set, so an editor doesn't land on two empty-looking fields and conclude the data is gone. `RouteFormState` holds `grade`/`aidGrade`/`length` as strings (never `null`, same convention as its other fields) so the length input can represent "empty" — `Number('')` is `0`, a legal length, which is why `length` isn't a plain `number` here; submit converts blank strings back to `null` for the wire, and client-side validation (`gradeBand`/`isAidGrade`) only runs when the corresponding field is non-blank.
- `pages/AcceptInviteScreen.tsx`/`pages/ResetPasswordScreen.tsx` — both reachable while logged out (see `App.tsx` above), both call `POST /auth/validate-token` on mount to show a dead-link error immediately rather than only on submit, and both complete via the same backend password-reset-token mechanism (see backend `CLAUDE.md`'s Auth model).
- `pages/SettingsPage.tsx` — profile name editing, password change (both `api/account.ts`), and passkey management (`api/passkeys.ts`): list/register/delete. Registration calls `@github/webauthn-json`'s `create()` with the options the backend returns, wrapped as `{ publicKey: options }` — the backend's Fido2NetLib option objects already serialize to the same WebAuthn-L3 JSON shape the library expects, no manual base64url handling needed.
